# 执行超时守门（沉默即死）

> 来源：Hermes `SOUL.md` §十四「执行超时铁律」（2026-08-03 用户亲定，标注**不可违背**）
> 适用：**所有 Agent 的所有执行**——不只 Hermes，也包括本会话的每一步 Bash / 脚本 / 后台任务。

## 核心判据

# 慢 ≠ 死，沉默 = 死。

判断一个执行是否卡死，**唯一依据是「最后一次新进展距今多久」**，不是「跑了多久」。

**超过 10 分钟没有新进展**（无新日志行、无新文件、无新输出）：
→ **立即判卡死 → 停手中止 → 报告卡在哪个步骤。禁止继续等待。**

> 原话：「"再等一等就会好"是本系统**被证伪过最多次**的想法（半开 TLS、无超时子进程、坏 WSL bash 全都永不返回）。」

## 超时预算表（所有执行必须遵守）

| 步骤 | 硬预算 | 说明 |
|------|--------|------|
| 单次 LLM 调用（含全部 key 轮询） | **≤ 10 分钟** | 本机实测单次 API 可达 390s，但含轮询的总等待必须封顶 |
| LLM 失败重试 | **只走 1 轮** | 全部 key 一遍不过 = 当日网络/账号层故障，等下个调度点，**不立即重试**（cron 铁律⑤推广到一切执行） |
| Whisper 转录 | 视频时长 ×0.8 + 2 分钟 | CPU 转录是正当慢活，按公式给预算 |
| 单条笔记/视频处理 | ≤ 3 分钟（不含反爬冷却） | 冷却 sleep 是设计内时间，不算沉默 |
| 整个 cron 任务 | **≤ 25 分钟** | 超了说明拆得不够小，回到 cron 铁律① 拆任务 |

## 例外（设计内的慢，不算沉默）

- **反爬冷却的固定 sleep**（有日志声明"冷却中"）
- **Whisper / 长生成等持续输出的环节**（有日志心跳即活）

> 判据永远是：**最后一次新进展距现在是否超过 10 分钟**。

## 落地做法（本会话怎么执行）

### 1. 起手就设超时，别靠"看着办"

Bash 工具已内置超时（默认由 `BASH_DEFAULT_TIMEOUT_MS` 控制）。**长时间任务用 `run_in_background: true`**——它会自动通知完成，不需要轮询、不需要 sleep。

```
# 正例：已知长任务 → 后台跑，等通知
run_in_background: true  →  npm install / 构建 / 大文件处理 / 批量采集

# 反例：前台干等几分钟，然后卡死
```

### 2. 绝不 sleep 轮询

不要写「sleep 60 然后再查一次」的循环。这是"傻等"的典型形态。要么前台等它返回，要么后台跑等通知。

### 3. 出现沉默立刻止损

若某个前台命令长时间无输出且已接近预算：
1. **停手**（不要"再等等"）
2. 报告：卡在哪个步骤、最后一条输出是什么、已等待多久
3. 让用户决策是重跑、换方法还是排查

### 4. 别把「慢」误判成「死」，也别把「死」误判成「慢」

- 合法慢：Whisper 转录、反爬冷却（有声明）、大文件 IO
- 真死：**没有任何新进展**的静默 —— 典型如半开 TLS、无超时子进程、坏 WSL bash

## 自检清单（每次执行前过一遍）

- [ ] 这个执行可能超过 10 分钟吗？→ 超了就用后台模式
- [ ] 有明确的完成信号吗（退出码 / 新文件 / 通知）？
- [ ] 如果它卡住，我怎么知道自己卡住了？（要有可观察的进展标志）
- [ ] 我在等的是"正当慢"还是"沉默"？

## 与其他 skill 的关系

- **`repair-gate`**：卡死之后要不要动手修？→ 走维修路径，**只报告不自修**
- **`obsidian-vault-health-check`**：巡检 Hermes cron 时，用它的 `executions.db` 分析定位真凶，不要靠轮询猜
