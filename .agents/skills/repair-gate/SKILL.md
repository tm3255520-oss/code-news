# 维修守门（只执行、只报告，不动手）

> 来源：Hermes `SOUL.md` §十三「维修路径」
> 适用：**所有 Agent**，对本会话尤其关键——**Work Buddy 持全库可读写权限**。

## 核心规则

发现问题的**默认动作是「报告」，不是「修理」**。

修理必须走完整四步：

1. agent 报告问题 → **用户看到报告**
2. **用户确认**要修，并由**用户指定的专用（高端）模型会话**先做测试，**确认问题真实存在**
3. 专用模型测试确认后，才允许**在该会话中**修理
4. 修理完成必须带**真实运行证据**（对照 SOUL §十二）

> **未走这条路径的一切"维修"，无论动机好坏，一律视为破坏。**

## 为什么（不是教条，是血泪）

- **不同会话的模型能力不同**。弱模型"认为有问题"的判断本身不可靠，让它修 = **越修越乱**。
- **skills 目录无版本控制**，改坏**不可回滚**。

**真实案例（2026-08-03）**：某会话把 `fix_xhs_transcript.py` "修复"成 curl + `Bearer ***` 不可用版本。

## 例外（仅两种）

1. **用户当场明确下达修改指令**（如"改一下这个 skill""确认修复"）
2. **新资产的开发会话**（资产尚未交付验证，本来就是工地）

除此之外：**只执行，只报告，不动手。**

### 例外 2 的**流程内建通道**：三段工作流返工（2026-10-12 补充）

**「三段工作流（计划 workbuddy → 实施 codex → 验证 claude）」本身就是一条结构化的例外 2 通道。**

验证段裁决**不通过**、并把缺陷落成「**文件名 + 行号 + 最小修复目标**」时：
- 该资产**尚未交付**（仍在验收循环内）→ **属例外 2**；
- 返工应**原样派回实施方**（写「修复卡」→ `devflow.py build`），**计划方不得代改**——
  代改会破坏「实施/验证分离」这条三段工作流的根基（自验自过）；
- 返工后**必须再由非实施方复验**，不得由实施方自证通过。

**判定句式**：这件事有「验收卡 / 修复卡 + 独立验证方」吗？→ 有 → 走流程，属例外 2；
没有、只是你路过看到的问题 → **报告，不动手**。

**⚠️ 修复合的写法有讲究（血泪）**：只写「方向」会让实施方凑合实现——
2026-10-12 评论互动线 D1 首版修复卡只写「host 是不是真实域名」，实施方给出「含点即放行」的宽判据，
**被验证方自设反例挖出 6 条漏网 → 多返工一轮**。
**对策**：修复卡里给**精确判据**（可直接采用的代码或等价条件）+ 计划方**离线自验的逐条证据**（N 反例全拦 / M 正例全留）。

**⚠️⚠️ 离线自验的三条硬纪律（2026-10-12 同日第二次踩坑，比上一条更隐蔽）**：

**① 自验必须跑「完整集合」，报告里的数字必须来自完整机器统计——禁止看前 N 条推断全集。**
- 踩坑实况：自验脚本写的是 `for t, h in reg_fix[:20]:`（只打印前 20 条），
  但报告里写成「**全部 7,030 条均含账号字面**」→ **误报**。
  实施方跑完整过滤后发现其中有 2,415 条不含该特征，**反过来纠正了计划方**。
- 🔴 铁律：**「脚本打印了多少条」≠「实际有多少条」**。凡要写进报告的数字，
  必须是脚本**对全集统计**得出的；做不到就对全集跑一遍计数，**宁可多跑一次，不可推断**。
- 自查句：*我这个数字，是机器数出来的，还是我看几条猜的？*

**② 判据的「口径」必须写进修复卡，并说明它的边界；口径不全 = 下游照字面判失败。**
- 踩坑实况：默认口径写成「联系方式字面 = `[a-zA-Z0-9_]{5,}`」，
  **漏掉了 `wx`（仅 2 字符的微信缩写）** → 把「加wx」这类**真引导的正确拦截**算成了误杀候选。
- 🔴 铁律：口径要**枚举完整**（账号串 **+** 缩写/谐音/拼音变体），并**明写"哪些算、哪些不算"**。
  若口径本身有争议（如「引用式句子」算不算误杀），**写进修复卡让验证方独立裁定**，别自己拍。
- 配套：**穷举词表的四个维度（前缀/动词/联系方式/后缀）要随口径一起写进卡**，否则验证方无法复现。

**③ 判据不确定时，宁可把「残余风险」明写出来，也不要靠扩大口径来"凑绿"。**
- 实例：`主加wx的意思是什么`（引用式）被拦 —— 属**低概率、方向保守**的残余，
  **如实登记为残余风险并说明为什么不修**（收它要重开 `加wx123` 类漏拦面，不划算），
  而不是改口径把它划成"非误杀"。

**④ 要写进修复卡的「判据本身」，必须先用可运行代码证明「语法合法 + 语义正确」——不能只凭读起来对。**

- 踩坑实况（同日第三次，最隐蔽）：验证方给的「最小修复目标」正则
  `(?<![不别莫勿](?:用|要|再|需要|用不着|莫要|无需)?)` 是**可变宽度后顾**，
  Python `re` **直接抛异常**（`look-behind requires fixed-width pattern`）→
  计划方若照抄进卡，实施方一跑就崩。
- **更隐蔽的一层**：**后顾里的方括号是「字符类」，宽度只有 1**。
  `(?<![不需要])` ≠ `(?<!不需要)`：前者含义是「前一个字符不是 **不/需/要**」，
  会把 **「要」开头的真引导**（`要加wx`、`需加wx`）**静默放行** →
  **不报错、不崩溃，只是悄悄漏拦**。错法与正法长得几乎一样，肉眼极易漏。
- 🔴 铁律：判据进卡前必须 `re.compile(<最终正则>)` **跑通**，并**各造一组正例/反例实测**。
  凡属「用错不报错、只静默失效」的判据，**必须在卡里点名它错在哪、怎么认**，
  否则实施方会踩进同一个坑。
- 自查句：*我这条判据，是编译通过 + 正反例实测都对了，还是我读着觉得对？*

**⑤ 取交付物「指纹」必须在后台任务**结束之后**——不能在任务 running 期间对照报告声称的值。**

- 踩坑实况：实施方返工任务仍在跑（"快了"），计划方先取了一次 sha256 得 `f33a4579…`；
  实施方最终报告声明 `11b68343…`。**实施方在写报告前还在改文件**（补自检用例），
  mtime `23:20:43` 才是定稿。若不是复核一遍，就会拿错指纹去派复验。
- 🔴 铁律：**`completed` 之前的一切文件读取都只是"取样"，不是"交付物"**。
  取指纹/跑判据的前置条件是任务已结束 + mtime 稳定。

**⑥ 「自检全绿」是**假绿**——穷举的「维度」必须覆盖卡面声明的**全部自变量**。**

- 踩坑实况（同日第四次）：上一版缺陷自检 **52/52 全绿**，却有 **7,920 条真误杀**。
  根因：穷举词表的 `前缀` 维只写了**单字否定**（`不`/`需`），**没有双字/三字否定**——
  即**穷举的维度漏了刚修的那个变量**，于是它**永远测不到自己**。
- 🔴 铁律：**每声明一个自变量，穷举里就必须有这一维**；自检用例集合**之外**的东西，
  自检永远抓不到。**「自检全绿」不能替代「维度完整的穷举」**——
  这条写进修复卡时要点名：「本轮的缺陷维度 X，必须在穷举的前缀维中出现」。
- 自查句：*这轮改的是哪个维度？穷举里有没有这个维度？*

**⑦ 卡面判据若允许「等价证据兜底」，必须**预先写明**；否则就是判据留白。**

- 踩坑实况：复验卡某组写「原文 9 条既有拦截用例 **9 条**（回归保护）」，
  但实施方自检里的既有 `bad` 只有 **4 条** → 该组**未落地为字面清单**。
  复验方**自行裁量**为「不构成不通过」（由「原文 pattern 未改」+ 独立实测兜底）。
  裁量结果合理，但属**判据留白**——换个复验方可能判不通过。
- 🔴 铁律：写复验卡时**逐组标注**它是「**必须逐条落地为独立用例**」还是
  「**可由等价证据（X + Y）兜底**」。留白 = 把裁量权丢给下游。
- 自查句：*这一组，是"必须落地"还是"可等价替代"？卡面写了吗？*

## ⚠️ 对我的特别提示

**我持「全库可读写」权限——能改 vault 里任何文件、能改任何 skill。**

权限越大，这条规则越关键：

- 「我能改」≠「我该改」
- 看到 `.md` 里的错别字/过时表述，如果用户没让改 → **报告，不动手**
- 看到脚本有 bug → **报告根因，不自己修**（尤其 code-news 里的脚本，改动必须过测试，且那是别人的主责）
- 看到产线失败 → **报告卡在哪、根因是什么**，等用户点名专用会话去修

## 落地做法

### 发现问题时，输出什么

合格的问题报告应包含：

| 项 | 内容 |
|---|---|
| 现象 | 什么坏了，具体表现 |
| 位置 | 文件路径 + 行号（精确到可复核） |
| 证据 | 原始报错 / 日志片段 / 实测命令与输出 |
| 根因判断 | 你认为的原因（**标明是判断，不是已证实**） |
| 影响面 | 坏了什么、还牵连什么 |
| 建议 | 建议怎么修、建议由谁修（**不自己动手**） |

### 什么时候可以直接改

只有两种情况：
1. 用户**当场**说「改」「修」「确认修复」
2. 正在**开发一个新资产**（skill / 脚本 / 工作流），且该资产**尚未交付验证**

### 判断句式自检

动手前问自己：
- 用户明确让我改这个了吗？→ 没有 → **停手，改报告**
- 这是新资产的开发过程吗？→ 不是 → **停手，改报告**
- 我在"顺手"改吗？→ **"顺手"就是危险信号**
