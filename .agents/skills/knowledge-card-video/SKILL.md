## 一、先做这个判断（比调参数重要一个数量级）

**这是「信息片」还是「氛围片」？**

| | 信息片 | 氛围片 |
|---|---|---|
| 典型 | 工具测评、干货口播、知识科普、产品参数 | 品牌形象、汽车广告、情绪短片 |
| 观众要 | 「是什么 / 多少钱 / 能干嘛 / 坑在哪」 | 「感觉」 |
| **走哪条线** | ✅ **卡片线**（`build_card_video.py`） | AI 空镜线（`compose_long_video.py`） |

🔴 **实测教训**：把信息片当氛围片做 → 三条短板同时出现且**微调救不回来**：
语速慢（4.46 vs 6.62 音节/秒）、信息点只覆盖 47%、**8 张画面有效信息图 0 张**。

**判据**：信息片的内容**必须被看见**（数字、专有名词、对比），不能只靠旁白说。

### 第 2 步 · 写 script.json

```json
{
  "series": "AI 工具速评", "episode": "SERIES 001", "breadcrumb": "dsh 插件",
  "voice": "yunjian",
  "lines": ["第一句口播。", "第二句口播。"],
  "cards": [
    {"title": "一个插件\n免费用上前沿模型", "kicker": "dsh 插件 / 01",
     "big": ["¥0", "免 Key"], "subtitle": "官方称不限量，实际看服务器负载",
     "from": 1, "to": 3},
    {"title": "能用哪些模型", "kicker": "模型 / 02",
     "blocks": [{"label": "CHAT", "text": "DeepSeek V4.1 Flash"}],
     "from": 4, "to": 4}
  ]
}
```

**字段说明**
- `lines` = 口播稿（**顺序即配音顺序**）；`cards[].from/to` = **1-based 行号区间，含两端**，
  必须**恰好覆盖所有 lines**（缺一行那张卡的时长就错）
- `title` 可用 `\n` 换行；`kicker` 是小标签；`subtitle` 是说明行
- `blocks: [{label, text}]` 列表式；`big: [A, B]` 大字对比式（渲染成 **`A → B`**）

### 第 3 步 · 🔴 四个硬约束（不知道就崩 / 就废）

| # | 约束 | 后果 |
|---|---|---|

| 3 | 🔴 **`big` 每项 ≤3 字**（**2 字才稳**；此前记的「≤4 字」是错的） | 超了**折行 + 溢出卡片** → ✅ **已被校验器拦** |
| 4 | **必须系统 Python**（`edge_tts` 不在产线 venv） | `ModuleNotFoundError` |

#### 🔴 约束 3 的几何依据（2026-10-06 实测修正，别再用「≤4 字」）

```css
.bignum { font-size:132px; font-weight:900; }   /* build_card_deck.py 的 BIG_SIZE_DEFAULT */
.row    { display:flex; align-items:center; gap:34px; }
```
卡片内容宽 = 画幅宽 − `card_inset` 左右 = 竖屏 1080 − 144 = **936px**（横屏 1296px）
一行宽 = 2×N×132 + 34（箭头）

| 每项字数 N | 竖屏一行宽 | 判定 |
|---|---|---|
| 2 | 562px | ✅ 稳 |
| **3** | **826px** | ⚠️ 可放，余量仅 110px（且只对纯中文成立，含拉丁字符更宽） |
| **4** | **1090px** | ❌ **超 936px → 必然折行 + 溢出卡片边缘** |

实测症状（两版成片都有，一直没人放大看过）：
```
实际渲染「个人装 → 生产慎用」：
  个人        生产慎
  装          用        ← 折行，左项还溢出了卡片左边缘
```

**引擎侧已加自适应**：`big_font_size(big, avail_px)` 按最长项算安全字号
（4 字→108px、5→86、6→72…，等于默认值 132 时不写 inline style 以保历史输出不变）。
**但校验器仍按 error 拦 >3 字** —— 因为「勉强放得下」会付代价：**字号被压小，「大字」就不大了**。
所以文案侧仍应压到 **2 字**，完整语义移到 `subtitle`（22px 一行可容约 42 字）。

**出片前自检**（10 秒，能省一次白跑）：

### 第 5 步 · 时长重排两遍法（把「每镜时长」做到合规）

**问题**：卡片时长 = 该镜分到的**口播行区间**长度，而每句话的实测时长不可控 →
第一遍出片必然有几镜过短（<2.5s）或过长（>4.5s）。

**两遍法**（第二轮**不用重跑 TTS**，只改分组 + 重渲染）：

1. 第一遍出片，从 `<out>/cards.json` 读每镜实测 `duration`
2. **合并过短镜、拆开过长镜**——改的是 `storyboard.json` 的 `scene.from/to`，**不动 `lines`**
3. 重跑硬校验 → 重建（`--skip-tts` 复用配音）→ 重渲染

```bash
# 重建时复用已有配音：先把 <旧out>/voice 整个拷到 <新out>/voice
"$VH" build_card_video.py --script sb3/script.json --out card11b \
  --format vertical --skip-tts --skip-render      # 只重算分组与 index.html
```

🔴 **前提：`lines` 一字不改**（改了配音就对不上）。校验：`json.load(旧)['lines'] == json.load(新)['lines']`

**实测收益**（2026-10-06，11 镜 / 32s）：
| | 改前 | 改后 |
|---|---|---|
| 逐镜时长 | 3.19/**1.76**/2.43/2.53/3.34/2.81/**5.79**/2.54/2.76/2.66/2.19 | 3.19/**4.19**/2.53/3.34/2.81/2.46/3.33/2.54/2.76/2.66/2.19 |
| 合规镜（2.5–4.5s） | 7/11 | **9/11** |
| 时长标准差 | 1.05 | **0.56** |

**合并过短镜的做法**：把两类信息单元合进一张卡（如「门槛 + 前提」）→ 用 `units:[{type:"list",items:[…4 项]}]`。
⚠️ 不要用 `blocks` 堆 4 项——渲染器 `.blocks` 的样式只分到 `n3`，第 4 项没有专门样式，有溢出风险；
`units.list` 支持 **2–8 项**且有专门 stagger，合并镜优先用它。

## 三、语速：六档实测校准表（2026-10-06 复测，**推翻了标称值**）

### 3.1 🔴 先说口径（不说清就会报出互相打架的数字）

| 口径 | 定义 | 用途 |
|---|---|---|
| **A 纯说话** | 发音音节 ÷ **旁白净时长**（去掉段间停顿） | 判断「听起来快不快」 |
| **B 含停顿** | 发音音节 ÷ **成片总时长** | ✅ **倒推时长一律用这个** |

🔴 **踩过的坑**：同一个片子我用三种分母报过 6.26 / 6.62 / 6.98 三个「语速」——
**报语速必须同时报口径。以后统一口径 B。**

### 3.2 校准表（定稿 12 句 / 203 发音音节 / 232 `len()`，**走完整链含 `normalize_pauses`**）

| 档位 | 成片时长 | **音节/秒（口径 B）** | 口径 A |
|---|---|---|---|
| `+16%`（list） | 35.44s | 5.73 | 6.36 |
| `+24%` | 33.35s | 6.09 | 6.79 |
| **`+28%`（talk·默认）** | **32.42s** | **6.26** | 6.98 |
| `+32%` | 31.50s | 6.44 | 7.19 |
| `+40%` | 29.88s | 6.79 | 7.60 |
| `+48%` | 28.39s | 7.15 | 8.02 |

🔴 **`build_card_video.py` 文件头标的「+28% → 6.07 字/秒」与实际不符**（口径不同）。
**以本表为准。推荐档位 `+28%`**（与卡片线自带对标样本 365 字/60.5s ≈ 6.03 `len()`/秒 基本一致）。

### 3.3 🔴 提速收益是**次线性**的（重要）

档位 `+16%` → `+48%`（增量 **3 倍**），音节率只从 5.73 → 7.15（**+25%**）。
**根因**：段间停顿 `0.16s × (n−1)` 是**固定的**，不随语速缩放。
→ **想缩短总时长，减句数 / 减 gap 比提速有效**（11 段 × 0.16s = 1.76s，占成片 5.4%）。

### 3.4 倒推公式（**按定稿文稿倒推时长**）

```
成片秒数 ≈ 发音音节数 ÷ R(档位)
R = {+16%:5.73, +24%:6.09, +28%:6.26, +32%:6.44, +40%:6.79, +48%:7.15}
发音音节数 = Σ len(每句) − 标点数
```

**反向查表**：

| 目标时长 | `+28%` 需 | `+40%` 需 |
|---|---|---|
| 30s | 188 音节 / ~215 字 | 204 / ~233 |
| 40s | 250 / ~286 | 272 / ~311 |
| 60s | 376 / ~430 | 407 / ~466 |

🔴 **不要固定死时长** —— 先定稿，再按本表倒推；或反过来按目标时长定稿字数。

### 3.5 ⚠️ 两条限制

1. **`voice_segmenter.py` 单独跑出的时长 ≠ 成片时长**（差约 21%）。
   实测：单独跑 `+28%` = 41.05s，成片 = **32.42s** —— 因为 `build_card_video.py` 里有一道
   **`normalize_pauses` 重建段间停顿**。
   → **量语速必须走完整链**（`--skip-render` 即可），不能单独调配音器。
2. **音色自然度脚本判定不了**：`+40%` 以上 edge-tts 的机械感会明显 → **必须人工听一次**。

## 四·补、🔴 质量门随机失败的真因：gsap 是联网依赖（本技能最大的坑）

### 症状（极具误导性）

```
⚠ composition_file_too_large: This HTML composition file has 342 lines.
⚠ timeline_track_too_dense: Track 1 has 11 timed elements in this HTML file.
⚠ timeline_track_too_dense: Track 2 has 22 timed elements in this HTML file.
⚠ nested_structure_needs_subcomposition: <div id="stage-bg"> ... <div id="card0"> ...
[fail] 质量门未通过 —— 成片已生成但不合格，见上方明细
```

⚠️ **上面这些 warning 全都不是 fail 原因。** 我据此把镜数从 11 降到 6「规避」，是**误判**。

### 三条判据（读懂就不会被误导）

| # | 判据 | 出处 |
|---|---|---|
| 1 | `ok = errorCount === 0 && (!strict \|\| warningCount === 0)` | `hyperframes/dist/cli.js:171066` |
| 2 | `strict: false`（默认）→ **warning 永不导致 fail** | 同上 `:171263` |
| 3 | `MAX_COMPOSITION_LINES=300`、`MAX_TIMED_ELEMENTS_PER_TRACK=3` 都是 **warning 阈值**，不是硬卡 | `:88936-88937` |

→ **看到「一堆 ⚠ + fail」时，真正的 error 一定在别处**（Runtime / Layout / Motion / Contrast 段）。

### 真因

```
runtime: error  request_failed  Failed to load npm/gsap@3.14.2/dist/gsap.min.js:
                                net::ERR_CERT_COMMON_NAME_INVALID
runtime: error  page_error      gsap is not defined
```

链条：
1. `build_card_deck.py:834` 把 gsap **硬编码为 CDN 外链** `https://cdn.jsdelivr.net/...`
2. `hyperframes check` 起 headless Chrome 加载 `index.html`
3. Chrome **读 Windows 系统代理**（本机 `ProxyEnable=1` → `127.0.0.1:7897` Clash）
4. Clash 对该域名的证书 CN 不匹配 → 浏览器 `ERR_CERT_COMMON_NAME_INVALID`
5. gsap 未定义 → 动效脚本全抛错 → **2 个 error** → fail

🔴 **为什么极难自诊**：`build_card_video.py:222-223` 的 `run_check()` 只打印
`startswith(("✗","⚠"))` 的行并**截前 900 字符** —— runtime 段排在 lint 的几十条 warning 之后，
**被整段截掉**，报错信息里根本看不到真因。

### 修法（**2026-10-06 起已内置进脚本，不用再手工补**）

`build_card_deck.py` 新增 `ensure_gsap(project)`：本地副本存在且 ≥20KB 就直接返回本地路径

### 诊断手法（通用，值得记）

想看真正的 error，**绕开被截断的人类可读输出，直接取 JSON**：

```bash

"$NODE" "$HF" check "<项目目录>" --json > check.json 2>&1
```

🔴 **解析必须用 `json.JSONDecoder().raw_decode()`，两头都会被污染**：
- 前部：stdout 有 `[INFO] ...` 日志行 → 不能直接 `json.loads`；
- 尾部：**stderr 也有 `[INFO] ...` 行**，而调用方通常把 stdout+stderr 拼起来 → JSON 后面接日志
  → `json.loads` 抛 **`Extra data`**。

```python
rep, _ = json.JSONDecoder().raw_decode(out[out.find("{"):])   # 只吃一个完整 JSON 值
```

🔴 **间歇性失败必须连跑 ≥3 次**（本坑 2/3 失败，跑一次可能恰好通过而误判「已修好」）。

## 六、给镜头配真实素材（截图）—— **机制已落地，2026-10-06 实测通过**

### 6.1 🔴 先记住这条公式：截图能不能用，由它决定

**此前完全没意识到，是本节最重要的一条。**

```
成片里的字高 = 页面正文字号 × (shot 槽位宽 ÷ 裁切区的 CSS 宽)
```

🔴 **分母是「裁切区的 CSS 宽」，不是抓图窗口的整页宽** —— 这条 2026-10-06 才纠正过来。
**裁得越窄，放大倍数越高**：同一个页面，只裁一小块比裁一大块清楚得多。

以 GitHub 正文字号 16 CSS px、竖屏 `shot` 槽位宽 900px 为例：

| 抓图窗口 | 裁切区 CSS 宽 | 缩放比 | 16px 正文落到成片 | 判定 |
|---|---|---|---|---|
| 1440 | 1440（不裁） | 0.625 | **10.0 px** | ❌ **白放**（成片最小的字是字幕 46px） |
| 520 | 520（整栏不裁） | 1.731 | **27.7 px** | ⚠️ 到门槛 |
| 1400 | **260**（裁星标区） | 3.462 | **55.4 px** | ✅ 清楚 |
| 1400 | **230**（再裁紧一点） | 3.913 | **62.6 px** | ✅ 本轮实测值 |

**推论**：让字变大有两路 —— ① 抓窄窗口 ② **裁窄区域**。
**② 更划算**，且是第一选择：不必为了字大去迁就窄布局，可以直接从桌面宽图里裁一小块。
（旧的「必须用 ≤520 CSS 窄窗口抓」那条经验，是②还没被想到时的替代方案，已被本条取代。）

**经验门槛**：落进成片的字 **≥ 28px** 才值得放（对照：成片列表正文 34px、字幕 46px）。
低于此值不算「看不清」，但等于**没起到作用**，不如不做。

### 6.2 抓图：窄窗口 + 超采样（**唯一正确姿势**）

窄窗口直接抓会糊，所以要用 `--force-device-scale-factor` 超采样：

```bash
CH="C:/Program Files/Google/Chrome/Application/chrome.exe"
"$CH" --headless=new --disable-gpu --hide-scrollbars --no-sandbox \
      --force-device-scale-factor=2 \
      --virtual-time-budget=20000 \
      --window-size=520,3400 \
      --screenshot="D:/abs/path/_raw.png" "https://github.com/<owner>/<repo>"
```

得到 1040×6800（= 520 CSS × 2），裁完再缩到 900 宽 → 等效 1.73 倍放大且不糊。

⚠️ **`--screenshot` 必须给绝对路径** —— Chrome 的 cwd 与 bash 的 cwd 不同，相对路径会写丢
（报 `N bytes written` 但文件不在预期位置）。
⚠️ `--window-size=520` 触发的是 **GitHub 移动端布局**（汉堡菜单、单列）——**不是 bug，正是我们要的**：
窄布局让正文按窄栏排版，字形相对页面更宽，放大后更清楚。
⚠️ `--virtual-time-budget` 给足（≥18000ms），GitHub 是 SPA，给少了会抓到骨架屏。

#### 🔴 抓图是不稳定的：同一 URL 两次结果可能相反

实测同一命令连抓两次：**一次抓到未渲染完的空白页、一次正常**。

两个理由，缺一不可：
1. **实时数据会变**（星标这类数字每次抓都在涨）→ 重抓等于换了数据源
2. **很可能再中一次失败页** → 两次失败叠在一起，就分不清是「自己裁错了」还是「页面没渲染」

### 6.3 精确定位裁剪区：靠页面自身的视觉特征，不靠目测

以 GitHub 为例（这套手法通用：**先找页面里天然的「尺子」**）：

1. **引用块的左侧竖条**是天然的纵向边界。先采样一行拿到色值（实测 `#d1d9e0`），
   再沿该列统计命中率 >0.7 的连续段 → 得到引用块精确范围（实测 phys 3004–3627）
2. **文本行切分**：灰度 <150 的像素按行求和，间隔 >2px 即断行 → 拿到每行物理 y 区间
   （中文引言 3 行 = phys 3014–3139）
3. **换算**：`成片坐标 = 物理 y × (900 ÷ 抓图物理宽)`

一次裁准，不用反复试。⚠️ 别用「画刻度线拿眼看」的办法 —— 精度不够，会反复返工。

裁图（推荐用 PIL，比 ffmpeg crop 好调）：

```python

c = im.crop((0, y0, 1040, y1))
```

### 6.5 怎么配（分镜侧只需写 `assets`）

分镜表 `scenes[].assets` 支持三种写法：

```json
"assets": ["assets/shot/r1_intro.png"]
"assets": [{"src": "assets/shot/r1_intro.png", "label": "README 原文"}]
"assets": [{"src": "assets/shot/star_btn.png",
            "label": "GitHub 页面",
            "stamp": "截至 2026-10-06 23:35"}]
```

- 路径**相对 storyboard.json 所在目录**写（校验器按此基准查文件）
- 转换器会自动 rebase 成「相对 script.json 输出目录」，下游按此解析 → **两边基准不会错位**
- `label` 渲染成标签条**左侧**（带三个圆点，仿窗口标题栏）→ 建议写来源，如「README 原文」
- `stamp` 渲染成标签条**右侧**（右对齐）→ 🔴 **数据截图必写**，见 §6.9
- 引擎**只渲染第 1 张**（`SHOT_KEEP=1`），配多了会告警

**硬校验（不过不出片）**：
- `src` 必填
- **文件必须存在**（🔴 **error 不是 warning**）——渲染端就是一句 `<img src>`，
  指向不存在的文件**不报错，只留一块空白**（典型静默失效），写错路径直到人肉看片才发现
- 扩展名白名单（png/jpg/jpeg/webp/gif/avif）
- `stamp` 非字符串 / 空串 → **error**；没写「截至」→ **warn**（见 §6.9 的理由）
- 未支持的键（如自己加 `h`/`pos`）会**告警**，因为会被静默丢弃

### 6.9 🔴 给数据截图标「截止时间」（`stamp`）

**用户 2026-10-06 提出的方案**，一句话：

> 「我们在说他多少星标的时候，图片中就给出截止时间。」

**为什么它成立**：截图里的数字是**实时值**，口播数字是**原文快照**，两者同屏 →
观众无法判断哪个对。但一旦标上「截至 2026-10-06 23:35」，观众看到的就是
**「某时刻的快照」**，而不是「一个不知道哪来的数字」→ 矛盾消解。

这是**内容策略**，不是技术修补 —— 值得记住这个思路本身。

**🔴 时间戳由引擎渲染，不要烙进 PNG**（三条理由）：
1. **字体/字号跟视频一致** —— 烙进 PNG 只能用系统字体（msyh），跟卡片字体打架
2. **数据驱动** —— 改时间只需改 json，不用重新抓图（重抓还可能中失败页，见 §6.2）
3. 在**最终分辨率**上渲染，比先烙后缩放更锐利

引擎侧实现：`.shot .sbar .sstamp`（等宽字体 / `margin-left:auto` 右对齐 / 13px），
与左侧 `label` 同处一条标签条，正好一头一尾。

**🔴 必须写成「截至 XXXX-XX-XX HH:MM」**（校验器会 warn 提醒）：
只写「2026-10-06」是**歧义**的 —— 是抓图时间？数据时间？还是发布日？
加上「截至」才自解释：**这份数据是那一刻的快照**。

### 6.10 🔴 抓图会静默写出空白图（本轮踩到的真实事故）

**现象**：素材图 `star_btn.png` 打开一看是「上黑下白」一条，什么都没有 ——
而脚本**一声不吭地写出去了**，一路进片，直到抽帧人眼看才发现。

**根因**：`capture_shot.py` 原本只查「文件存在 + >1024 字节」，
而 Chrome 抓到的**失败页有 28 KB**，轻松通过；**裁切产物更是完全没校验**。
典型静默失效：`<img src>` 指向坏图不报错，只留一块空白。

**判据（实测标定，别拍脑袋）** —— 缩到 160px 宽后统计**灰度唯一值个数 `uniq`**：

| 样本 | `uniq` |
|---|---|
| 正常裁切区（星标按钮） | **161–180** ✅ |
| **失败产物** | **5** ❌ |
| 合成纯白 / 纯蓝 / 纯灰 | 1 ❌ |

→ 阈值取 **`uniq < 20`**，距正常样本 8 倍余量。

🔴 **别用灰度动态范围（`p98-p2`）当判据**：那张坏图是「上黑下白」两段，
动态范围高达 **255**，反而全样本最高 —— **判据选错比没有判据更糟**。

**修法**：`assert_has_content()` 插在**缩放后、打戳前**，`uniq < 20` 直接拒绝写出（退出码 3）。

⚠️ 位置很关键：**打戳前**。`draw_stamp()` 自己会加文字和色条，把 `uniq` 抬上去 ——
检查放在它后面，等于对着「已经化过妆」的产物说合格。

⚠️ **这个闸门拦不住「有内容但内容不对」**：裁到页面灰底（`uniq=71`）照样放行。
空白/未渲染拦住了，**裁错位置**没拦住 —— 那个仍靠人眼兜。别以为加了闸门就万事大吉。

## 八、🔴 音频听感诊断与配乐接线（2026-10-13 新增）

用户报「这一段声音连接有问题 / 断断续续」时，**先按 8.1 的顺序查，别一上来就改文案**。

### 8.1 五查对照表（前四项查「有没有」，第五项查「全不全」）

| # | 检查 | 手法 | 判据 |
|---|---|---|---|
| 1 | 文字对不对 | whisper 逐词转写 | 转写文本 vs 母版 `lines`，逐字比 |
| 2 | 声画同不同步 | SRT 时间轴 vs 转写时间戳 | 应吻合；不吻合是字幕问题不是音频问题 |
| 3 | 有没有爆音 | 样本级一阶差分 `abs(diff)` | 无 >0.9 的跳变 |
| 4 | **有没有死停** | 20ms RMS 包络 + 静音段检测 | **≥0.45s 的绝对静音即缺陷**（正常逗号 0.2–0.3s、句号 0.4–0.5s） |
| 5 | **BGM 有没有混进去** | `ls <out>/voice/voice_mix.wav` | **文件不存在 = 整片无配乐** |

> 2026-10-13 实例：用户报视频号 35–39s「连接有问题」。1–4 全过（文字对、声画同步、无爆音、
> 停顿量级正常），只有第 5 项不过 → 根因是**没配乐**。

### 8.2 🔴 最隐蔽的根因：`voice_mix.wav` 不存在 = 整片无配乐

`build_card_video.py` 里 `BGM_DEFAULT = "off"`、`SFX_DEFAULT = "off"`
（注释明写「off=不加，存量基准逐字节不变」）。
**任何编排层不显式传 `--bgm` / `--sfx`，成片就是裸人声。**

裸人声会把 `qwen3-tts-flash` **自身**的 0.2–0.5s 短语停顿**全部暴露**；
在 1.2x 以上语速（矩阵 rate 普遍 +16%~+28%）下，听感就是「声音断开 / 连接有问题」。

**因果链**：`atempo` 提速 → 语音变快 → 停顿相对变长 → 无 BGM 垫底 → 听感断裂。
→ **判据先行**：先 `ls <out>/voice/voice_mix.wav`。没有它，**先别怀疑 TTS 模型**。

修复后 BGM 会在停顿处垫底（实测混音 0.017–0.057 vs 纯人声 0.0005），
`sidechaincompress` ducking 正常工作（说话时压低、停顿处露出）。

### 8.3 🔴「矩阵写了、适配器没接线」是同型缺陷（一天踩两次）

`D:/AI-VIDEO/config/平台适配矩阵.json` 是参数单一事实源，**六个平台每个都写了**
`engine / rate / bgm / sfx`。但 `adapt_for_platforms.py` 组 `build_card_video.py` 命令行时，
**只传了作者当时想到的那几个字段**：

| 日期 | 漏传 | 后果 |
|---|---|---|
| 2026-10-13 | `--tts-engine` | 恒用默认 `fish`（已不可达）→ **六平台全部渲染失败** |
| 2026-10-13 | `--bgm` / `--sfx` | 恒用 `off` → **六平台全部无配乐**，听感断裂 |

**纪律**：矩阵新增字段后，必须在适配器的 `cmd` 里同步出现；
改完**用 `--dry-run` 打印命令逐字段核对**（`--dry-run` 只出 script.json 不渲染，秒回）。

### 8.5 修法优先级（2026-10-13 实测）

1. **先接 BGM/音效**（主因）——一步到位，且不用改文案、不用重写分镜
2. **再考虑改文案**（次因）——把句中句号去掉、让长句一口气连诵，只能小幅改善

> 反例：一开始以为「句号造成 0.5s 死停」，A/B 实验发现**去掉句号后新句的停顿量级与原句相当**
> （都是模型自身的短语停顿），说明改文案解决不了根本问题。**先做 A/B，再决定改哪一层。**

### 8.6 复验口径（改完必须重跑）

对**每个平台**的成片：`≥0.45s 死停条数` 应归 **0**；峰值 <0.98（不削波）；
时长与画幅与矩阵一致。2026-10-13 修复后实测：六平台死停 **0/0/0/0/0/0**，峰值 0.31–0.40。

**已知遗留（非缺陷）**：混音整体比纯人声低约 2.9 dB（`mix_audio` 的增益设计）。
嫌小声调 `--bgm-gain`（默认 −8 dB），别去改人声链路。

### 8.7 ⚠️ 环境坑：safe-delete 配额闸会杀掉 TTS 子进程

`voice_segmenter.py` 内部要删 `seg_*.mp3.raw` 临时文件。沙箱的删除闸按「本轮累计」计数，
**到 50 个就抛 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]`**，
`voice_segmenter` 子进程被中途杀死 → 该平台渲染 `退出码 1`。

**不是产线缺陷**。规避：**六平台分批跑**（先 3 个、再 3 个），或换轮次重跑。
2026-10-13 连续两次撞到，都是「前 3 个成功、后 3 个失败」这个形状。

### 8.8 🔴 用户交付规约（2026-10-13 用户明确要求）

**凡生成的作品（视频 / 封面 / 图文 / 脚本 / 报告），都必须在对话框用 `present_files` 贴出来**
让用户点击查阅，**不能只报路径**。落盘目录照样保留，方便后续批量取用。

### 8.9 🔴🔴 音效必须压过配乐 —— 「定音效目标时忘了 BGM 的存在」

这是 8.2 修完之后的**第二个坑，错法完全不同**，必须单独记：

一次修正把音效目标定成「旁白 −10 LU」，而 **BGM 目标是「旁白 −8 LU」** →
**音效比背景音乐还轻 2 LU**。分离渲染实测（视频号）：

| 层 | 整合响度 | 真峰值 |
|---|---|---|
| 纯音效层 | −25.79 LUFS | **−11.53 dBTP** |
| 纯 BGM 层 | −23.02 LUFS | **−9.12 dBTP** |

→ 音效在**响度与峰值上双双低于**音乐，被整个盖住。用户听出来「音效不明显」。

**雪上加霜**：音效有 `SFX_LEAD = 0.12s` 提前量，那 0.12s 里 BGM **还没被 ducking 压下去**
（ducking attack 20ms 要等旁白出现才启动），恰好把音效的**起音**盖掉 —— 而起音是瞬态里最要紧的部分。

**定稿修法（双约束取更响者）**：
1. **真峰值锚定**：音效真峰值 = 旁白真峰值 + `SFX_PEAK_REL_DB`（默认 −5dB）。
   转场音效是**瞬态**，峰值才是有意义的锚点；整合响度对 0.1–0.5s 的音效不适用
   （`ui_click_01.wav` 仅 0.15s，EBU R128 门控测出 `-inf`，会算出 +inf 增益炸掉混音）。
2. **不得低于 BGM**：音效响度 ≥ BGM 目标 + `SFX_OVER_BGM_LU`（默认 4 LU）。

实测结果：六平台音效峰高出 BGM **16.5–20.6 dB**。

**自查句**：*我这条音频层的目标值，是相对谁定的？还有别的层在同一频段抢位置吗？*

### 8.10 🔴 判据要"对得上物理量"—— 同一条判据返工三次的教训

| 版本 | 判据 | 错在哪 |
|---|---|---|
| 一版 | 触发窗能量 vs 全片人声峰 | 窗内**本来有人声**，音效删掉照样过 → **无区分度** |
| 二版 | 音效层 40ms 包络峰 vs BGM 层 40ms 包络峰 | **对瞬态不公平**：0.47s 的 whoosh 包络峰远低于采样峰，音乐是持续音 → 真峰值已高于音乐电平，仍被判"被盖住" |
| 三版（定稿） | **真峰值 vs 整合响度**（ffmpeg `loudnorm` 直接量） | ✅ 区分度验证：旧值 +1.8dB 判不过 / 新值 +17.5dB 通过 / 压到 −30dB 判不过 |

**纪律**：判据两边必须是**同一物理量**（峰对峰、响度对响度），
或**明确说明为什么可以跨量比**（这里：瞬态能否穿透持续床，看的正是「峰 vs 床电平」）。
用自己手搓的包络去比，很容易把「瞬态 vs 持续」比成不公平的对比。

### 8.11 🚀 只重混音、不重渲染（省掉整轮渲染）

音效/BGM 增益**只影响音频层**，画面逐帧不变。所以改音频参数时**不要重渲染**：

```bash
# 1) 用新参数重跑混音，产出新的 voice_mix.wav（几秒）
# 2) 替换 mp4 音轨，视频轨 -c:v copy 逐字节复制
ffmpeg -v error -y -i final.mp4 -i voice_mix.wav \
       -map 0:v:0 -map 1:a:0 -c:v copy -c:a aac -b:a 192k -shortest out.mp4
```

- 收益：几秒完成（重渲染要十几分钟），**且绕开 safe-delete 配额闸**（见 §8.7）
- 前提：**音频总长不变**（改增益不改时长；改文案/语速会变长，那才需要重渲染）
- 复核：重封装后比对视频流时长与音频流时长（±0.05s，见验收表 S3）
