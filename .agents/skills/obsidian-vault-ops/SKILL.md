### 🔴 同一批资料写多份时，**文件名必须互不重名**（2026-09-16 踩到）

Obsidian 的 `[[双链]]` 按 **basename** 解析。同一批作业若产出「决策 + 复盘 + SOP + 运行小结」，
很容易起出两个同名文件（实例：决策 `2026-09-16-<主题>.md` 与运行小结 `2026-09-16-<主题>.md`）
→ **`[[2026-09-16-<主题>]]` 变成歧义链接，指向哪一个由 Obsidian 自行决定**，且**不报错**。

**做法**：
- **不同目录的同类命名要带语义后缀** —— 运行小结那份写成 `YYYY-MM-DD-<主题>-运行小结.md`，
  让**决策占裸名**（被引用最多的是决策）。
- **同一批作业内部自检**：把全库 `.md` 的 basename 建索引，**出现 ≥2 次即报歧义**（见 §十·校验）。
- 改名了就**必须同步引用**（改名必跑引用同步，见 §八/§十）。

### 讲「双链」这个概念时，别在正文里裸写双方括号

`[[双链]]` 这种**字面量会被 Obsidian 当成真链接**，于是校验时报断链、库里多一个红链。
写法：用反引号包裹（`` `[[双链]]` `` 也仍会被部分校验器提取 —— 所以**最稳是改写措辞**，
如「双链语法（双方括号）」）。

### 定期做「登记 = 事实」一致性扫描（2026-09-15 实例固化）

**为什么**：索引类登记会**悄悄落后于事实**，而**落后的索引比没有索引更糟**。
实例：`AGENTS.md` 强制要求「开发任何新 Skill / MCP / 工作流 / cron 脚本前，**必须先查阅** `工作流/` 对应领域篇」，
但它的表把 **5 篇已存在**的规范标成「**待补充 / 待建**」（实际 07-20、09-06 就建好了）→
会让人和 Agent **直接跳过已写好的文档**，甚至重复开发。

**做法（三步）**：

1. **扫标记**：搜 `待补充 / 待建 / 待创建 / TODO / FIXME / 待回填 / 尚未` 等词
2. **扫计数**：搜「自有 N 个 / N 条接线 / 共 N 个 / N 个实体」这类**会被事实推翻**的数量登记
3. **逐个核实事实**：对每一个标记，去**实测**它说的东西到底存不存在（`Test-Path` / `ls` / 读 frontmatter），
   **不要相信标记本身** —— 标记就是那个可能过时的东西

> **排除历史产物**：`raw/`、`内容生产/`、`知识库/`、`参考库/`、`AI日报/` 下出现"待办/共N个"是**当时的内容**，
> 不是需要更正的登记，别去动。

**改的时候**：顺手加一条「**完整清单以 <权威索引> 为准**」的指回（如 `[[index|工作流索引]]`）——
否则同一份清单会**再落后一遍**。

**三条边界（踩过的）**：

- `check_doc_references.py` **只校验路径类引用，不校验 skill 名引用** → **`MISSING 0` ≠ 引用都对**，
  skill 名要人工判。
- 判「某 skill 不存在」前，先搞清该生态的**目录结构**：**Hermes 侧是分层的**
  （`~/.hermes/skills/<分类>/<name>/`，如 `productivity/skill-dev-research/`），
  **WorkBuddy / codex 侧是平铺的**（`~/.workbuddy-ai/skills/<name>/`）。
  曾只查平铺目录就断言 `skill-dev-research` 不存在 → 误判。
- **`.env` 里放密钥是正常的**，别当"明文泄漏"报；要查的是**散落在配置 JSON 里的明文**
  （如本机 `settings.json` 的 `claw.*.channels`）。

**改正「登记落后」时的自守规矩**：先备份 → 改完跑校验 → **断言「旧表述已清除」必须限定结构位置**
（如表格单元格 `| _(待补充：X)_ |`），**不能用裸子串** —— 因为更正说明里会**故意引用旧表述**。

**扫到「待建 / 引用了不存在的路径」时，先判「该建还是该改」—— 别急着照字面新建**：
**先看同类东西在生态里的既有约定**。实例：`skill-design.md` 引用 `工作流/templates/skill-template.md`（标「待建」），
而 `工作流/` 及其上游 `经验沉淀/` 的既有约定是 **`_模板-` 前缀 + 平铺**
（`决策/_模板-决策.md`、`复盘/_模板-复盘.md`、`工作流/_模板-工作流.md` **三处都在**），
且 `工作流/index.md` 的 dataview 已按 `!contains(file.name, "_模板")` 排除模板
→ 落为 **`工作流/_模板-skill.md`**（**零改动即生效**），**而非照字面新建 `templates/` 目录**
（那会造成**两套约定并存**，正是「重叠」问题的成因）。
> 通则：**归属问题先查约定，再决定建还是改**。「照文档字面补文件」经常是把一处偏差变成两套标准。

### 🪞 改了某篇正文，别忘了它在「索引表 / 目录页」里被一句话描述着（2026-09-16 踩到）

**实例（同日两处，都不是断链，是「摘要落后于正文」）**：

| 文件 | 落后点 |
|---|---|
| `系统中枢\经验沉淀\工作流\index.md` | 人工兜底表里该行写着「含硬规则 **6~9**」，而正文当日刚补到**硬规则 10** |
| `系统中枢\经验沉淀\工作流\vault-health-check.md` 的 frontmatter | `来源复盘` 字段只列了 1 篇，当日新写的复盘没补进去 |

**为什么容易漏**：`dataview` 那一半（条目列表）**会自动跟着变**，人工那一半（**一句话摘要 / 覆盖范围 / 数量区间**）不会 ——
于是同一页里「自动的半边是新的、人工的半边是旧的」，**看起来还挺整齐**，不核不出来。

**做法**：改某篇正文的「**结构 / 数量 / 覆盖范围**」后，除正文本身，还要扫三处：

1. 同目录 `index.md` 的**人工兜底表** —— 该行的简介、括号里的说明、「含硬规则 N~M」这类**区间**；
2. 该篇自己的 frontmatter 字段 —— `来源复盘` / `来源决策` / `关联总结` / `最后更新`；
3. 其它文档引用它时写的「**一句话定义**」。

> **通则**：**摘要与正文分居两处时，改一处必漏另一处。** 与本节「登记 = 事实」同族 ——
> 只是这里的"登记"是**对某一篇的摘要**（而不是条目清单），所以上面那三步扫描（扫标记 / 扫计数）也扫不到它。

### 🔴 删除文件/目录，前后也必须跑引用校验（2026-09-15 实测踩到）

**既有铁律只写了「改名必跑引用同步」—— 实测「删除」同样会打断引用，而且更隐蔽**（改名至少目标还在，删除是直接没了）。

**实例**：清理回收区 `_cleanup-quarantine\config-backups-20260818\` 后例行跑校验 → **MISSING 1**：
`系统中枢/规则与权限/智能体共享/03-工具与调用.md:114` 引用的正是刚删掉的那个目录。

**做法（删除类作业标准动作）**：

1. **删前**：在 vault 里搜这些**路径片段 / 文件名**有没有被引用
2. **删后**：**立刻跑**引用校验（`cd ~/Documents/code-news && python scripts/check_doc_references.py`）
3. **修引用**：把指向已删目标的路径改成「**历史记录**」表述 ——
   ⚠️ **改写后的路径不要再放进反引号**，否则校验器照样把它当硬引用提取 → **仍报 MISSING**；
   改用自然语言 + **相对片段**（如「原备份目录 `config-backups-20260818`」）即可落进 SKIP 类

### 🗂️ 归档清单必须按「目录实际内容」重建，不能只写本批次（2026-09-16 踩到）

**实例**：清理 `内容工位/_脚本/` 临时脚本，归档到 `_脚本-已清理备份-20260916/`。
事后再看目录：**57 个被清理文件**（`03:20` 批 48 个 + `03:21` 批 9 个），
但 `_manifest.json` 的 `count` 只有 **9** —— 第二批的脚本**只写了自己的 9 条**，覆盖了第一批的记录。
一度怀疑「文件丢了」，实为**记录被覆盖**；逐条比 sha256 后确认 **9/9 一致、文件本体无损**。

**根因**：把 manifest 当成了「**本次运行的日志**」，而它实际是「**归档区的事实记录**」。
多个批次共用一个归档目录时，**每批只写本批次 → 后写覆盖先写**。

**做法（二选一）**：

| 方案 | 要点 |
|---|---|
| ① 按批次分目录 | `_脚本-已清理备份-20260916-01/`、`-02/` …… 各批各写各的清单，天然不覆盖 |
| ② 清单从目录重建 ★推荐 | 归档完**枚举归档目录实际内容**逐个算 sha256，而不是只 append 本批次；旧清单留档为 `_manifest-部分清单-<批次>.json` |

**自证（跑完必做）**：`归档目录实际文件数 == 清单 count + 清单/脚本自身数`。
本次对账：`57 + 4(两份 manifest + 执行脚本 + 原部分清单) = 61` ✓。

> ⚠️ **推论（并入 §十 同族）**：输出里的**计数与目录实际不符**时，
> 先别怀疑丢数据，先怀疑**记录的覆盖面** —— 「不是文件少了，是清单没写全」。
> 与「报错全量覆盖时先怀疑判据」是同一族的**口径问题**。

### 🔄 决策记录 §结果 的「事后回填」（2026-09-16 立）

决策模板（`决策/_模板-决策.md`）的 `## 结果` 段留的是 `（事后回填：实际效果 / 是否回滚）` 这类**占位**。
凡决策已执行一段时间的，**该段必须按实测回填** —— 否则决策史只剩「当时的承诺」，没有「后来的结果」。

**四条要点**：

1. **先实测取证，再动笔** —— 每条回填都要有可指认的证据（计数 / 文件 mtime 分布 / sha / 脚本输出）。
   **禁止写「效果良好、运行稳定」这类无证据套话**（那和占位没区别）。
2. **主动找「与当时预期的偏差」** —— 决策当时若写了「残余风险 / 触发条件」，回填时要明确回答「它发生了吗」；
   **发现登记与实际不符时如实写「偏差」，不粉饰**。实例（2026-09-16）：某决策写「保留关闭 3 个插件」，
   实测 `enabledPlugins` 里其中一个**一直是启用态** → 如实记录，并注明「已于同日只更正登记、不擅自关闭」。
3. **核验不了的，就写「无法核验」** —— 不要用推测填空。要写明**阻塞原因**（如本机安全策略阻断某工具）
   与**补核方式**（谁能、怎么补），把这一项标成本轮唯一未完成项。
4. **写回工艺与改正文同规格**：备份 → **锚点唯一性断言**（`count == 1`）→ **按该文件自身行尾写回**
   → **反向重构逐字节 == 原文**。

> **别混淆两种「结果」**：① 决策**当时**的 `## 执行清单`（「我做了什么」）；② **事后**回填的 `## 结果`
> （「做了之后怎样了」）。前者是计划回执，后者是效果验证 —— **两段都要在**。
>
> **替换占位时留个指示**：占位文本改为 `**回填（<日期>）**` 这类**指向性标题**，避免读者误以为「还没回填」。
>
> **回填里提到别的文档时写全路径**（带路径双链或路径），别只写裸名 —— 否则又制造同名歧义（见 §十·补）。

### 坑在哪

写入工具插入的行，**行尾可能与被编辑文件不一致** → 文件变成**行尾混用**。
本次实测：`工作流/index.md` 在我动它之前就已是混用（LF=54 / CRLF=46，历史遗留）。

### 🔴 第 5 类根因：`Edit` 会把 MIXED 文件静默归一为纯 LF（2026-10-01 三组探针坐实）

**结论**：`Edit` 对行尾的处置分两档 ——

| 编辑前状态 | 编辑后 | 说明 |
|---|---|---|
| **纯 CRLF** | **保持 CRLF** | 未触碰行与新增行都维持 CRLF |
| **纯 LF** | **保持 LF** | 同上（本 skill 自身即属此类） |
| **MIXED（CRLF 少数）** | **归一为纯 LF** | 哪怕只改一行、且该行不在 CRLF 处 |
| **MIXED（CRLF 多数）** | **归一为纯 LF** | **即便 CRLF 占多数，仍归 LF** —— 最反直觉的一条 |

**三组探针原始记录**（探针目录 `D:\Obsidian Vault\备份\_tooling-probe-20261001`，跑完即删）：

| 探针 | 编辑前 | 编辑后 |
|---|---|---|
| 纯 CRLF 文件 | CRLF=3 / LF=3 | **CRLF=3 / LF=3（保持）** |
| LF 多数 MIXED | CRLF=1 / LF=3 | **CRLF=0 / LF=3（归一为 LF）** |
| CRLF 多数 MIXED | CRLF=2 / LF=3 | **CRLF=0 / LF=3（仍归一为 LF）** |

> 表中 `LF` 计数 = 换行符总数（`\r\n` 也含一个 `\n`），故「CRLF=1 / LF=3」= 3 行里有 1 行 CRLF、2 行 LF。

> ⚠️ **这条改写了旧认知**。旧版曾以为「`Edit` 会保留未触碰行的 CRLF」。本轮 `00-简版操作说明.md`（编辑前 CRLF=1 / LF=191）编辑后变成纯 LF，遂做三组探针证伪。
> **真实机制**：`Edit` 只保证「**纯行尾文件**保持原样」；只要文件处于 **MIXED** 状态，它就**无条件按 LF 重写整个文件**（与改动位置无关）。

**对策（MIXED 文件的正确改法）**：

1. 改前先读字节，判定是否 MIXED（`crlf > 0 and crlf < nl`）。
2. 若 MIXED 且**该文件本应保持 CRLF**（如 `log.md`、`模型配置母本.md`）→ **不要用 `Edit`**，改走「Python 读字节 → 二进制替换 → 断言内容不变 → 按 CRLF 写回」。
3. 若 MIXED 且本应 LF（治理区绝大多数）→ `Edit` 的归一**恰好是我们要的方向**，可放心用，但收尾仍须复读字节确认。
4. **新建文件**不适用本条（无「原约定」可言），按 §八·补「同目录多数」定基准。

### 检出与归一（写完必做）

```python
raw = p.read_bytes()
nl, crlf = raw.count(b"\n"), raw.count(b"\r\n")
lone_cr  = raw.count(b"\r") - crlf
if crlf == nl and nl > 0 and lone_cr == 0:   target = "CRLF"   # log.md 这类
elif crlf == 0 and lone_cr == 0:             target = "LF"     # 手写治理区主流
else:                                        target = None     # ← 混用，需归一
if target is None or (target == "LF" and crlf) or (target == "CRLF" and crlf != nl):
    lf = raw.replace(b"\r\n", b"\n").replace(b"\r", b"\n")
    fixed = lf if target == "LF" else lf.replace(b"\n", b"\r\n")
    assert fixed.replace(b"\r\n", b"\n") == lf     # 自证：只动行尾、内容一字不动
    p.write_bytes(fixed)
```

**归一方向 = 该文件原本的约定**。⚠️ 新建文件按「同目录多数」定基准，但**目录内可能不统一**（`智能体共享/` 里 00~05 是 LF、`模型配置母本.md` 是 CRLF）→ **改既有文件一律以该文件自身的行尾为基准，不以目录为基准**。
`log.md` 追加必须**二进制写入 + `\r\n`**，不要用文本模式（会混进 LF）。

### 🔴 判定行尾**绝对不要用 `grep`**（本次踩到，代价是改错 7 个文件）

`grep -c $'\r' <file>` 在 Git Bash 下**对纯 LF 文件也返回「全部行含 CR」** —— 完全不可用。
我据此误判「vault 是 CRLF」，把 6 个 LF 文件全改成了 CRLF，随后靠备份才发现方向反了。

> **规矩**：行尾判定**只认 Python 读字节**（`raw.count(b"\n")` vs `raw.count(b"\r\n")`）。
> 改行尾前，先拿**未碰过的同类文件**和**备份**双向核对基准，别凭一次抽样就下结论。

> 同一轮里对**同一个文件**发了**两处**修改，两条并行提交 → **后写覆盖先写**，
> 工具两条都回「成功」，实际只落下一处。凡「同文件多处改动」一律**串行提交**；
> 收尾时用脚本**重新从磁盘读取**校验关键字符串是否真的在位（本次正是靠这一步发现静默丢失）。
>
> ⚠️ **锚点断言失败时，第一步是「打印真实字节」，不是「改文件」**（2026-09-16 第 2 次踩到断言）：
> 写 `assert 锚点 in raw` 之前，先 `print(repr(目标行))` 核对磁盘上的**真实字节**。
> 本轮实例 —— 断言 `### 七、⚠️ 未完成（需用户裁定）` 失败，实际磁盘上 `⚠️`（`U+26A0` + `U+FE0F` 变体选择符）
> 与「未」之间**多一个半角空格 0x20**，而 **Read 工具渲染时这个空格看不出来**。
> 同类隐形字符：变体选择符（`U+FE0F`）、零宽空格（`U+200B`）、不换行空格（`U+00A0`）、全角/半角空格混用、行尾 CR。
> **判据**：断言报「找不到」时，先用 `repr()` 比对锚点与磁盘字节的**逐字节差异**；
> 确认是锚点写错 → 改**锚点字面量**（不是改目标文件）；确认文件真被改动 → 才走备份/回滚。
> 顺带：**整文件重写优于多处串行 Edit 的场合** —— 当同一文件要改 ≥3 处时，改为「读全文 → 改 → 整体写回 + 断言」更稳，天然避开「后写覆盖先写」。
>
> 🔴 **「写入工具回执成功」≠「文件里是你要的字节」—— 用 `.py` 辅助脚本写长篇中文，会把源脚本的行尾透传进去**（2026-09-16 第 3 次踩到行尾）：
> 先把一大段正文塞进 `.py` 的**三引号字符串**（用 Write 生成该 `.py`），再 `python x.py` 去追加/写入目标文件 →
> **源脚本文件自身的行尾会原样进入字符串字面量**，于是目标文件被写成交织的 `\n` + `\r\n`（MIXED）。
> 本轮实例：给 memory 日志追加 4593 B 正文，**引入 42 处 CRLF**，而该文件基准是**纯 LF**（此前一直是纯 LF 才被误以为"安全"）。
> **判据**：凡「用脚本往文本文件里写多行内容」，**写完立刻按字节复判行尾**，并**打印首个 CRLF 的 offset**
> —— 若首个 CRLF 的 offset **正好等于「写入前的文件长度」**，则 100% 是本轮引入，**不是**文件原有。
> **修法**：按该 offset 切成前缀/后缀 → **断言前缀无 CRLF** → 只对后缀做 `\r\n`→`\n` → 回写 → 复判「CRLF=0 且 LF 数不变」。
> **预防**：宁可先用 `Write` 产出 `.md`，再程序化读取并追加，**也不要把大段正文塞进 `.py` 字符串字面量**。
> **一句话**：行尾纪律不只管「改一个 .md 时别改错它的行尾」，也管**「你用来改它的那件工具自己带什么行尾」**。
> 🔴 **用 `python -c "…"` 往文件追加中文正文 —— shell 会先把反引号当命令替换、`$` 当变量展开**（2026-10-02 第 5 类「工具对字节动了手」，与第 3/4 类同族）：
> 本轮实例：`python -c "…"` 里写「反引号 `--levels AB` 反引号」，bash 把反引号内整段当**命令执行**并替换为**空**
> （终端报 `--levels AB: command not found`）→ **文件确实写成功了，但所有反引号包裹的内容全部消失**，
> 而脚本仍打印「追加完成」、退出码 0，**回执完全不报错**。
> **判据**：凡用 `python -c` / `bash -c` 携带**含反引号或 `$` 的正文**，写完必须**回读复检关键串**（`grep` 或 `in`），不能只看脚本自报成功。
> **预防（唯一正解）**：正文一律**先用 `Write` 产出 `.md` 片段文件**，再用**极短的** `python` 只做「读片段 → 追加 → 按字节复判」——
> 正文一个字都不进 shell 引号。这是上一条「宁可先用 `Write` 产出 `.md`」的**强化版**。
> 🔴 **`Write` 工具会把源码里的行尾转义序列「规范化」—— 字节字面量锚点会静默失配**（2026-09-16 第 4 类根因，与第 3 类同属「工具对字节动了手」）：
> 用 `Write` 生成 `.py` 时，若在里面写 `old = b"...\r\n..."` 这类**含转义序列的字节字面量**，工具会把 `\r\n` 规范化掉，
> 于是脚本里的锚点**与磁盘上文件的实际字节对不上** → `raw.count(old)` 得 **0**；
> 而**在 shell 里用同一串字符验证却通过**（shell 侧没被规范化）→ 极易误判成「文件被改了」。
> 本轮实例：给 `auto_ingest.py` 打补丁时，shell 侧 `count==1` 通过，脚本内 `assert raw.count(old) == 1` 报 **0 次**，白排查两轮。
> **判据**：**凡锚点含 CR/LF，绝不在源码里写转义序列**；报「找不到」时先怀疑**你写锚点的方式**，而不是文件被改。
> **对策（唯一正解）**：CR/LF 一律**运行时构造** —— `CRLF = bytes([13, 10])`，再 `CRLF.join(...)` / `a + CRLF + b` 拼锚点；
> 或直接 `raw.split(CRLF)` 按行处理，**永不在字面量里写 `\r` / `\n` 转义**。
> **一句话**：第 3 类是「工具的行尾**流进了目标文件**」，第 4 类是「工具把**你写的行尾转义改了**」——
> 两头都指向同一条元纪律：**「你用来改它的那件工具，自己带什么行尾、会不会改写行尾」必须先行确认**。

> 这条**当即成为新的断链引用**，会把验收数字从「MISSING −2」污染成「−1」（自己把自己刚修好的账又弄脏）。
> **被谁挡住**：改完后的**「全文双链计数必须回落到改动前原值」**这一步复核（计数 30，而改动前原值应为 29）→ 定位到新节。
> 同一坑本轮**触发两次**：治理方案那处**已写入**→靠事后复算发现；母本条目那处→被写入**前**的「块内不得含字面双链」断言挡住。
> 对策：① **文档内引用双链一律脱去方括号**，写成描述形式（如「长路径双链（原指向 `…`）」）；
> ② **写前断言 + 写后复算，两道都要有** —— 断言防新增，复算防漏网。）
> （**第 12 次（正则写死形态类）**：用 `^## 结果$` 扫「结果段」→ **漏掉带序号的章节标题**（`## 八、结果`），
> 一度把 6 篇判为「结果段极短」、2 篇判为「无结果段」；改用 `^##\s*(.+)$` 取全部标题后按关键词筛选 →
> **16 篇全部有结果段**，真实缺口是**占位文本**（`（事后回填：…）`）而非「没有结果段」。
> **规律**：凡「找某一节 / 某一行」的扫描，**只按语义关键词筛，不按标题的精确字符串** —— 标题会带序号、会被改名。）
> （**第 13 次（自证漏洞类）**：用**同一个通用「替换」函数**处理多个 job 时，**忘了区分「锚点要保留」与
> 「锚点要被消耗」** —— 本次两个 job 本意是「在锚点**之后**插入」，代码却写成「**替换**锚点」，
> 于是 `技能变更日志.md` 的**表头分隔行**、母本 `## 五、变更记录` 的**章节标题**被直接吃掉
> （Markdown 表格与章节结构双双损坏，属**次生破坏**）。
> **为什么没被当场发现**：当时的自证写成 `after.replace(nb, ob) == raw`（**可逆性**检验）—— 逆向替换当然能还原，
> **它根本不检查「锚点是否还在」**。
> **对策**：① 每个 job **显式声明**「保留锚点」还是「消耗锚点」；② **插入类必加断言** `after.count(ob) >= 1`、
> **替换类必加断言** `after.count(ob) == 0`；③ **元纪律：「反向重构通过」只证明「可逆」，不证明「语义正确」** ——
> 两件事，都要断言。**改完必须逐 job 复读磁盘**，逐个确认锚点与结构仍在。）

## 十·补、同名双链歧义的完整审计法（2026-09-16 立）

**一句话：同名 ≠ 歧义。只有「裸 basename + 引用方同目录无同名 + 全库同名 ≥2」才是真歧义。**

### 三连判据（缺一即产生假失败）

| 序 | 判据 | 处理 |
|---|---|---|
| 1 | 双链目标**含 `/`** | 带路径 → Obsidian 明确解析 → **跳过** |
| 2 | 裸 basename，且**引用方同目录存在同名文件** | 同目录优先 → **跳过** |
| 3 | 裸 basename + 同目录无 + **全库同名 ≥2** | **★真歧义，这才是要处理的** |

### 处置流程（五步）

1. **全库 basename 建索引** → 列同名组，并**逐组比对内容哈希**：
   - **逐字节相同** = 重复副本（真问题，多半是自动化写回）
   - **内容不同** = 分类体系下的同名主题页（知识库/参考库常见，**多为设计使然，勿擅动**）
2. **对"被引用的"同名组跑三连判据** → 得到真歧义清单。
3. **定唯一权威位**（本例依据：`运行小结/index.md` 早已声明「历史复盘用 dataview 查看」→ 权威位是 `经验沉淀/复盘/`）。
4. **备份 → 哈希比对 → 原子移出**（`os.replace`；vault 与备份同卷时为原子操作）。
5. **追写回源**：查有没有 cron / 脚本会把它写回来 → **不堵住写回源，次日必复发**（`★只清不堵 = 表演`）。

### 移出后必做

- 全库引用校验：确认**本次删除造成断链 = 0**（关键判据是「被删 basename 在全库还剩几份 + 引用是否写作被删除的路径」）。
- 对每个 MISSING **定性**，别直接当断链（四类**全是假失败**）：
  **模板占位**（含 `YYYY-MM-DD` / `序号` / `<id>`）、
  **历史路径描述**（旧目录结构，basename 现存别处）、
  **已删文件的叙述**（如"某文件已删除" / 删除登记里记录的旧路径）、
  **带行号 / 字段后缀**（`xxx.py:56`、`file.md#小节` —— 校验器把 `:56` 当路径的一部分 → 文件其实存在，
  只是后缀没剥；**这是校验器自身的判据缺口，不是死链**）。
- 顺手扫**自己刚写的说明文字**有没有裸写双方括号（本轮又踩一次：`[[<X>]]` 包了反引号照样被提取）。

#### 🔴 生成器把「LLM 自由文本」写成双链时，必须先校验存在性（2026-09-16 端到端验证挖出）

**背景**：选题池生成器把 LLM 返回的 `materials[]` 直接拼成双链。实测（改后产物）
**20/20 条格式正确带路径，但 18/18 条反解落空** —— 格式改造完全生效，可解析性反而归零。

**排查路径（可复用）**：

1. **先对照改前产物** —— 改前是裸名（`[[题材名]]`），改后是带路径。确认改造**格式生效**。
2. **别急着定成退化** —— 拿**历史多期产物**跑基线，命中率一目了然：
   `09-02~09-11 与 09-13 = 100% 命中真实归属目录`，`09-12 / 14 / 15 / 16 = 0%`。
3. **用 A/B 两组数字锁定漂移** —— 同一批素材名分别查「真实归属目录」与「另一套名字来源」：

   | 日期 | 素材数 | 命中真实归属（题材卡） | 命中另一套（证据链标题） |
   |---|---|---|---|
   | 09-09 | 17 | **17** | 0 |
   | 09-15 | 30 | 0 | **28** |
   | 09-16 | 20 | 0 | **19** |

   → 结论：**LLM 从 09-12 起发生目标漂移**，不再按 prompt 输出目录名，改为照抄 prompt 里给的示例文本。
4. **回到 prompt 找自相矛盾** —— `SYSTEM_PROMPT` 写「素材：从素材示例中引用…**写题材名即可**」，
   而 `build_planner_prompt` 喂进去的「素材示例」是 `sample_titles`（**文章标题**）。
   **要求写 A、示例给 B** → LLM 只能照抄 B。**这是 prompt 与数据结构不一致，不是模型"不听话"。**

**纪律**：

- 写入双链前必须**校验目标是否存在**；落空时**降级为纯文本引用**，宁可不给链接，也不制造断链。
- 凡「要求 LLM 输出可解析标识（文件名/路径/ID）」时，**必须把可选值列表显式列进 prompt**，
  且**示例字段要与要求回填的字段同源** —— 示例给什么，LLM 就抄什么。
- 判断「新改动是否引入退化」时，**改前改后两期对比不够** —— 必须拉长时间线看基线，否则会把**既有漂移**误判成**新引入**。

1. **谁写的？** —— 找脚本/常量（本例 `sync_error_postmortems.py:8` `DST = HANDOFF`，而 `vault_paths.py` 已定义

3. **有没有互斥指令？** —— 本例两个 Hermes 技能一个要"复制到 `运行小结/错误复盘/`"、一个要"该目录保持空"，
   叠加之后**两边都没达成**。

### 同判据「前后对比」的虚拟构造法（2026-09-16 立）

**问题**：本轮 F3 合并（22 文件并入 + 25 文件移出）跑完后，复扫得到「真歧义 53 组 / 1159 次」——
与基线**一致**，看起来是好事；但**基线是用内联的、和现在不同的判据跑出来的**，`①带路径 1887 / ②同目录 164 / MISSING 1631`
与基线的 `1878 / 38 / 22` **根本不可比**。此时若直接宣布「没变化」，是**拿两把尺子量同一个东西**。

**做法**：写一个脚本，用**同一套判据**扫两遍 ——

| 遍 | 数据来源 |
|---|---|
| **改动后** | 真实磁盘（直接 walk vault） |
| **改动前** | **脚本虚拟构造**（vault 零改动）：① **跳过**本次新增的文件（白名单来自改动前快照）② 从**归档区/备份区**读被移出的文件，按**原相对路径**虚拟还原 ③ 被修改过的文件改用**备份里的旧版内容** |

两侧跑同一套 `scan()`，输出同一组判据 → **数字严格可比**，能精确说出「净效果 = 什么」。

**本轮实测产出（可作范例）**：

| 判据 | 改动前（虚拟） | 改动后（真实） | 差 |
|---|---|---|---|
| .md 总数 | 4227 | 4224 | −3（+22 −25）|
| 同名 basename 组 | 364 | 364 | ±0 |
| ★ 真歧义 | 53 组 / 1159 次 | 53 组 / 1159 次 | **±0（零恶化）** |
| MISSING | 1633 | 1631 | **−2（修好 2 条断链）** |

**关键收益**：把「同名组 ±0」这种**看起来没变、实际内部发生了一增一减**的结果解释清楚 ——
本例是 `2026-09-06-垂类热力报告` 撞名组消失（−1）＋ 改名产生的 `2026-09-06-0900-热榜TOP20`（+1）→ 净零。
**不做虚拟对比，这个"内部一增一减"就永远看不见，也就无法判断改名这个动作是否值得。**

**脚本落点**：`C:\Users\Administrator\WorkBuddy AI\内容工位\_治理临时\g6_before_after.py`（可作下次模板）。

**三条注意**：
1. **虚拟还原必须用归档区/备份区的真实字节**，不要"照记忆重建"；
2. 改动前快照要在**动手之前**就落盘（本例 `snapshot_before_merge.json` = 改动前 A 目录逐文件清单）；
3. 被改文件（本例 3 个参考库 .md）要**用备份旧版内容**参与"改动前"这一遍，否则双链计数会不真实。
