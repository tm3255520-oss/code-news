# 写一份「借鉴优先型」开发方案

> 权威口径：`D:/Obsidian Vault/obsidian Vault/系统中枢/规则与权限/智能体共享/06-复用守则.md`
> **§十一**（外部工具调研必带「借鉴开发对照」A/B/C 三档）+ **§十二**（**借鉴优先**，优先级高于其余各节）。
> 本 skill 是它们的**可执行版**——即「按这两节写成一份方案」的标准动作。
> 实例：`系统中枢/经验沉淀/工作流/AiToEarn-评论抓取与回复链路源码分析.md` → `评论互动线-开发方案.md`；
> `多平台发布线-功能缺口分析与借鉴选型.md` → `多平台发布线自建通道-开发方案.md`。

## 〇、什么时候用 / 不用

**用**：用户让你「看完某个外部工具后，综合写一份新的开发方案」——即**方案的输入是别人的东西**。

**不用**：从零设计、无外部参照物的方案（那走常规三段流程即可）。

**硬前提（用户已多次强调）**：**方案只是方案**。用户说「不要动手，只是整理文件」时，
**不写代码、不装东西、不改配置、不建 cron**。产出物只有：方案 md + 索引同步 + 日志。

## 一、六步固定动作（**顺序不可乱**）

### 1️⃣ 先盘家底 —— **这一步最常被跳过，也最致命**

> 🔴 **真实教训（2026-10-12）**：用户让「借鉴 AiToEarn 写新方案」，
> 若直接按外部工具体系设计，会写出**一整条我们其实已经做好的链路**。
> 实际盘点发现：`~/.hermes/scripts/` 里**已有三个评论脚本**（采集 / 意向分类 / 回复草稿），
> **缺的只有最后一段「执行层」** → 方案从此从「从零设计」变成「补最后一段」，**写法完全不同**。

**动作**：
```bash
ls -la ~/.hermes/scripts/ | grep -iE "关键词"
ls -la ~/.hermes/scripts/*.py | sort -k9        # 全量，别只按名字猜
```
**判据**：每一个「以为要新建」的环节，都要先回答「**我们有没有**」。
**并用规模（行数/字节数）作证据**，别凭印象说「好像有」。

### 2️⃣ 核清外部工具的**许可实物与源码实物**（§十一 第 6 条）

**三步验真**（零成本）：

| 步 | 看什么 | 假开源特征 |
|---|---|---|
| ① | `language` / `size` | `language=None`、`size` 只有几 KB |
| ② | 仓库文件列表 | **只有 README**（纯引流） |
| ③ | 🔴 **源码树逐层展开到叶子** + 依赖里有没有「仓库外的私有包」 | 核心逻辑 `import` 到仓库外、且那些包不可公开获取 → open-core |

🔴 **「搜关键词」≠「看源码树」**。只跑 `rg "xxx" src/` 就下「没有源码」的结论是错的
（PostBot 曾被这样误判——实际 `src/media/publisher/platform/` 下有 37 个平台适配器）。

**许可判定**：必须**打开实物 `LICENSE` 文件**，不能只看 README 里的 license 字段或 GitHub 侧栏。
- `MIT / Apache-2.0` → 可商用可改
- `GPL` → 传染，慎用
- 自定义「评估许可 / 禁商用 / 需付费取源码」 → **一律 C 档**

### 3️⃣ 做「借鉴开发对照」——**A / B / C 三档**（§十一 必备章节）

**🔴 没有这一节的方案视为未完成。**

| 档 | 含义 | 判据（两条都要满足） | 落地要求 |
|---|---|---|---|
| **A 可直接照搬引用** | 许可证允许 **且 技术栈可对接** | 许可 OK + 栈通 | 注明来源仓库与许可；搬进产线后登记 `技能变更日志.md` |
| **B 需借鉴开发自行实现** | 许可 OK **但栈不通**（或只能看设计） | — | 写清「**借鉴什么设计 → 落到我们哪个文件**」；**不得抄代码** |
| **C 不可借 / 不建议借** | 法律或纪律上不能碰 | — | 写明**具体原因**，**别只写「不合适」** |

**判档的四个易错点**（都是踩过的）：

1. 🔴 **「语言无关的契约文本」可归 A 档**。接口定义、事件协议名、字段表、命名法
   ——这些不是代码，可**直接采纳**，即便上游是别的语言。
   （AiToEarn 是 TS，但它的 `IPlatformInteraction` 签名 / 7 段进度事件名 / `XxxByOther` 命名法
   被归 A 档照搬；而它的**算法实现**归 B 档。）
   → **表述纪律**：A 档写「照搬的是**契约/协议文本**，不是代码」。
2. **B 档借的是「判据」，不是「写法」**。可以沿用它的**结构**，但要**修掉它的缺陷**。
   （例：AiToEarn 的 `sleep(10s)` **无抖动** → 我们沿用「每条间隔」结构，但**加 ±30% jitter**。）
3. **C 档常见且必须写明的理由**：① **凭据须交第三方**（外包签名服务、要求上传设备私钥）
   ② 硬编码密钥/签名（必失效、来源不清）③ 栈不通且无设计价值 ④ 业务不相关 ⑤ **号称有、实测零实现**。
4. 🔴 **§十二 的反向应用：已有更优实现，不得「改差」**。
   §十二 第 3 条禁「重复开发」，**反过来也成立**——若我们的实现比外部干净，
   **不借**并在 C 档写明「我们更好」。（例：我们评论抓取走 DOM + bsk **不碰签名**；
   AiToEarn 走私有接口 + 签名 → **借它是倒退**。）

### 4️⃣ 技术路线决策 —— **用证据论证，不是罗列选项让用户选**

> 🔴 用户明确批评过：「**你让我这样去决策是不精准的**……你应该从技术这个角度分析清楚，给出结论」。

**写法**：给一张**对照表 + 明确结论 + 为什么**，并**与已有路线的关系要交代清楚**
（哪怕结论与另一条线相反——**说明场景不同，不是不一致**）。
**每一项技术可行性都要有「已有先例」或「实测输出」作证据**，不能是「应该可以」。

### 5️⃣ 三段工作流 + 可复核验收标准

- **三段**：计划 = workbuddy ／ 实施 = codex ／ 验证 = **claude（非实施方）**。
- **验收标准编号化**：M0（前置/探路，零风险）→ M1（核心闭环）→ M2（扩展）→ M3（台账回流）。
  **每条必须给「判定方法」**（命令 + 预期输出 + 退出码）。
- **M0 必备三条**：通道/环境健康、**探路项**、**回归门**（改之前先证明起点是好的）。
- 🔴 **探路项要如实标注「未实测」**，不能写成已确定。
  （例：抖音 DOM 能否稳定拿到 `cid` —— 列 M0 探路，**并写明拿不到时的降级方案**。）
- **fail-closed**：默认不产生副作用，必须显式开关才动手。

### 6️⃣ 落盘 + 两处同步索引 + 日志 + 校验

```
① 方案 → D:/Obsidian Vault/obsidian Vault/系统中枢/经验沉淀/工作流/<线名>-开发方案.md
② 同步 工作流/index.md 的【手工表】（dataview 块自动，但手工表必须手动加行！）
③ 追加工作日志 .workbuddy-ai/memory/<YYYY-MM-DD>.md（append-only，带 §编号）
④ python code-news/scripts/check_doc_references.py --quiet   → 期望 0 MISSING
```

- **行尾**：按目录惯例判（`经验沉淀/工作流/` 惯例 **LF**）。写完用
  `grep -c $'\r' <file>` 复核（期望 0）。
- ⚠️ `check_doc_references.py` **只扫固定「活文档」清单**（AGENTS.md / 共享认知 / 运行手册 /
  工具登记专区 / **索引页**），**不含 `经验沉淀/工作流/` 正文**。但 `index.md` **在清单内** →
  新增文档后**必须重跑**，否则断链不会暴露。

## 二、方案文档的骨架（照抄这个结构）

```
frontmatter: 类型: 方案 / 标题 / 日期 / 最后更新 / 状态: 待审批 / 来源: [[...]]
开场：本方案独立成文 + 上游依据 + 【审批流程：须经用户确认后方可实施】+ 口径依据(协作原则11 + 复用守则§十一§十二)

〇、开工前核对（属止血还是结构改造？哪个阶段？会不会改别的模块接口？出口条件写了吗？）
一、开发内容
   1.0 硬原则：借鉴优先（① 直接调用 ② 照搬引用 ③ 借鉴开发 三条落到本方案哪儿）
   1.1 家底盘点（已有 vs 缺口，每条给证据 + 规模）
   1.2 🔴 借鉴开发对照（A / B / C 三档）★ §十一 必备
   1.3 技术路线决策（对照表 + 结论 + 已有先例为证）
   1.4 架构图（标出「只新建哪一层」）
   1.5 不做的（划边界）
二、开发步骤（计划 / 实施 / 验证 三段，含执行方）
三、验收标准（M0 / M1 / M2 / M3，每条带判定方法）
四、审批流程图
五、风险与回滚
六、相关（上游 / 规则 / 资产路径）
七、待用户确认项（★ ≤3 项，一次确认）
```

## 三、与用户协作的纪律（**优先级高**）

1. 🔴 **确认项压到 ≤3 项，一次确认**。用户原话：「**你太多要确认的事项了**……
   你把全部任务拆成 5 次来完成，每一次都要我确认」。**别一次抛一堆**。
2. **方案里要把「需要用户拍板的」和「我自己判断的」分开**：
   凡我能从技术角度定结论的，**直接给结论 + 理由**，不要「A 还是 B 你来定」。
   只把**真改红线 / 真改业务边界**的事留给用户。
3. **若方案会改既有红线，必须显式标红并单独说明**。
   （例：现有脚本开头写着「不做自动发送」，而新方案要机器发送 → **标为唯一红线变更，必须明确批准**。）
4. **互斥纪律**：同一时间只开一条线。若已有另一条线在跑 → **在方案里写明互斥与优先级建议**
   （一般原则：**止血 > 增量**）。
5. **说人话**：路径要准、数字要有出处、**有问题直说别粉饰**。

## 四、反模式（明确禁止）

1. ❌ **不盘家底就设计** —— 写出整条已存在的链路（最致命）。
2. ❌ **只看 README 判开源** / 只跑关键词搜索就判「无源码」。
3. ❌ **把「借鉴产品设计」包装成「借鉴源码」**（闭源软件没有源码可借，要如实说并给可借的开源替代）。
4. ❌ **C 档只写「不合适」** —— 必须写具体原因（许可 / 凭据 / 必失效 / 不相关 / 实测无实现）。
5. ❌ **罗列选项让用户选技术** —— 要自己论证出结论。
6. ❌ **把未实测的事写成已确定** —— 一律列 M0 探路并写降级方案。
7. ❌ **写完方案就动手** —— 用户说「不要动手」时，只交付文档。
8. ❌ **漏同步 index.md 手工表** —— dataview 自动但手工表不会自动。
