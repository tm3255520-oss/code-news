# 判读规则：把数字翻译成制作结论

## 方向陷阱（最容易读错，先看这里）

**D 组"声画耦合"必须算「每个切点是否落在句首」，不能算「每句话是否都有切点」。**

反例：一条 53 秒视频里，旁白有 33 句、画面只有 15 个镜头。用后者算，覆盖率只有 36%，
会得出"画面先行"的错误结论——而真相恰恰相反，画面是严格按语音句首切的。

正确读法：

| 切点数 `cut_sample` | `cut_coverage` | 结论 |
|---|---|---|
| ≥ 8 | ≥ 0.6 且中位偏差 ≤ 0.6s | **配音先行**（`sample_confidence=high`） |
| ≥ 8 | 0.4–0.6 | 部分对齐（主要节点跟语音，细节自由） |
| ≥ 8 | < 0.4 | 画面先行（切点与语音无对应） |
| 5–7 | 任何值 | 给结论但标 **`low`（低置信）**，结论字符串里会写明"切点仅 n 个" |
| < 5 | 任何值 | **证据不足，不作制作顺序判断** |

`median_deviation_s` 越小越强。≤ 0.2s 说明是严格对齐，几乎可以断定用了自动化对齐或
分了非常细的镜头表。

> ⚠️ **样本量门槛（2026-09-16 加，2026-09-17 分级）**：`cut_coverage` 是"每个切点是否
> 落在句首"的比例，分母是切点数。实测一条卡片片只检出 4 个切点却算出 3/4=0.75，
> 落在"配音先行"区间——**看着达标、实则 4 个样本什么都说明不了**。
> 现分三级：<5 一律"证据不足"；5–7 给结论但标低置信（7 卡结构天然只有 6–7 个切点，
> 一味沉默会让整类片子无法作答）；≥8 正常。**读 JSON 先看 `sample_confidence`，再读结论。**

## A 技术指纹 → 形态

关键量是 `bits_per_pixel_per_frame`（bpp = 视频码率 ÷ fps ÷ 像素数）：

| bpp | 形态倾向 |
|---|---|
| < 0.02 | 图文动效 / 幻灯片（画面几乎静止） |
| 0.02–0.06 | 口播 / 录屏 / 图文混合（低动态） |
| > 0.06 | 实拍或高动态画面 |

配合 `static_shot_ratio`（**相机**静止占比）：≥ 0.6 说明多数镜头画面不动，强烈指向图文卡片。

> ⚠️ **已知度量缺陷（2026-09-16 实测发现）**：`static_shot_ratio` 测的是**相邻帧灰阶差异**，
> 因此它反映的是"**相机**是否静止"，不是"**内容**是否静止"。有运镜的片子（连续推拉平移）
> 会得到很低的数值，与 bpp 的判断**相互矛盾**。
> 实例：一条 1920×1080 文档型动效片 bpp 0.0182（判"图文动效"）但 static_shot_ratio 仅 0.19，
> 抽帧目视确认内容确为静态卡片、动的是相机。
> **处置**：两者冲突时**以 bpp 为准，并用抽帧目视定案**；报告里必须写出这个冲突，
> 不要只挑对自己有利的那个数字。

**注意**：bpp 低也可能来自"高压缩的实拍"，必须抽帧目视确认后才能下结论。

## B 场景/卡片节奏 → 剪辑密度

**先读 `video_class`，它决定用哪套口径：**

| 片型 | 判定 | 度量 | 实例（2026-09-17 三条留档样本） |
|---|---|---|---|
| 静态卡片型 | 帧间差均值 < 1.0 | 联合判据：幅度 ≥1.5 **且** 变化像素占比 ≥ 阈值 | 抖音 [7, 23]、视频号 [2, 9] |
| 动态素材型 | 帧间差均值 ≥ 1.0 | 自适应阈值法（原实现） | B站 53 镜 |

**卡片/场景数是"口径依赖量"，禁止只报一个数。** 同一素材在不同口径下可差 2–3 倍
（抖音那条：严口径"整体换屏"=7、宽口径"含只动中央文字"=23；真值 7 张卡）。
读法：

- `scene_count_range` = [严口径, 宽口径]。**引用时必须写明口径**，否则数字没有意义。
- 严口径（面积≥5%）= 整屏/整块更换，适合判断"换卡"；
- 宽口径（面积≥2%）= 含只动中央文字的换卡，也是 D 组的主口径（"跟着语音切"两种形态都算）。
- `event_detail` 每条带 `kind`（硬切=单帧完成 / 淡变=2–4 帧完成）、`peak`、`area_ratio`。

节奏阈值（仍有效，但引用时注意这是经验值）：

- `median_shot_s` 1.5–2.5s：短视频常规快节奏
- `median_shot_s` 3–4s：讲解型 / 清单型（一个信息点一个镜头）
- `median_shot_s` > 5s：口播长镜或沉浸型

> ⚠️ **度量演变记录（不要退回旧实现）**：最初用 HSV 直方图距离 + 自适应阈值，
> 在卡片片上失效（一条 7 卡视频只报 4 个切点，2 真 2 假、漏 5；另一条报 0）。
> 换成"幅度 + 变化面积"联合判据后，三条样本同时对上（严口径抖音 7 = 7 张卡、
> 宽口径视频号 9 = 9–11 卡、动态素材型 B站 53 镜）。**幅度单指标不够**——
> 元素进场与换卡的幅度是重叠的，必须加"变化面积"这一维。

## E 配音类型

| 信号 | 结论 |
|---|---|
| `pause_count_ge_0.25s` = 0 且 `dynamic_range_db` < 8 | 强推断 TTS：全程无换气，广播级压缩 |
| 停顿 1–2 次 | 倾向 TTS |
| 停顿 ≥ 3 次且有自然分布 | 倾向真人 |

**只能判停顿规律，判不了音色。** 报告里必须写"需人工听一次确认"。

## F 视觉规范

- `dark_pixel_ratio` > 0.5 → 暗色系；> 0.8 → 纯暗底模板
- `dominant_colors` 前两位若是近黑（如 #06/#18 系）且第三位是低饱和金褐（如 #B7A272），
  指向"黑金"商务模板——这是知识类/工具类内容的高频选择
- 强调色（占比 1–3% 的高饱和色）通常用于关键词高亮、警示数字、CTA

### F2 版式 / 字号 / 强调色（2026-09-17 新增，OCR 逐帧）

F 组只给"颜色占比"，F2 给"能直接抄的版式信息"。三个量：

**① 字号档 `type_tiers_px`**——文字块高度聚类（间隔 8px），等价于字号层级。
实测锚点：视频号 **97.9 / 53.6 / 29.6 px**（三档）、抖音 **103.4 / 71.0 / 18.8 px**。
对照 Work Buddy 独立得出的 97–106 / 54 / 30，两条路径吻合 → 可用作模板字号规范。

**② 纵向占用带 `y_bands` 与密集带 `y_dense_bands`**——5% 分箱的直方图。
⚠️ **不做槽位聚类**：实测各卡片版式不同（标签/大标题/批注位置各异），y 分布是准连续的，
全局"槽位"并不存在，硬聚会把 82 个块并成一簇（我第一版就是这么错的）。
读法：视频号集中在 **30–70%**（单栏居中片）；抖音在 **0–15%**（顶部装饰：系列名 + 页码）
与 **20–60%**（内容框）、**80–100%**（底部字幕条 + 页脚）三段分布。

**③ 居中率 `centered_ratio`**——只算内容区（y 20–80%）、按行判定（并排块算一行）：

| 取值 | 版式判断 |
|---|---|
| ≥ 0.85 | 居中单栏纵向堆叠（实测视频号 0.911） |
| 0.6–0.85 | 以居中为主，存在并排/分栏行 |
| < 0.6 | 多框/多栏版式（实测抖音 0.373：标题 + 并排框 + 底部字幕） |

**④ 强调色 `accent_color`**——高饱和像素（S>90 且 V>90）的中位色与占比：
| 占比 | 判读 |
|---|---|
| < 0.5% | 极简，几乎不用强调色 |
| 0.5–3% | 正常（对标区间：抖音 0.74%、视频号 1.07%） |
| > 3% | 偏高，颜色可能铺面积、失去强调作用 |

> ⚠️ **颜色"语义"（红=工具 / 绿=收益 / 紫=能力）不在脚本产出里**——那是判断不是测量。
> 脚本只给强调色清单与占比，语义映射由报告作者写，并标明属推断（铁律 1）。

**两种非卡片片子的读法（2026-09-17 实测）**：

| 情形 | 实测长相 | 怎么读 |
|---|---|---|
| 实拍/录屏为主（B站样本） | 只有 **1 个字号档**（34.6px）+ 密集带在 **5–10% 与 90–95%** | 那是账号水印 + 底部字幕条，**不是版式槽位** → 此片是"字幕型"，F2 只能告诉你字幕字号与位置 |
| 多框/多栏版式（抖音样本） | 居中率 < 0.6（0.373）+ 字号档 3 档 | 版式是"标题 + 并排框 + 底部字幕"，居中率低是真实特征而非噪声 |

> ⚠️ **强调色指标只对低饱和设计的卡片片有判读价值**：实拍/多色画面里"高饱和像素"遍地，
> 中位色会落到灰调（实测 B站 #6C7176、2.33%），此时该数字不代表"强调色"。

> 🔧 **OCR 依赖**：用 Windows 自带 OCR（`scripts/win_ocr.ps1`，WinRT）。
> 需 `Language.OCR~~~zh-CN` 语言包已安装（本机实测 Installed）；缺引擎时该组按
> `failed` 返回、不影响其余组。**必须用 Windows PowerShell 5.1 执行**（PS7 不支持
> `ContentType=WindowsRuntime` 投影），脚本因此刻意写成纯 ASCII（PS5.1 按 GBK 解码非 ASCII 注释会崩）。

## G 溯源

- `has_c2pa` = false 是常态，**不代表内容有问题**，只代表拿不到加密溯源链
- 出现 `Lavf*` 说明经过 FFmpeg 系转码。**平台交付件里这是平台服务端留下的**，
  不能据此反推创作者的工具链
- 想真正确定创作者工具：只能拿原始导出文件（看 `encoder` / `ilst` / XMP）

## H 响度/母带（2026-09-17 新增）

三个数：`integrated_lufs`（整体响度）、`true_peak_dbtp`（真峰值）、`lra_lu`（动态范围）。
参考基准：整体响度约 **-14 LUFS**、真峰值 **≤ -1.0 dBTP**。

| 判读 | 结论 |
|---|---|
| `true_peak_dbtp` > -1.0 | **越界，存在削波**——说明对方导出前没过限幅，我方不要照抄 |
| `integrated_lufs` 明显高于 -14（如 -9） | 比平台标准响 5 dB 左右，平台会压音量、听感变闷 |
| `lra_lu` < 3 | 广播级压缩，配合"停顿 0 次"可强化 TTS 判断 |

实测锚点（2026-09-17 三条样本，`measured_on` 标注为原视频音轨）：

| 样本 | I | TP | LRA | 判读 |
|---|---|---|---|---|
| 抖音 | -13.25 | -1.09 | 2.2 | 合规 |
| 视频号 | -13.33 | **+0.25** | 2.0 | 真峰值越界 |
| B站 | **-9.15** | **+1.77** | 1.3 | 又响又削波（最严重） |

> 注意两点：① 必须在**原视频**上测——先降到 16k 单声道 wav 再测，抖音那条会从
> -13.25 变成 -16.28 LUFS，差 3 dB；② 三条专业成片全部越线，说明这是行业普遍疏漏，
> 不是个例，"越界"要当成常见情况写进报告，而不是当成异常。

## 阈值出处（可追溯性）

本文件所有阈值都是**经验值 + 小样本实测**，尚未做过独立标定。写报告时若被追问依据，
按下面这张表回答，不要拔高可信度：

| 阈值 | 出处 | 样本量 |
|---|---|---|
| bpp < 0.02 / 0.02–0.06 / > 0.06 | 本技能 2026-09-16 实测（0.0052、0.0104）+ 早前记录 1 条（0.0182），三条均为图文动效并经抽帧目视确认 | n=3 |
| `static_shot_ratio` ≥ 0.6 | 同上两条样本（0.492、0.919）；注意该指标测的是**相机**静止，不是内容静止 | n=2 |
| `cut_coverage` 0.6 / 0.4 | 两条样本（0.958 强对齐、0.75 但切点不足）；阈值本身是经验分档，非标定结果 | n=2 |

| 切点 <8 不作结论 | 由"4 个切点算出 0.75"这次假阳性反推得出，是保守门槛而非统计推导 | n=1 反例 |
