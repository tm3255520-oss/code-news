# 新视频模型接入评估

> 适用：`D:\AI-VIDEO` 产线（本地 Wan2.2 TI2V-5B 为主力）。
> 首次落地：2026-10-06 第一轮评估 Agnes Video 2.5 **Flash**（免费档，出片成功）；
> 第二轮接入 Agnes Video 2.5 **完整版**（收费档）；
> **第三轮（方法论复核）**：推翻多条旧结论，新增「**seed 不保证可复现 → 跨档比画质不成立**」、
> 「**免费档实测成功率 8%**」、「**data: URI 免托管**」、「**用量差记账必须串行**」等关键纪律；
> **第四轮（第二轮复核 — 逐条重发请求、亲眼看响应体）**：又查出 2 处**更基础**的方法错误 ——
> ① 「**`/models` 不校验 token 内容（假 key 也返回 200）→ 根本不能用来判 key 有效性**」
>    （旧版表格里「假 key → 401」是**没实测就写的**，且与旧结论自相矛盾）；
> ② 「**沙箱代理与 Clash 是互补关系** —— 同一域名的可达性可以完全相反，
>    记连通性结论**必须同时记代理端口**」。
>
> **第五轮（定档实验）**：先找到「`seed` 锁不住画面」的出路，**又被自己的实测推翻一半** ——
> ① 「**`keyframe` 同图法**」能让三档 `t=0` 相同，但 **`t>0` 仍分叉**
>    → 🔴 **画质指标（sobel 边缘能量）会被"人物断裂伪影"虚高**：
>    实测 1080P 分数最高（71.68）**恰恰因为伞缺了一半、人物上下身错位**；
>    → **结论：`seed` 失效的平台上，跨档画质对比本质上不可靠，定档只能靠确定性事实**；
> ② 「**`agnes-video-v2.0` 实测免费 + 原生竖屏（704×1280）**，
>    但参数名与 2.5 完全不同（`ti2vid`/`resolution`/`ratio`），用错会**静默忽略**」；
> ③ 「**`-flash` 对已充值账户疑似不再免费**」（唯一成功那条被扣 $0.125）；
> ④ 「**客户端默认模型是免费档**（`MODEL = MODEL_FLASH`）→ 测付费档必须显式传 `model=`」。
>
> **第六轮（★ 首次走本地路线 — MiniMax H3，2026-10-07）**：
> 前五轮全是云端 API；本轮首次评估**本地 ComfyUI 模型**，发现**那套云端纪律一条都用不上**，
> 本地是另外四个坑（新增 §七·补·3）：
> ① **内存数据必须同环境重测** —— 同一条 Wan 基线，清场前后提交峰值差 **23.28GB**，
>    拿旧基线比会得出完全错误的"H3 更吃内存"结论；
> ② **判"内存够不够"看 commit charge，不是页面文件物理占用**（我曾写错字段名）；
> ③ **ComfyUI 的 `filename_prefix` 带 `/` 会被当 subfolder** → 输出路径多一层
>    （`h3bench/h3bench/`），污染全部历史 JSON；
> ④ **帧数约束必须查官方 blueprint，别照抄别的模型** —— H3 是 `n ≡ 5 (mod 17)`，
>    照抄 Wan 的 72 帧**不合法**。
> 🔴 **本轮最重要的一条判断纪律**：**"结构性能力"与"性能差异"必须分开看** ——
>    H3 慢 25.6% 是**性能差异**（会随优化缩小）；"一次出画面+声音"是**结构性能力**
>    （Wan 体系补不上）。**接不接取决于后者能不能省掉一整条链路，不是前者。**
>
> 🔴 **本技能的历史版本曾同时收录互相矛盾的结论**（代理是否被拦、哪档最划算、假 key 返回什么）。
> 这本身就是教训：**把一次观测写成硬事实会带偏后面所有判断。**
> 涉及「能不能通 / 哪档更好 / key 有没有效」的判断，**必须当场重测**，
> 并用 `--usage` 核验真实成本。
> 🔴 **自查法：证据与结论是否互相支撑** —— 旧版说「假 key → 401」却又说「200 不能证明 key 有效」，
> 两句不可能同时成立。**自相矛盾 = 至少有一句是凭印象写的。**

## 一、先问三个问题（顺序不能反）

1. **能不能用？** —— key 有效吗？接口通吗？（技术门槛）
2. **能不能用得起？** —— 免费是限时还是长期？限流多严？（成本门槛）
3. **能不能用着不出事？** —— 商用授权明确吗？（**法律门槛，最容易被跳过**）

> 🔴 **90% 的人只做第 1 步就下结论。** 但对自媒体（有收益 = 商用），
> **第 3 步不过关，前两步做得再漂亮也不能用于正式发布。**

> 💵 **第 2 问怎么展开？** 计费规则要按「通用核查清单」逐条问 —— 见
> 第五节「★ 计费核查：单价便宜 ≠ 真的便宜」。**别只抄单价表，要读计费公式。**
>
> 落地动作三条：
> ① 把单价表 + 公式 + 免费额度做成「速查卡」落产线 `config/`（例：`config\Agnes计费规则要点.md`）；
> ② 把**官方计费示例写成 `--selftest` 断言** —— 供应商悄悄改价/改公式会当场暴露；
> ③ 客户端内建 `--estimate`（只算钱不提交）与 `--max-cost-usd`（安全阀），
> 且**默认模型必须是免费档**（否则一次手滑就是真金白银）。

## 二、判断 key 是否有效：别踩「/models 陷阱」

### 🔴 陷阱：模型列表端点的鉴权常常形同虚设

实测（Agnes，2026-10-06 **二次复核**，逐条真发请求看过响应体）：

| 实验 | 请求 | 实测结果 |
|---|---|---|
| A | 不带 Authorization → `/v1/models` | **401** `Token not provided` |
| B | **乱写的假 key** → `/v1/models` | **200 + 完整模型列表** ← ★ **露馅** |
| C | 不带 key → `/dashboard/billing/usage` | **401** `Token not provided` |
| D | **假 key** → `/dashboard/billing/usage` | **401** `Invalid token` |
| E | 真 key → `/dashboard/billing/usage` | **200** `{"object":"list","total_usage":N}` |

→ 🔴 **`/models` 只校验「有没有传 token」，不校验「token 对不对」** ——
   连乱写的 key 都返回 200 和完整模型列表。**拿它判 key 有效性从根上失效。**
   （曾误记为「假 key → 401」，那是**没实测就写下的**；实测反了。
   若假 key 真返回 401，200 就**能**证明 key 有效，与原结论自相矛盾 —— 自查方法：看证据与结论是否互相支撑。）
→ ✅ **正确判据：换一个「真正需要授权」的端点**（用量/余额/账单都行）。
   Agnes 上就是 `/dashboard/billing/usage`，三态区分干净，
   **错误措辞本身就是判据**：

   | 措辞 | 含义 |
   |---|---|
   | `Token not provided` | **没读到 token**（查 key 有没有传出去、代理有没有吞 header） |
   | `Invalid token` | **读到了但不认**（key 真的无效） |
   | 200 + 数据 | **有效** |

   **措辞比状态码可靠** —— 因为 401 有两种完全不同的病因。

### 正确的探测手法（两步）

**第 1 步：GET 一个需要授权的端点 —— 判「key 有没有效」**

```bash
# Agnes 上是这个；别的平台找它自己的「用量/余额/账单/me」端点
curl -s -H "Authorization: Bearer $KEY" {base}/dashboard/billing/usage
# 200 {"total_usage":N} = 有效 ｜ 401 Invalid token = 无效 ｜ 401 Token not provided = 没传到
```

**第 2 步：POST 一个「规则上必定被拒、但不需要真正生成」的业务请求 —— 判「能不能访问这个模型」**

```
POST {base}/videos   body: {mode:"reference"}   # reference 模式不给素材 → 规则必然 400
```

判读：

| 返回 | 含义 |
|---|---|
| **400** | ✅ **鉴权通过** —— 服务端进入了参数校验阶段，说明 key 有效且有权 |
| **401 / 403** | ❌ key 无效或无权（**必须读正文**：403 也可能是余额不足） |
| 200 | ⚠️ 服务端没校验参数（少见），换别的方式探 |

好处：**两步都不消耗生成额度、不产生费用、共耗时 1–2 秒。**
第 1 步单独就能定「key 有效性」，第 2 步额外验证「这个 key 有权用这个模型」。

### 🔴 陷阱 2：鉴权通过 ≠ 能出片

**鉴权探测返回 400（通过）只证明 key 被识别，证明不了模型能出片。**
Agnes 实测：鉴权探测 ✅ 通过，但真实提交返回
`403 Failed to pre-consume quota, remaining $0.000074` → **余额只有 0.0074 美分**。

**验收标准（重要）**：接入一个付费模型，必须**跑到一次真实提交**（即使被拒），
看返回的是「参数错误」还是「额度错误」。
**只跑 `/models` 或鉴权探测就宣布「接入成功」是不合格的。**

> 四种「用不了」怎么区分（401 / 403-token / 403-quota / 429 / 503）见本节末
> 「★ 四种「用不了」必须分清」——**403 有两种完全不同的病因，必须读错误正文。**

### ⚠️ 连不上时先怀疑本机代理，别急着怪接口

#### 🔴 代理坑 A（**2026-10-06 定量复核后的最终版**）：沙箱代理**会漂移**，别凭单次观测下结论

**现象**：请求 API 返回 **HTTP 200 + `<!DOCTYPE html>…百度一下`**（约 127KB）。
**这不是服务端错误页，是代理的兜底页** —— 一眼判据：**响应体出现「百度一下」**。

**定量探测（同一时刻，每格 4 次）**：

| 目标 | 沙箱代理（环境变量） | **Clash `127.0.0.1:7897`** | 直连 |
|---|---|---|---|
| `apihub /v1/models` | ❌ JSON **0/4**（全百度页） | ✅ **4/4 稳** | ❌ 3 百度 + 1 失败 |
| `apihub /billing/usage` | ❌ JSON **0/4** | ✅ **4/4 稳** | ❌ |
| `platform-outputs.agnes-ai.space`（产物） | ❌ 302 → `m.baidu.com` | ✅ **200 + video/mp4** | ❌ |

★★ **二次复核（同日稍晚）—— 沙箱代理的可达范围【本身也会变】**：

| 目标 | 沙箱代理（当日 49418） | Clash `7897` |
|---|---|---|
| `apihub`（API） | ❌ **000 完全不通**（同期另一次实测却记到「200 正常」） | ✅ 200 |
| `example.com` | ✅ **200 可达** | ❌ SSL error 35（被 Clash 规则拒） |

→ 🔴 **两个代理是「互补」关系，不是「一个不行就换另一个」**：
  沙箱代理通「普通公网域名」，Clash 通「apihub 与产物 CDN」，
  而 **`example.com` 在两者上结论完全相反**。
→ 🔴 **这解释了历史上「example.com 可达 / 不可达」两种记录打架的根源**：
  **不是谁记错了，是测的时候走了不同的代理。**
  → **纪律：记连通性结论必须同时记「当时用的哪个代理 + 什么端口」**，
    否则下次引用时必然误判。

- 🔴 **关键：它不是「域名黑名单」，而是「会漂移」** —— 实测**同一会话内先通、后不通**
  （开局能 200 返真 JSON，跑一阵后 100% 百度兜底页）。**疑似有配额/熔断。**
  → 「今早测过是通的」**不能**当作长任务不加代理的理由（本轮真实踩过：跑一半漂移、整轮崩）
- ✅ **稳妥做法：长任务一律走本机 Clash `127.0.0.1:7897`**（API 与产物 CDN 都通）
- 代理端口每次会话都变（见过 49418 / 55150 / 64413 / 7897）→ `env | grep -i proxy` 现查
- 客户端留 **`--proxy` / `--no-proxy`** 两个开关，并**允许 API 与下载用不同代理**

> 🔴 **两条教训（这是本坑最有价值的部分）**：
> ① **单次探测不足以下结论** —— 它既可能冤枉一条好路，也可能误放一条坏路；
>   要判就**连测 ≥4 次**看命中率。
> ② **纠正一个旧结论时，同样要多次测量** —— 本轮差点因为「开局那一次是通的」，
>   把一个**本来正确**的结论改成错的。**改结论的门槛，不能低于下结论的门槛。**
> 另外仍成立：**「curl 能通」≠「Python 能通」**（curl 用 Windows schannel，Python 用 certifi）。

#### 🔴 代理坑 A2（★ 2026-10-06 实测，最容易被误判的一条）：**API 主机与产物 CDN 的代理需求不同**

同一套代理设置下，**两个域名行为完全相反**：

| 域名 | 角色 | 走【沙箱默认代理】 | 走本机 Clash `7897` |
|---|---|---|---|
| `apihub.agnes-ai.com` | **API 主机**（提交/查询） | ⚠️ **会漂移**：见过 ✅200 也见过 ❌000 | ✅ 200 |
| `platform-outputs.agnes-ai.space` | **产物 CDN**（下载成片） | ❌ **302 → `https://m.baidu.com`**，拿回一张百度网页 | ✅ **200 + `video/mp4`** |

**症状与误判链**（本项目真实踩过）：
1. 产物下载失败 → 报 `CERTIFICATE_VERIFY_FAILED: Hostname mismatch`
2. 第一反应归因「**证书问题**」→ 去开 `--insecure`（**方向错了**）
3. 其实根因是**代理把产物域名 302 兜底到百度** → 拿到的是 HTTP 网页，根本不是视频流
4. 🔴 更早的一次误判：把这条兜底现象记到了 **`apihub`** 头上，于是得出
   「API 被拦、必须走 Clash」的结论修正为「API 一直是通的」——
   **而后续定量探测（每格 4 次）又证明：那条路确实会 100% 兜底成百度页。**
   → 🔴 **教训：单次探测既能冤枉一条好路，也能误放一条坏路。改结论的门槛不能低于下结论的门槛。**

**正确做法**：
- **API 与下载分开配置代理**：客户端要有独立的 `--download-proxy`
  （本项目已加，环境变量 `AGNES_DOWNLOAD_PROXY`）
- 走 Clash 下载产物时**不需要 `--insecure`**（证书本身没问题，是路由问题）
- 🔴 **下载后必须校验它真是视频**（看魔数 `ftyp` / `Content-Type`），
  否则会把一张百度网页当成 mp4 存下来 —— **文件大小看着像成功了**
- 🔴 **产物已生成即已计费**：下载失败**只能补下载**（`--resume` / 补取脚本），
  **绝不能重新提交**（会二次扣费）

#### 🔴 代理坑 B：TLS 证书不被 certifi 认可（**间歇性，必须自动降级**）

Python 走 certifi CA，而代理对 HTTPS 做 TLS 中转时证书不被认可 →
报 `CERTIFICATE_VERIFY_FAILED: Hostname mismatch: certificate is not valid for '<host>'`。
**而且它是间歇性的** —— 实测**同一个进程里前几次请求正常、第 N 次突然失败**，
极易被误判成「服务端不稳」或「域名被拦」。

🔴 **关键设计结论：这件事无法「事先判断」** —— 不能靠启动时探测来决定要不要放宽校验，
**必须在失败后自动重试一次**。客户端应内建：
`第一次用默认校验 → 证书失败 → 立即用 `_create_unverified_context()` 重试一次并打警告`。
（本项目已实现，开关 `AGNES_TLS_FALLBACK`，默认开。）

排查顺序（**按这个顺序，别跳步**）：
1. `env | grep -i proxy` 看当前代理（**端口会变，别用记的**）；
2. **看响应体**：是不是百度页/HTML？（→ 坑 A，切 Clash）
3. `curl --noproxy '*'` 对照 —— 直连不通、走代理能通 → 是代理路径问题；
4. 才是证书问题 → 客户端留 **`--insecure` / `AGNES_INSECURE=1` 逃生阀**，
   并**默认开启「证书失败自动降级重试」**（不要只给手动开关）。
   ⚠️ `--insecure` / 自动降级只适用于受控的本地代理环境，公网直连时应关掉。

### 还要排除的变量

| 变量 | 怎么排 |
|---|---|
| **鉴权 header 格式** | 依次试 `Authorization: Bearer X`、`api-key: X`、`x-api-key: X`。看报错措辞：「Token not provided」= 没读到；「Invalid token」= 读到了但不认 |
| **站点/区域** | 国际站与中国站（`.com` / `.cn`）**key 通常不通用**，两边都要试 |
| **key 格式** | 查长度、字符集、有无隐藏空格。若格式正常却仍 401 → **是 key 不被平台认可**，不是复制残缺 |
| **端点路径** | 试 `{base}/xxx` 与 `{base去掉/v1}/xxx` 两种 |

### 关于「来源不明的 key」

若 key 来自教程/博客/群分享（线索：前缀与某公开项目作者 ID 重合等）：
- 大概率**已被回收或限流**
- 用它可能违反条款里「**不得共享 API 密钥**」的约定
- → **建议用户自己注册**，并把判断依据如实说明，不要含糊带过

### ★ 四种「用不了」必须分清（解法完全不同）

| 响应 | 含义 | 怎么解 | 会扣费吗 |
|---|---|---|---|
| 401 / 403 + `Invalid token` | key 无效 | 换 key | 否 |
| **403 + `quota` / `balance` / `remaining`** | 🔴 **余额/额度不足** | **充值** | 否 |
| **429** | 速率限流 / **免费档总量限制** | 退避重试；或升级付费 | 否 |
| **503 `queue is full`** | 服务端整体队列满 | 指数退避重试 | 否 |

**🔴 最容易误判的一对**：`403` 既可能是「key 无效」，也可能是「余额不足」。
**必须读错误正文**，不能只看状态码。实测原文：

```
HTTP 403: Failed to pre-consume quota,
remaining: ＄0.000074, required: ＄0.125000
```

→ 若不细看就会误报「key 无效」，把用户引到完全错误的方向（换 key 而不是充值）。
**客户端应把这类单独识别，给出充值指引。**

**🔴 免费档不是「无限免费」**：实测 Agnes 免费档跑过若干次后返回：

```
HTTP 429: You've reached the API rate limit for free users.
Upgrade to a Token Plan to unlock higher limits...
```

→ 免费档有**总量 + 速率双重限制**。号称"限时免费"的服务，
**批量生产前必须先摸底真实可用量**，否则排产计划会落空。

## 三、🔑 无凭证时怎么办：用 mock 网关验证客户端

**这是本 skill 最有价值的一条。**

拿不到有效凭证时，最容易犯的错是**让「客户端逻辑没验证」和「凭证无效」两件事混在一起** ——
最后既不知道代码对不对，也不知道服务能不能用。

**正确做法：把两件事拆开。**

1. 本地起一个 mock 网关，模拟三段行为：
   - `POST /v1/videos` → 返回 `video_id`
   - `GET /agnesapi?video_id=...` → 依次返回 `queued` → `in_progress` → `completed` + 视频地址
   - `GET /mock/video.mp4` → 返回一段真实的小 mp4
2. 让客户端指向 mock（需要客户端支持 `--base-url`，**写客户端时就要留这个口子**）
3. 跑完整流程，再用 `ffprobe` 校验下载物是合法视频

→ 结论：**「除凭证外一切就绪」**，用户拿到 key 后一条命令即可实测。

**★ 出片后必做：核对「实测时长 / 分辨率」与请求参数**（2026-10-06 实测才发现）

云端视频模型**不保证时长精确等于请求值**。Agnes Flash 请求 4 秒，实测输出
**4.458 秒 / 107 帧 @24fps**（多出约 0.46 秒尾帧），分辨率倒是精确 1280×720。

```bash
ffprobe -v error -select_streams v:0 -show_entries \
  stream=width,height,r_frame_rate,nb_frames,duration \
  -show_entries format=size -of default=noprint_wrappers=1 out.mp4
```

**为什么必须查**：产线做音画对齐时，如果拿「请求秒数」当预期值，
每段都差 0.3~0.5 秒，8 段累积下来字幕必然错位。
→ **一律以 ffprobe 实测 duration 为准**回填到合成参数（与本产线既有的
「单段帧数上限 ≥ 最长音频段」纪律是同一类问题的两种表现）。

**实测到的三种「对不上」**：

| 现象 | 实例 | 处理 |
|---|---|---|
| 时长偏长 | 请求 4s → 实测 4.458s；请求 5s → 5.17~5.18s | 按实测回填 |
| **分辨率被输入素材带偏** | keyframe 请求 720P → 实测 **1280×704**（非 1280×720） | 按实测归一化，**别信请求档位** |
| 档位等于放大 | 2K 码率 ≈ 1080P → 细节没提升 | 见 §五「每像素成本」 |

→ 🔴 **一句话：请求参数只是「意向」，实测值才是「事实」。**
混拼前一律用 ffprobe 读实际宽高/时长/帧率，否则 `xfade` 会 size mismatch。

**省事做法**：本机已有跑通的实例 —— `scripts\agnes_e2e.py`（同进程起 server 线程 + 12 项断言）。
换模型时只需改 `agnes_mock.py` 里的路径和响应字段，客户端不用动。
**别自己从零写**，这套里已经踩掉了代理拦截、后台进程被回收这两个坑。

**连通注意**：本机有 HTTP 代理。代理环境有**两个方向完全相反**的坑：

| 场景 | 现象 | 解法 |
|---|---|---|
| 访问**本地回环**（mock/自建服务） | 502 | **绕开**代理 |
| 访问**外网 API** | `CERTIFICATE_VERIFY_FAILED: Hostname mismatch` | **放宽校验** |

**① 本地回环要绕开代理**
- curl：`--noproxy '*'`
- Python：`os.environ["no_proxy"]="127.0.0.1,localhost"` + `build_opener(ProxyHandler({}))`

**② 外网 API 会被代理拦截 TLS（本轮实测，稳定复现）**

- **根因**：代理对 HTTPS 做了转发，其证书不被 Python 的 certifi 认可
- `curl` 用 Windows **schannel** → 信任该证书 → **能通**
- Python `urllib` / `requests` 用 **certifi** → 不认 → **失败**
- → 🔴 **「curl 能通」不代表「Python 能通」，这个差异极具误导性**

**解法**：客户端内建 `--insecure`（或环境变量），用 `ssl._create_unverified_context()`：

```python
INSECURE = os.environ.get("AGNES_INSECURE", "").lower() in ("1","true","yes")
def _ssl_context():
    return ssl._create_unverified_context() if INSECURE else ssl.create_default_context()
# 注意：要用 build_opener(HTTPSHandler(context=ctx))，urlopen 不能直接传 context
```

- ⚠️ **仅限受控的本地代理环境**；公网直连不要开（会让 MITM 无法察觉）
- **SSL 失败时要主动提示这个开关**，开启时打印醒目警告
- 环境变量里 `https_proxy` 指向哪，就是这一个坑的来源（排查第一步就看它）

**③ 不要用 `&` 在 Bash 工具里起后台服务**
命令结束就被回收 → 改成**同进程内起 server 线程**，跑完即退出（自包含、可重复）。
长任务同理：用工具原生的后台机制，别用 `nohup &`。

### 客户端该内建的自检

| 开关 | 作用 |
|---|---|
| `--selftest` | 离线校验：参数规则、地址解析、状态机、端点构造、报错可读性。**不需要网络和 key** |
| `--check` | 只探鉴权，不消耗额度 |
| `--base-url` | 指向自建/中转/本地 mock |

## 四、授权与商用风险核查（自媒体必做）

### 必须查的三件事

1. **条款里有没有「商业使用」这个词？** —— 没有出现 ≠ 允许，也 ≠ 禁止，**是灰色**
2. **是否默认拿你的数据训练？退出开关真的提供吗？** —— 警惕「*如果可用*」「*在提供该选项的情况下*」这类措辞
3. **是否要求标注 AI 生成？** —— 现在多半是强制义务（国内 2025-09 起也有法规要求）

### 常见的坑（实测汇总）

| 坑 | 说明 |
|---|---|
| 条款沉默 | 大量 AI 服务条款**根本不提商用**，只写「输出归用户」。网上「可用于商业用途」多为**二手转述**，不能当依据 |
| 免费计划无 SLA | 「不保证任何级别的可用性」是标配 |
| 责任上限极低 | 常写成「索赔前 N 个月已付费用」→ 免费用户 = **0** |
| 赔偿单向 | 用户须为平台辩护并承担费用 |
| 境外管辖 | 优先新加坡/美国法律 + 仲裁，维权成本高 |
| **限时免费** | 免费是获客手段，随时恢复原价。**若已大规模接入，成本会突增** |
| 内容审核 | 云端一律受可接受使用政策约束，可删内容、停账户 |

### 与产线既有标准对齐

产线现在用的都是**授权明确**的方案：
- ACE-Step（Apache 2.0）
- Mixkit（明确「免版税 + 免署名 + 可商用」）

→ **新加入者如果授权明确度明显偏低，应当直接指出，不要因为「免费」就放低标准。**

## 五、与本地方案对比：记住是「互补」不是「替代」

必比的维度（缺一不可）：

| 维度 | 为什么关键 |
|---|---|
| 分辨率 | 决定超分链的起点质量 |
| 单段时长 | **段数越少 → 转场补偿误差累积越少 → 字幕同步越稳** |
| 单段耗时 | 决定批量产能 |
| **显存占用** | ★ 本机 16GB 是硬约束；云端 = 0 占用 |
| 自带音频 | 省一层音效来源 |
| 可控性 | 本地有 ControlNet 精确锁构图；云端多半只有首尾帧/参考图 |
| 内容审核 | 云端有，本地没有 |
| 网络依赖 | 云端强依赖 |
| 成本 | 电费 vs 按秒计费 |
| **商用许可** | 见第四节 |

### ★ 「机会成本」视角：但也别高估速度

**起初我以为云端与本地耗时打平，真正的差别在显存。**
**实测后要修正这个判断 —— 免费档的排队会把「耗时打平」彻底推翻。**

实例（Agnes vs 本地 Wan2.2，生成 8 段）：

| | 本地 | 云端（免费档，实测） |
|---|---|---|
| 生成耗时 | 8 × 78 秒 ≈ **10.4 分钟**（稳定） | 8 × (75s 限流 + **队列等待** + 生成) ≈ **30–60 分钟**（不可预测） |
| 成功率 | 100% | **约 1/3**（实测连续 3 次 `503 queue is full`） |
| 显存 | 🔴 **全程被占满** | ✅ **空闲** |
| 机会成本 | 期间干不了别的 GPU 活 | **本机可并行跑出图/超分/TTS** |

→ **实时结论**：云端**更慢且不稳定**，但它**把显存解放出来**。
→ 所以云端真正的价值排序是：
**① 画质（可能代际领先）② 不占显存 ③ 长单段** —— **速度不是它的卖点**。
→ 结论通常是：**本地当主力（快、稳、可控、授权清晰），云端当辅助**
（高质量 B-roll / 空镜、显存被占时的并行产能、需要长镜头的段落）。

> ⚠️ **教训**：评估云端服务时，**「官方标称耗时」几乎一定偏乐观**。
> 免费/推广档必须实测**排队时间**与**提交成功率**，否则产能估算会错一倍以上。

### ★ 计费核查：单价便宜 ≠ 真的便宜

**核心动作：读「计费公式」，不要只抄「单价表」。** 公式里常常藏着额外收费项。

#### 通用核查清单（接任何云端生成服务都问一遍）

| 项目 | 要问的问题 |
|---|---|
| **输入/参考素材** | 计费吗？按什么单价计？**会不会按输出单价计？** |
| 素材时长 | 是否计入「总计费时长」？ |
| 免费额度 | 前几张免费？超出单价多少？ |
| **最低计费单位** | 不足 N 秒按 N 秒算？ |
| 失败任务 | 退费吗？ |
| 结果保留 | 出片后存多久？超期收存储费吗？ |
| **积分 vs 现金** | 两套价的计量结构相同吗？**单价是否不同**？以哪个为准？ |
| 分辨率档位 | 每档单价差异 |

#### ⭐ 先找「用量查询接口」—— 没有它就只能靠猜

**别假设「官方没有额度接口」**（本项目曾据此记为「只能人工核对后台」，后来实测**是有的**）。

**排查顺序**（OpenAI 兼容网关常沿用这套路径）：

```bash
curl -s -H "Authorization: Bearer $KEY" https://<host>/v1/dashboard/billing/usage
#   -> {"object":"list","total_usage":107.94}      ← 单位：美分
curl -s -H "Authorization: Bearer $KEY" https://<host>/v1/dashboard/billing/subscription
#   -> {"has_payment_method":true,"hard_limit_usd":...}
```

- 常见的 `/v1/usage`、`/v1/quota`、`/v1/balance` 可能全是 404，**但 billing 路径存在**。
- 🔴 **`total_usage` 是「账户累计值」**：实测带 `?start_date=&end_date=` **也返回同一个数**，
  **不能按日期分段**。
  → **单条任务成本 = 任务前查询值 与 任务后查询值 的差值**。
- 🔴🔴 **记账必须串行**：多个任务并发时，各进程读的是**同一个全局计数器**，
  会把别人的消费算进自己的差值（本项目实测出现过一次异常的 $0.60）。
  **要逐条核对成本，就一次只跑一条。**

**验证计费公式是否抄对**：用官方文档给的计费示例写成自检断言（见 §五「验算」）。

#### 实战案例：Agnes Video 2.5 的两个反直觉点

1. 🔴 **参考视频按「输出档位」单价计费**，不是免费、也不按输入规格：
   `总额 = 输出秒数×单价 + 输入视频秒数×【输出】单价 + ...`
   → 12 秒参考视频在 2K 档要 **$0.66**，可能比输出本身还贵。
2. ✅ **音频参考不计费**（公式里没有音频项）。
   → 「让画面跟随音乐节奏」这个能力是零成本的 —— **对产线是纯赚**。

#### ⭐ 跨档比较要用「每像素成本」，不是「每秒单价」

Agnes 实例（16:9）：

| size | 单价 | 像素 | 每美元像素·秒 |
|---|---|---|---|
| 720P | $0.025 | 1280×720 | 36.9 M |
| 1080P | $0.040 | 1920×1080 | 51.8 M |
| **1K** | $0.040 | 1024×1024 | **26.2 M（最差）** |
| **2K** | $0.055 | 2560×1440 | **67.0 M（最好）** |

→ **1K 与 1080P 同价，但像素只有一半** —— 只看单价表会挑错档。

#### 🔴 「每像素成本」只能粗筛 —— 但**理由和之前记的不是同一个**

**之前记的理由**：「码率不随像素线性增长（实测 2K 码率 ≈ 1080P）」→
**这个前提本身是错的**。两批独立批次复测（同 prompt 同 seed，各 3 档）：

| 档位 | 像素 | 码率（批次A / B） | **bpp**（A / B） |
|---|---|---|---|
| 720P | 1280×720 | 7330 / 7682 kbps | 0.33 / 0.35 |
| 1080P | 1920×1080 | 12568 / 10676 kbps | 0.25 / 0.22 |
| 2K | 2560×1440 | 23731 / 19607 kbps | 0.27 / 0.22 |

→ ✅ **码率确实随像素近线性增长**；**2K 不是放大**。

**真正让「每像素成本」不准的是另一件事**：

1. **绝对码率强烈依赖画面内容**：上一轮 2K 只测到 6.02 Mbps，本轮 19.6–23.7，
   **差 3–4 倍** —— 仅仅因为随机到了不同画面。→ **码率不能跨画面比较。**
2. **「每像素便宜」≠「更有用」**：交付分辨率决定你需要多少像素，
   多出来的像素只是**白花钱**（见下「按交付分辨率选档」）。
3. 🆕 **同 prompt + 同 seed 也不够**：分辨率一变，**latent 尺寸就变**，
   采样轨迹必然分叉 → 三档成片亮度能差 30+，**画面根本没对齐**。
   → 要真正"同画面"，只能 **keyframe 模式 + 同一张首帧图**（`agnes_kf_sweep.py`）。

→ 所以最终定档顺序是：
**① 先用「每像素成本」粗筛候选档 → ② 用「交付分辨率」砍掉多余档 →
③ 若该平台 `seed` 不可复现（见下一节），到此为止，不要再试图用画质测量翻案。**

> 🔴 **下一节是本技能最重要的一条**：实测 `seed` **不提供可复现性**，
> 意味着上面这些「跨档比较」的**全部测量手段都建立在流沙上**。先读它。

#### 🔴🔴 先看这条：**`seed` 很可能不提供可复现性 → 跨档位比画质根本做不了**

**2026-10-06 决定性实测（Agnes 2.5）**：同 prompt、同档位、同 `seed`，独立跑两次——

| 比较 | 帧差（0=相同，255=全不同） |
|---|---|
| **同 seed、同档位，两次生成** | **46–51 / 255** |
| 不同 seed、同档位 | 52–55 / 255 |

→ **同 seed 的差异 ≈ 不同 seed 的差异，`seed` 形同虚设。**
（视觉证据：两次生成一张是「车驶向街深处」、一张是「轮毂特写」，构图完全不同。）

**推论：在这类平台上「控制变量实验」不成立**，因此**所有跨档位清晰度对比都是在比不同画面**，
数字必然是噪声。这就是为什么同一实验换个 seed 会得到**互相矛盾**的档位排序。

🔴 **补充（同日实测，很重要）：`keyframe` 同图法只能救回 `t=0`，救不了 `t>0`。**
同首帧图驱动三档 → `t=0` 相同 ✅，但放大人物区域后发现**三档演化成三个不同画面**
（720P 伞完整 / 1080P 伞缺半且人物断裂 / 2K 伞消失）。
→ **所以连 `keyframe` 也不能用来做跨档画质定论。**
→ 更隐蔽的后果：**1080P 的"高边缘能量"其实是人物断裂产生的假边缘**
（详见「画质怎么测」一节的实测表）。

#### ⚠️ 画质指标会被"画面分叉"和"伪影"双重污染（实测警告）

`sobel` 边缘能量这类指标**对「断裂的轮廓」响应极强** ——
一个人物上下半身错位，会产生大量**假边缘**，让分数**虚高**。

🔴 **Agnes 2.5 实测反例**：

| 档位 | 边缘能量 | 看起来 | **实际画面** |
|---|---|---|---|
| 720P | 60.60 | 中等 | ✅ 伞完整、人物完整 |
| 1080P | **71.68（最高）** | "最清晰" | ❌ **伞缺一半、人物上下身断裂**（假边缘推高分数） |
| 2K | 47.44（最低） | "最糊" | ❌ **伞完全消失**（内容丢了 → 纹理最少 → 分数低） |

→ 🔴 **分数排序与观感排序完全相反** → **不要用画质指标给这类模型定档。**
→ ✅ **正确用法**：指标只用来**粗筛异常**（如整片灰白、明显崩坏），
   **不能用它排"哪档更好"**。**一定要导出帧目视**。

🔴 **接任何云端视频模型，先花 1 次调用验证 seed 是否可复现**（同 seed 跑两次比帧差）：

```bash
# 两次生成后比帧差；>30/255 基本可判定「不可复现」
ffmpeg -v error -ss 2.5 -i run1.mp4 -ss 2.5 -i run2.mp4 \
  -filter_complex "[0:v][1:v]blend=all_mode=difference,signalstats,\
metadata=print:key=lavfi.signalstats.YAVG" -frames:v 1 -f null - 2>&1 \
  | grep -o "YAVG=[0-9.]*"
```

**不可复现时，选档只能依据三件确定性的事**
（🔴 **任何模式都别再测「谁更清晰」** —— 连 `keyframe` 同图法也做不到，见下）：
1. **交付需要多少像素**（先量清自己的成片分辨率）
2. **单价**（每次生成前后的用量差值可精确核验）
3. **码率**（唯一勉强内容无关的信号，但也需多样本平均）

#### ⚠️ 出路：用「输入图」代替「seed」来锁画面 —— **但只能锁住起点**

`seed` 锁不住，但**输入图能锁住起点** —— 因为 `t=0` 那一帧由输入图决定，与 `seed` 无关：

```bash
python agnes_kf_sweep.py          # 同一张首帧图驱动 720P/1080P/2K 三档
```

- ✅ **t=0 逐像素相同** → 起点被锚住（比 text 模式好）
- ✅ **验收方法**：把三档帧导出**目视比对构图**确认同画面（`agnes_clarity2.py` 会导出）
- 🔴 **但 t>0 仍会分叉！** 实测把**人物区域放大**后，三档演化成**三个不同画面**：

  | 档位 | 人物实际形态 |
  |---|---|
  | 720P | ✅ 伞完整、全身完整 |
  | 1080P | ❌ 伞只剩一半、**上下半身错位断裂** |
  | 2K | ❌ **伞完全消失**，只剩无脸人影 |

  → 🔴 **所以 keyframe 同图法「只救回一半」：起点相同 ≠ 过程相同。**
- 🔴🔴 **由此得出一条极易犯的错**：Agnes 2.5 实测里 1080P 的**边缘能量最高（71.68 vs 720P 的 60.60）**
  —— 但这个高分**主要来自人物轮廓断裂产生的「假边缘」**，**不是真细节**！
  2K 最低（47.44）也不是"最糊"，而是**它那一帧恰好丢了最多内容**（伞都没了 → 纹理最少）。
  → ✅ **正面印证**：「**客观指标只作辅助；主观观感差距往往比数字更大**」。
    若只看数字就下"1080P 画质最好"，会得到**方向都错**的结论。
- 🔴 **必须显式传 `model="agnes-video-2.5"`** —— 客户端默认是免费档（见 7.3 的工程坑）

**结论：在「`seed` 失效」的平台上，跨档画质对比本质上不可靠** ——
无论用什么实验设计，都排除不掉「内容分叉」这个干扰。
→ **定档只能依据确定性事实**（交付分辨率 / 单价 / bpp），见下一节。

**Agnes 2.5 实测（keyframe 同图，1280×720 首帧）：**

| 档位 | 实测输出 | 码率 | bpp | 归一化后边缘能量 | **这个数字能说明什么** |
|---|---|---|---|---|---|
| 720P | 1280×704 | 6895 | 0.319 | 60.60 | — |
| 1080P | 1888×1088 | 20993 | **0.426** | 71.68 | ❌ **伪影推高的，不能解读为"更清晰"** |
| 2K | 2688×1536 | 37552 | 0.379 | 47.44 | ❌ **内容丢失导致的，不能解读为"最糊"** |

→ ⚠️ **这三档的边缘能量排序不可用**（已实测证伪）。
  可用的只有 **bpp**（三档 0.32–0.43 → 都是真渲染），以及**交付分辨率算术**。

> ⚠️ 早前本技能里「1080P 是甜点、2K 是陷阱」的结论**建立在无效方法上**（跨档比清晰度），
> **不要再引用**。而且码率对比同样受内容干扰 → 也不可单独作定档依据。

#### 🔴 keyframe 模式下「实测分辨率 ≠ 请求档位」（三档同时证实）

| 请求 | 文档标称 | keyframe 实测 | 偏差 |
|---|---|---|---|
| 720P | 1280×720 | 1280×**704** | 高 −16 |
| 1080P | 1920×1080 | **1888×1088** | 宽 −32 / 高 +8 |
| 2K | 2560×1440 | **2688×1536** | 宽 +128 / 高 +96 |

→ 输出尺寸由**首帧图 + 档位共同决定，偏移无简单规律** →
  **混拼前必须 ffprobe 量实测尺寸再归一化，绝不能信请求档位。**

#### ✅ 但 `reference` 模式与 `text` 模式尺寸是**精确**的（2026-10-06 补）

**实测 6/6 全中**：`reference` + `size=2K` + `aspect_ratio=16:9` → **6 条全部 2560×1440**，零偏移。
（`text` 模式亦精确，含 9:16 竖屏 720×1280。）

→ 🔴 **订正一条容易过度概括的印象**：**「实测尺寸≠请求值」只对 `keyframe` 模式成立。**
→ **纪律**：「尺寸不准」必须按 **模型 + 模式** 分别验证，不能笼统记成"这个平台尺寸不准"。
→ **实践**：需要精确交付尺寸时**优先用 reference/text，而不是 keyframe**。

#### ⭐ 按「交付分辨率」选档

```bash
ffprobe -v error -select_streams v:0 -show_entries stream=width,height \
  -of default=nw=1 <你的成片.mp4>          # 先量清交付分辨率，再选档
```

实测本产线交付是 **704×480**（337,920 像素），所以：

| 档位 | 像素 | 相对本地 | 每 5 秒成本 | 每像素成本（算术） |
|---|---|---|---|---|
| 720P | 921,600 | 2.73× | $0.125 | 7.4 M px/$ |
| **1080P** | 2,073,600 | 6.14× | $0.200 | **10.4 M px/$** |
| 2K | 3,686,400 | 10.9× | $0.275 | 13.4 M px/$ |

- **要付费提升画质，别停在 720P**（相比本地只升 1.5× 垂直分辨率）。**1080P 是合理起点。**
- 2K 的「每像素成本」算术上最优，但**「这些像素是否真细节」在本平台无法验证**（见上）
  → 除非确实需要 1440p 母版，否则**不付溢价**。
- 🔴 交付分辨率若是 720p 或更低，**更高档位只是被降采样**，纯浪费。

#### 验算：把官方示例做成本地断言

官方文档一般给一个计费示例。**把它写成自检断言**，公式抄错立刻暴露：

```python
c = estimate_cost(size="720P", out_seconds=8, in_video_seconds=3, n_images=7)
assert abs(c["total_usd"] - 0.285) < 1e-9   # 官方：(8+3)×0.025 + 2×0.005
```

#### 收费模型必须内建的两道闸

1. **提交前打印预估费用**（用户看得见才会注意）
2. **`--max-cost-usd` 安全阀**：预估超阈值直接中止，**不提交、不扣费**
3. 外加 `--estimate`：只算钱不提交，用于批量前摸底

> 💡 **默认模型要选免费档。** 用户没显式要求时，
> CLI 不应产生费用。收费模型必须显式指定（`--model <付费版>`）。

## 六、接入产线的落点

产线在 `compose_long_video.py` 里由 `gen_video(prompt, w, h, length, steps, cfg, seed, out_file, start_image)`
生成每一段视频。**云端接入 = 在同一签名位置替换**：

```
现在：  gen_video(...)              → seg01.mkv（无损 FFV1）
改为：  agnes.generate(prompt, ...) → seg01.mp4
```

**后续流程完全不用改** —— `final_encode()` 接受任意视频文件列表，与来源无关
（转场拼接、三轨混音、烧字幕都照旧）。

### 🔴 但「完全不用改」有个前提：先把片段归一化

**这是我实际踩到的最大坑。** 云端片段与本地片段**不能直接混拼**，
`xfade` 会连续报两个错：

```
First input link main parameters (size 1280x720) do not match
the corresponding second input link xfade parameters (size 704x480)

First input link main timebase (1/12288) do not match
the corresponding second input link xfade timebase (1/1000)
```

**根因：封装与采样特征三处不一致**

| 特征 | 本地（FFV1 mkv） | 云端（h264 mp4） |
|---|---|---|
| 分辨率 | 704×480 | 1280×720 |
| **timebase** | **1/1000** | **1/12288** |
| **像素格式** | **`gbrap16le`（16 位 + alpha）** | `yuv420p`（8 位） |

> 🔴 **订正（2026-10-06 复核）**：本表**此前把两列 timebase 写反了**。
> 实测本地产线中间片（`output\long_*.mkv`）= **FFV1 / 704×480 / 1/1000 / gbrap16le**；
> 云端 Agnes = **h264 / 1280×720 / 1/12288 / yuv420p**。
> 注意：上方**报错原文其实是对的** —— `main`（1280x720, 1/12288）是云端、
> `second`（704x480, 1/1000）是本地，只是表格标签贴反了。
> 好在下方的**处理动作一直是对的**（把云端片段归一化到 704×480 去适配产线）。

> ⚠️ `gbrap16le` 特别隐蔽：它会让 `sobel` 等滤镜链**直接失败**（实测报错）。

**解法 —— 五件事一次做完**（`settb=AVTB` 最容易被漏）：

```bash
ffmpeg -i cloud.mp4 \
  -vf "scale=704:480:flags=lanczos,fps=24,settb=AVTB,setsar=1" \
  -c:v ffv1 -level 3 -pix_fmt yuv420p -an out.mkv
```

| 参数 | 缺了会怎样 |
|---|---|
| `scale` | xfade 报 size mismatch |
| `fps` | 时基仍可能不一致 |
| **`settb=AVTB`** | **xfade 报 timebase mismatch** |
| `setsar=1` | 播放时拉伸 |
| `-pix_fmt yuv420p` | 滤镜链失败 |
| `-an` | 产线只取 `:v`，留着无用 |

**💡 只需归一化云端一侧**：归一化产物（8-bit）与本地 16-bit 片段混拼时，
ffmpeg 会自动做色彩空间转换 → **产线的 FFV1 中间格式完全不用动**。
（会有 `No accelerated colorspace conversion` 警告，那是走软解，**不影响结果**。）

**现成工具**：`code-news\scripts\agnes_normalize.py`（单文件 / 批量 / `--match-dur` 对齐时长）

### 💡 第二条路：全云端模式无需归一化

**同源**的云端片段之间 `xfade` **直接成功**（实测）。所以：

| 模式 | 需要归一化 | 适用 |
|---|---|---|
| **全云端** | ❌ 不需要 | 整条片子都用云端出图，格式天然统一 |
| **混用** | ✅ 必须 | 主力本地、个别段用云端补质量 |

### ⚠️ 云端片段自带的音轨，产线多半会丢弃

**接入前务必核查目标产线的音频处理逻辑。** 本产线的 `final_encode()`：

```
音频只接三轨：① 旁白  ② BGM  ③ 音效
输入构建只用 "-i <clip>"，取流只取 :v —— 片段自带音轨从未被引用
```

→ 实测确认：**云端的环境音/口语不会进入成片**（设计使然，非 bug）。
→ 若要用上，需要把它做成第 4 条混音轨 —— **那属于改核心脚本，先验证 + 拿用户确认**。

### ⚠️ 改产线核心脚本前必须满足

1. **先跑通独立工具**（不要一上来就改核心脚本）
2. **有实测证据**（真实生成过、看过片）
3. **拿到用户确认**

→ 产线纪律：**不给「推测性修改」开门**。没验证过的改动一律先进独立工具。

### 试用三步走

| 步 | 做什么 | 判定 |
|---|---|---|
| 1 | 拿到 key → 跑 `--check` | key 有效 |
| 2 | 生成 2–3 条不同 prompt 的样片（含 1 条中文场景） | 用眼睛判断画质 |
| 3 | 替换 demo30 的某一段，走完整产线 | 看端到端效果 + 字幕同步 |

**没看片之前不讨论架构** —— 这是产线一贯的纪律。

### ★ 画质对比必须「同 prompt」，否则结论会错一倍

**踩过的坑**：我先拿云端的「霓虹街景」比本地的「场记板」——内容不同 → 不公平。
客观指标算出 **4.7 倍**差距；换成**同一个 prompt** 重测，只有 **1.78 倍**。

→ **做法**：从目标产线已有的分镜里**取真实 prompt**，让两家生成同一个画面。
→ 云端输出统一缩放/降位深后再比，否则编码差异会污染结论。

> 🔴 **「同 prompt」还不够 —— 2026-10-06 追加**：实测该平台 `seed` **不提供可复现性**，
> 「同 prompt + 同 seed」仍然会生成**完全不同的画面**（帧差 ≈ 不同 seed 的帧差）。
> → **跨档位/跨批次比画质在数学上不成立**。详见 §五「`seed` 很可能不提供可复现性」。
> 本条仍适用于**两家不同服务商之间的粗对比**，但**不要用它给同一家的档位排序**。

**客观量化手法**（Sobel 边缘能量，越高越锐利）：

```bash
ffmpeg -hide_banner -i in.mkv \
  -vf "format=gray,sobel,signalstats,metadata=print:file=-" \
  -frames:v 24 -f null - 2>/dev/null \
  | grep -o "YAVG=[0-9.]*" | cut -d= -f2 \
  | awk '{s+=$1;n++} END{printf "%.2f\n", s/n}'
```

- 必须 `metadata=print:file=-` 才会输出到 stdout（不加会被 `-v error` 吞掉）
- 必须先把 16-bit 源降成 8-bit，否则滤镜链失败
- **客观值只作辅助**：主观观感（细节可信度）差距往往比数字更大

### ★ 免费档的 503「队列满」必须内建重试 —— 但先确认**它到底能不能用**

**这与「提交限流」是两个不同问题**：

| 问题 | 含义 | 应对 |
|---|---|---|
| 429 限流 | **你**提交太快 | 提交间隔 ≥70 秒 |
| **429 `rate limit for free users`** | **免费用户身份**受速率限制 | 退避；**升级付费才解** |
| **503 `queue is full`** | **服务端整个队列塞满** | **指数退避重试**（60→120→240→300s） |

**但更重要的是：先量它的「实际可用性」，别假设它可用。**

🔴 **2026-10-06 实测（12 次提交，间隔 45 秒）**：

```
成功率 1/12 = 8%      总耗时 506 秒才拿到 1 次入队
```

- 🔴 **不要沿用「成功率约 1/3」的旧估计** —— 实测是 **8%**。
- 两种拒绝混在一起：**429（免费用户限速）** 与 **503（队列满）**，含义不同。
- → **「每天 500 秒」这类额度可能是纸面的**：理论值 100 条 5 秒片段，
  按 8% 成功率要约 1250 次提交才跑得完 → **兑不出来**。
- → **免费档不能当按需产能**，只能「空闲时蹲」。排产必须按**实测成功率**算，不能按标称额度算。
- ⚠️ 有些模型的「免费」是**身份标签**而非独立额度：实测 `agnes-video-v2.0` 计费为 $0，
  但第二次调用即报 `rate limit for free users` → **它和免费档共用限流池**。
- 🔴 **「免费」还要连「账户状态」一起测**（2026-10-06 第二组探测）：
  `-flash` 对**已充值账户**成功的唯一那条，**账户被扣了 $0.125**
  （= 720P 完整版价，时间戳与扣费窗口完全吻合），且产物 URL 路径是
  `videos/agnes-video-2.5/…`（**不是 flash**）。
  → 疑似「免费额度耗尽后自动转标准价」或「对充值账户本就不免费」。
  → ⚠️ 仅 1 次观测（成功率 8%，难重复取证）→ 标"高怀疑、待复核"。
  → 对比：**同一天 `v2.0` 4 次成功全部 $0.0000**。
- 🔴 **可选：把「免费档可用性」做成一个专门的 probe 脚本**（`agnes_flash_probe.py`），
  因为它**不花钱**、可以长时间蹲，最适合在开工前跑一次摸当前时段的水温。
  **同一时段不同模型的结果可能天差地别**（本次：Flash 8% vs v2.0 50%）。

**顺手记两条环境坑**：
- 用 `nohup ... &` 起的长任务在工具环境里**会被回收**（日志停在某一刻不再更新）
  → 用工具原生的后台机制，并把日志实时落盘
- Python 输出到管道会**块缓冲**，看不到中间进度 → 加 `-u` 或 `flush=True`
  （**尤其别把后台任务 `| tail -N`**，tail 要等管道结束才输出，你会以为卡住了）

### ★★ 异步任务的生命周期纪律（钱最容易在这里白花）

把「提交」和「轮询」当**两件不同的事**处理 —— 它们的失败代价完全不同：

| 阶段 | 失败后果 | 正确策略 |
|---|---|---|
| **提交**（创建任务） | **任务未创建 = 未扣费** | ✅ **放心重试**（429/5xx/代理页都退避重试） |
| **轮询/下载** | **任务已创建 = 已计费** | ❌ **绝不能重新提交**（会二次扣费）<br>✅ 只能**退避重试查询**，退到成功为止 |

**三条硬要求**：

1. **提交重试**：退避序列 `60→120→240→300s`，默认 4 次
2. **轮询容错**：查询失败**不退出**，加大间隔继续轮询到 `max_wait`
   （实测一次 429 就把「已计费的片子」丢了 —— 钱花了、片子没拿到）
3. **`--resume <task_id>` 续取能力**：任务已创建但本地没拿到结果时，
   用 id 把片子捞回来。**不重新提交、不二次扣费**
   → 进程被 kill、终端断线、轮询超时，都靠它救

> 🔴 **实测教训**：默认轮询间隔 2 秒 → 直接 `429 too many video status queries`，
> 而**任务已经创建并计费**。当时没有 `--resume`，只能手写 curl 去捞。
> **官方文档建议的轮询间隔不可信**（Agnes 文档说 1–2 秒，实测 2 秒必被拒）——
> 实测值：**≥10 秒**才稳。
>
> **另一个坑：本地记账字段绝不能混进请求体。**
> 为了算准报价，我给 `videos[]` 加了本地字段 `_duration`，服务端直接 400：
> `videos[0]._duration is not an allowed field`。
> → 发请求前**剥离下划线开头的字段**，并加回归断言。

### ⚠️ reference / keyframe 模式的素材：先试 `data:` URI，可能免托管

**官方多半没有上传接口**（Agnes 实测 `POST /v1/files` → 400；`/uploads`、`/assets`、`/media` 全 404）。
文档会写「所有素材必须是**公网可直接访问的 URL**」。
→ 于是很容易得出「必须自建对象存储/CDN，这是独立前置工程」的结论。

#### ✅ 但对有些服务，`data:` URI 就是「上传接口」

**2026-10-06 实测（Agnes）**：传 `data:image/png;base64,<1×1 图>` 后，服务端报的是：

```
HTTP 400: input image side length must be between 256 and 5760 pixels
```

🔴 **注意它在说什么**：不是「URL 无法访问」，而是「**图太小**」——
说明服务端**已经解析了 data URI 并把内容当图片处理**了。

→ **结论：本地文件可直送，无需托管。**（图片每边须在 **256–5760 px**，太小会被拒。）

**这是评估清单里该加的一步**：
```bash
# 用一张「尺寸违规」的小图探路：若报错是「尺寸/内容」类，说明 data: 被接受
# 若报错是「URL 不可达 / 无法下载」，说明只支持公网 URL
```
- ✅ 免托管的额外好处：**素材不出公网**（合规上更干净），且上线周期短很多
- 客户端应实现「**本地文件路径自动转 data URI**」（本项目已做，并加了自检回归）
- ⚠️ 仍然要**公网托管方案作为兜底**：大视频文件不适合塞进请求体

## 七·补、★ 产品类广告实战：用「免费出图」锚定付费视频的一致性

**场景**：6 镜 × 5 秒的产品广告（车 / 数码 / 家电…），最怕**每个镜头长得不像同一个产品**。
提示词复读挡不住这个问题 —— 生成模型每次都会重新"设计"产品。

**已验证的做法（2026-10-06，一条 30 秒 2K 汽车广告，6/6 镜一致）**：

```
① 用【免费的】图像模型出一张「产品基准图」
   （Agnes 实测：agnes-image-2.5-flash，2K → 2624×1472，$0.0000，17–21 秒）
        ↓
② 把这张图作为【所有镜头的共同参考图】
   → 全部镜头统一走 reference 模式，ref 图 = 同一张基准图
        ↓
③ 提示词里对产品的描述（写成常量逐字复用）保持不变，
   每个镜头只改「场景 / 镜头运动 / 光线」
```

**收益**：出图环节 **$0**，却把付费视频的一致性从**"抽卡"变成"锚定"**。

### 配套纪律

- 🔴 **首图要先验收再拿去锚定**：模型常会硬画一个**乱码状"Logo/车标/文字"**。
  实测首版基准图就画出了一团乱码车标 → **重做一次**（明确要求 *plain featureless body panels,
  no emblem, no badge, no logo, no license plate, no text*）才可用。
  → 花一次免费重做，避免后面每条付费片段都带着这个瑕疵。
- 🔴 **`reference` 模式的参考图必须是 `http(s)` URL** —— 但客户端 `validate()` 与
  `as_media_url()` **自相矛盾**（后者声称支持 `data:`）。见 §六 的「data: URI」一节。
  **绕行**：基准图本身就是该平台生成的、**自带公网 URL** → 直接把这个 URL 回传即可，
  **完全不需要对象存储**。这是最省事的一条路。
- ✅ **不要用会画手的镜头**：手部是重灾区（实测第 4 镜方向盘上的手严重畸形）。
  改成"掠过仪表台 + 只有驾驶员剪影 + 明确 *no hands and no arms are visible*"后一次通过。
  → 产品广告里尽量**用产品本身和光来讲故事，少让人出镜**。

## 七·补·2、云端片段下载与拼装的 6 个坑（2026-10-06 实拍踩全）

### 1. 🔴 图片下载**不能**复用视频下载函数

视频下载按 `<code>ftyp</code>` 魔数校验 → **PNG/JPEG 永远过不了**，
会把"下载成功"误报成"代理兜底成网页"。
→ 写**独立的**下载函数，按 **图片魔数（`\x89PNG`/`\xFF\xD8\xFF`/`RIFF`）+ 视频魔数（`ftyp`）** 双判。

### 2. 🔴 **不要在下载进行中检查文件大小并据此下结论**（我犯过）

实测看到某片段只有 1.05 MB（同批其他是 6–8 MB），`ffmpeg` 解码报 `partial file`，
于是判定"下载被截断"。**实际那只是下载途中的中间态** —— 最终 8.33 MB、解码无误。

> **教训**：文件写入是**过程**，不是**事件**。
> 这与「单次观测当硬事实」是**同一类错误的复发** —— 纪律写进清单还不够，要盯执行。

**要校验完整性，就等进程结束后用解码器验**：
```bash
# ✅ 正确：ffmpeg 全解码一遍（比查大小可靠）
ffmpeg -v error -i clip.mp4 -f null - 2>&1 | head    # 无输出 = 完整
```
> 🔴 **`-f null` 是 ffmpeg 的 muxer，ffprobe 没有**。
> 用 `ffprobe -f null` 会报 `Unknown input format: null` 并**把所有文件判为不完整**（自伤 bug）。

### 3. ⚠️ 产物 URL 一定要**存下来**（写进日志）

任务一旦完成就**已计费**。存下 URL 意味着下载环节出问题时可以 `--refetch` **免费重取**，
不必重新生成。→ 客户端应把响应原文落盘（`--save-json`），别只留本地文件。

### 4. 🔴 音频链里**不要**放 `loudnorm`（单遍精度不够且会顶爆真峰值）

实测数据：

| 做法 | 结果 |
|---|---|
| 滤镜链内单遍 `loudnorm=I=-14:TP=-1.5` | 落 **-11.99 LUFS**（差 2 dB）；**真峰值被顶到 -1.33**（源 -3.30） |
| **两遍法**：先测 → 再带 `measured_*` + `linear=true` | **-13.85 LUFS / TP -2.25** ✅ |

```bash
# 第 1 遍：只测（读 input_i / input_tp / input_lra / input_thresh）
ffmpeg -v info -i bgm.flac -af "loudnorm=I=-14:TP=-1.5:LRA=11:print_format=json" -f null - 2>&1 | sed -n '/{/,/}/p'
# 第 2 遍：带测量值线性归一化 → 输出【无损】母带（不增加有损编码次数）
ffmpeg -y -i bgm.flac -af "loudnorm=I=-14:TP=-1.5:LRA=11:measured_I=<..>:measured_TP=<..>:\
measured_LRA=<..>:measured_thresh=<..>:offset=<..>:linear=true" -c:a flac bgm_master.flac
# 拼装链里只留 纯音量 + 淡入淡出
```
→ **纪律**：归一化在**无损母带**上做完，**拼装链内只做纯增益**。
→ 本机 ffmpeg 五条里的「`loudnorm` 会升采样率到 192 kHz」是**另一条**坑，两者都要防：
  音频链末端仍需 `aformat=sample_rates=48000:channel_layouts=stereo` + 输出 `-ar 48000 -ac 2`。

### 5. ⚠️ 音乐模型（ACE-Step 等）出片后**必测 TP / LRA**

提示词给的"驱动感 / 爆发感"越强，越容易**顶爆**。
实测首版配乐 `input_tp = +0.55 dBTP`（**已削顶失真**，频谱表现为一片高频竖纹），
且 0–6 秒近无声后骤然切入（LRA 17.5）→ 不可用。
换 hybrid orchestral 取向的 take：`TP -3.30 / LRA 10.7`，且有"弱起→铺垫→20s 推起"乐句结构 → 采用。

> **纪律**：**生成多版择优**，选之前先看 `input_tp`（要 < -1）与 `input_lra`（< 15 更稳），
> 再看频谱有没有整段饱和的竖纹。**别只听"感觉够燃"就上片。**

### 6. ✅ 拼装凑整：让交叉溶解吸收误差

若片段时长是 5.1667s（124 帧 @24fps），6 段想要正好 30.00s：
```
6 × 5.1667 − 5 × d = 30.00   →   d = 0.2 s
```
→ **用交叉溶解时长把总长"配平"到目标值**，比先拼完再裁切好（不丢内容、不加一次编码）。

## 七·补·3、★ 本地模型接入（ComfyUI 路线）：与云端完全不同的四个坑

> 首次落地：**2026-10-07 MiniMax H3 评估**（33B dense，含 Qwen3-VL-32B 文本编码器，
> 模型总量 42.46GB）。报告 `config\H3接入评估报告-2026-10-07.html`，脚本 `scripts\ops_h3_bench.py`。
>
> 🔴 **本技能前七节讲的全是云端 API** —— 那套纪律（key 有效性、计费公式、排队、
> 代理漂移）在本地路线上**一条都用不上**。本地路线的坑是另外四个，见下。

### 坑 1（最重要）：内存/提交类数据**必须同环境重测**，不能拿旧基线比

**实测踩到**：Wan2.2 基线先在**未清场**环境测了一次，之后项目推进、用户清场，
再测 H3 —— 拿两组数一比，H3 的 "内存多占" 是假的，因为基线本身被其他程序抬高了。

| | 物理内存峰值 | 提交峰值 |
|---|---|---|
| WAN-BASE（**清场前**，22:46） | 25.37 GB | 68.34 GB |
| WAN-BASE（**清场后**，00:01 重测） | **16.29 GB** | **45.06 GB** |

→ 差距 **23.28GB**，与我们实测的"清场能释放 22.43GB 提交内存"完全吻合。
→ ✅ **两次样片文件字节数完全相同（341,373）** —— 证明清场只影响内存与速度、**不影响画质**，
   所以重测是**公平的**，不需要担心画面变了。

🔴 **纪律：凡是要对比"谁更吃内存"，两边必须在同一环境状态下测。**
   环境状态（常驻程序、ComfyUI 是否已加载模型）写进报告，否则数字不可比。

### 坑 2：Windows 上判「内存够不够」，看的是 **commit charge**，不是页面文件占用

用 `GlobalMemoryStatusEx` 的 `ullTotalPageFile` / `ullAvailPageFile`：

```
提交上限 = 物理内存 + 页面文件      （本机：31.79 + 42.5 ≈ 74.30 GB）
已提交   = 上限 − 可用              ← 这才是"内存够不够"的真判据
```

🔴 **常见误读（我犯过）**：把这个差值写成「页面文件物理占用」。
   它不是 —— 它是**已提交量（commit charge）**，只有逼近上限才真正触发大量换页。
   字段名一律用 `commit_gb`，别用 `pagefile_gb`。

**本机的真实约束**（16GB 显存 + 32GB 单通道内存）：
- 显存是第一瓶颈：H3 各档实测占 16GB 的 **97–98%**（15.5–15.7GB）
- 内存是第二瓶颈：H3 内存峰值 29.56GB **逼近 31.79GB 物理上限**
  → 模型放不进物理内存，全程在 NVMe 页面文件上倒腾（3–7 GB/s vs 双通道 83 GB/s）
- → 🔴 **「提交没爆」≠「跑得舒服」**：本项目 H3 提交峰值 58.13GB < 74.30GB 上限、
  **没爆**，但代价是 3 秒片子要跑 175s（turbo）/ 329.5s（20步）。
  **判"能不能上产线"要同时看"没爆"和"耗时能不能接受"两个条件。**

### 坑 3：ComfyUI 的 `filename_prefix` 带 `/` → 会被当成 subfolder（路径多一层）

```python
OUT_DIR = r"D:/AI-VIDEO/output/h3bench"     # 已经是输出根 + 子目录
prefix  = f"h3bench/{name}_{stamp}"          # 这里又带了一次 "h3bench/"
# → ComfyUI 输出到 <输出根>/h3bench/xxx
#   /history 返回 {filename: xxx, subfolder: "h3bench"}
# 若再拿 OUT_DIR 去拼 subfolder → D:/AI-VIDEO/output/h3bench/h3bench/xxx  ❌ 多一层
```

✅ **正确做法**：以 **ComfyUI 的输出根**（通常是 ComfyUI 目录下的 `output/`，
   本项目重定向到 `D:/AI-VIDEO/output`）为基准拼 `subfolder + filename`，
   **并做存在性校验 + 兜底递归查找**，别只靠拼接：

```python
def resolve_output(subfolder, filename):
    primary = os.path.join(COMFY_OUT_ROOT, subfolder or "", filename)
    if os.path.exists(primary): return primary
    for root, _d, files in os.walk(COMFY_OUT_ROOT):      # 兜底
        if filename in files: return os.path.join(root, filename)
    return primary
```

> ⚠️ 同一个脚本里"记录路径"和"实际落点"不一致，会污染所有历史 JSON。改完记得**批量回填**。

### 坑 4：帧数/尺寸约束**必须查官方 blueprint**，别照抄另一个模型的参数

H3 的硬约束是 **帧数 n ≡ 5 (mod 17)**（官方 blueprint 里的 ComfyMathExpression）：
`n = max(5, round(秒×24)) + (5 − 该值 % 17) % 17` → 2s=56、3s=73、5s=124 帧。

🔴 **我踩到的**：做"同分辨率对照"时，为了跟 Wan 对齐，`length` 直接照抄了 Wan 的 **72** ——
   但 `72 % 17 = 4`，**不满足 H3 约束**。正确值是 73（差 1 帧，可视为等价对照）。

**H3 与 Wan/SD 体系的另外两处结构差异**（迁移工作流时必踩）：
- **H3 没有负面提示词输入**（`MiniMaxH3ImageToVideo` 只有 `prompt`）
- **H3 输出是"整包"**：`SamplerCustomAdvanced` 的 **slot0 output**（不是 `denoised_output`）
  同时喂 `VAEDecode` 和 `VAEDecodeAudio` → `CreateVideo(fps=24)` → `SaveVideo`

> ✅ **通用做法：新模型的约束一律从「官方 blueprint / 节点源码」里读，不从别的模型类推。**
>   ComfyUI 0.38.0+ 已原生内置 H3（`comfy/ldm/minimax`、`comfy/text_encoders/minimax.py`），
>   不需要自定义节点 —— 先查有没有原生支持，再考虑自己接。

### 本地路线必做的三条验收（替代云端那套 key/计费检查）

1. **链路预检**：用假模型名（`__NO_SUCH_FILE__.safetensors`）提交一次。
   HTTP 400 只报 `value_not_in_list` → 说明**节点类型/参数名/连线全部正确**，只是文件没下载。**零成本**。
2. **"有音轨" ≠ "有声音"**：用 `ffmpeg -af astats` 验能量与变化。
   🔴 **关键判据 `Flat factor`**：纯静音/直流会显著非零；**0.000 = 真有内容**。
   再比左右声道是否不同（判真立体声 vs 单声道复制）。实测：H3 Peak −3.9～−17.6 dB /
   RMS −14～−34 dB / Flat 0.000，随画面内容浮动 → 真音频。
3. **画质必须导出帧目视**：`ffmpeg -vf "select='eq(n\,0)+eq(n\,24)+eq(n\,48)',scale=W:H,tile=3x1"` 拼 contact sheet。
   🔴 与云端那一节同样的教训：**客观指标不可靠，别用它排"哪档更好"**。

### ⚠️ 评估"值不值得接"时，先分清**结构性能力**与**性能差异**

H3 vs Wan2.2 的实测结论（清场环境，同 prompt 同 seed）：

| | WAN-BASE | H3-SAMERES（同尺寸同长度） |
|---|---|---|
| s/帧 | 0.976 | 1.210（**慢 25.6%**） |
| 内存峰值 | 16.29 GB | 25.13 GB |
| 音轨 | ❌ 无（`nb_streams=1`） | ✅ 32kHz 立体声 |

→ 🔴 **结论不是"谁更快"，而是**：H3 慢 25.6% 是**性能差异**（会随优化缩小），
   而"一次生成同时出画面 + 声音"是**结构性能力**（Wan 体系补不上，只能靠 TTS+对口型+贴音效另做）。
   **接不接取决于后者能不能省掉你一整条链路，不是前者。**
→ 但也要给出**代价**：H3 显存贴顶 15.5–15.7GB/16GB → 接进来之后 16GB 卡**没有余量**。

> 🔴 **别把"更好的做同一件事"和"做别人做不了的事"混为一谈。**
> 前者是替换（要赢在性能），后者是补位（只要够用就行）。

## 七·补·4、★★ 本地接入的「崩溃级」三个坑（2026-10-08 Kandinsky 6 Lite 实测定案）

> 三个坑都是**实测踩出来的**，且都是「不做就白跑一次试跑」的量级。

### 坑 A（最狠）：32GB 内存机器上 ComfyUI 的**两个默认值**会把进程压死

**症状**：进程**直接崩死**，不是普通报错 ——

```
Windows fatal exception: access violation
  File "comfy\utils.py", line 1230 in tiled_scale_multidim
```

🔴 **定位关键**：**同样的节点、同样的参数，在单独探针里能跑成功**。
→ 既然代码路径没问题，就**一定是运行时资源状态问题**，别再怀疑节点写法。

**根因**（两个默认值叠加，32GB 机器上是病态的）：

| 默认行为 | 问题 |
|---|---|
| 启用 pinned memory（本机 13022 MB） | 12.7GB「**不可换出**」物理内存被锁死（占 40%） |
| `RAM pressure cache` 非活跃阈值 = **系统内存 100%** | 把全部权重常驻内存 → 页面文件吃爆 → 提交内存见底 |

**修复**（已验证有效，重启实例时加）：

```
--disable-pinned-memory --cache-ram 2 4
```

**判据**：崩溃时**提交内存峰值 / 上限** 已到 80.94/85.3 GB（余量 < 5GB）。
🔴 **信号**：若某实例「提交内存很大但工作集很小」（实测 27.5GB 提交 / 0.61GB 工作集 → 基本闲置），
说明它占着巨额提交额度却没用，**这就是内存被榨干的第一嫌疑对象**。

⚠️ **修完仍要复核余量**：本次修完提交内存峰值 83.43/85.3 GB，余量仍不足 2GB
→ **结论：不要与其它重型模型挂在同一个 ComfyUI 里跑。**

### 坑 B：模型目录**硬编码**时不能靠 `extra_model_paths`，且 Windows 联接**必须用 PowerShell**

想放外置盘就得建**目录联接**：

```powershell
New-Item -ItemType Junction -Path "D:\AI-VIDEO\ComfyUI\models\audio_vae" `
         -Target "D:\AI-VIDEO\models\audio_vae"
```

🔴 **别用 Git Bash 的 `cmd //c mklink /J`** —— MSYS 路径转换会把 `/J` 吃掉，
报「参数格式不正确 - "D:"」。**必须用 PowerShell 执行**。

🔴 **COMBO 兜底陷阱**：有些扩展在目录为空时**回退成硬编码默认值**，
所以 `/object_info` 里能看到 `["v1-44.pth"]` 这类值，**不代表文件真的存在**。
→ 验收要看**实际加载**（接一个消费端），不能只看 `/object_info`。

### 坑 C：16GB 卡上**解码方式**能差 17 倍，且必须验「不掉帧」

| 解码节点 | 耗时 | 显存峰值 |
|---|---|---|
| `VAEDecode`（整块） | **427.8 s** | 15.6 GB |
| `VAEDecodeTiled`（分块） | **25.1 s** | 8.7 GB |

🔴 **官方模板常按 24GB / 专业卡写整块解码，16GB 卡照抄会白等 6 分钟。**
🔴 换完必须**验不掉帧**：把两种方式的产物逐字段比对（分辨率/帧率/帧数/时长），
本机实测完全一致 → 确认只提速、不掉帧。

### ★ 新增第 4 条本地验收：**用 ASR 回读验证"音频能不能听懂"**

比 `astats` 强一档。摘音频丢给 whisper，与 prompt 里写的台词**逐字比对**：

```bash
ffmpeg -v error -y -i out.mp4 -ac 1 -ar 16000 a.wav
whisper a.wav --model small --language en --output_format txt --output_dir .
# 本机实测：转写结果与 prompt 的 <S>...</S> 台词一字不差
```

**副产品（很有用的排产视角）**：对比 6 步与 50 步两版转写 —— **完全相同**。
→ **音频收敛远快于画面**：音频轨可低成本先定稿，算力花在画面步数上。

### ★ 试跑必须**两阶段**，且要能检测「进程被打死」

1. **先 6 步冒烟 → 再 50 步正式**。
   因为「`node_errors=0` 结构校验通过」**≠**「能跑通」，首次加载权重/采样器仍可能运行时炸。
2. 🔴 **崩溃检测用「进程失联」判据**：被致命异常打死时 `/history` **永远不会给结果**，
   轮询脚本会一直空等到超时（本次白等了 10 分钟）。
   → 循环里必须加：`if elapsed > 30 and not alive(): 判定崩溃`。

### ★ 显存测量必须**双口径** + **全新实例**

- 常驻其它程序（本机 1.3~4.3GB）会被算进 `vram_total - vram_free` → 必须同时报
  **绝对峰值**与**相对运行前基线的增量**。
- 旧探针实例里残留已加载模型 → 峰值测虚高 → **测显存必须新起干净实例**。

### ★★ attention 后端选型：本机最省事的提速杠杆（2026-10-08 实测定案）

**结论先行**：ComfyUI 默认走 `pytorch attention`（SDPA eager）。换 `--use-ck-attention` **零安装成本**，
本次实测**采样提速 29.9%、显存增量降 32.8%、画质与音频无损**。

本机可用后端判定（**别凭启动日志的 triton 行下结论**）：

```bash
# 三个后端互相独立，triton 不可用 ≠ comfy-kitchen 不可用
C:/Users/Administrator/.workbuddy-ai/binaries/python/versions/3.13.12/python.exe -c \
  "import comfy_kitchen as ck; print('int8 attn:', ck.int8_attention_is_available())"
```

| 开关 | 依赖 | 本机状态 |
|---|---|---|
| （默认）pytorch attention | 无 | ✅ 基线 |
| `--use-ck-attention` | comfy-kitchen 自带预编译扩展 | ✅ **可用（本机实测 True）** |
| `--use-sage-attention` | 单独装 sageattention wheel | ⛔ 不必装（见下） |
| `--enable-triton-backend` | triton | ❌ 未装 |

🔴 **别装 SageAttention wheel** —— SageAttention 作者官方 README 明写：
> If you're using ComfyUI, you no longer need to install my SageAttention wheel.
> You can use the SageAttention in comfy-kitchen. When launching ComfyUI, add
> `--use-ck-attention` rather than `--use-sage-attention`.

且官方称 **CUDA minor 版本（12.8/12.9）不同没关系**，故本机 cu126 无需升级。
（旁证：`woct0rdho/SageAttention` 的 Windows wheel 只有 cu128/cu130、**无 cu126**，
硬装会引入版本冲突风险 —— 而 `--use-ck-attention` 已经免费拿到同样的 INT8 注意力。）

### 下载完整性：别用「字节数对得上」判断完成

用远端权威哈希。HF 取哈希：

```bash
curl -s "https://hf-mirror.com/api/models/{repo}/tree/main?recursive=true" \
  | python -c "import sys,json;[print(i['path'], (i.get('lfs') or {}).get('oid')) for i in json.load(sys.stdin)]"
# items[].lfs.oid 即 sha256
```

非 LFS 小文件用 **git blob SHA1**（`sha1(b'blob %d\0' % len + bytes)`）跨平台精确比对。
🔴 **`curl` 取 HF 文件必须带 `-L`**，否则拿到 307 跳转文本，会被误判成「文件损坏」（我犯过）。

#### ✅ 已沉淀可复用工具 `scripts/fetch_hf_model.py`（2026-10-08）

**不要**在下载脚本里写 `if [ -s "$dest" ]` / `if [ -f "$dest" ]` 判完成 —— 前者把**残缺文件**当完成跳过，后者连 **0 字节**都跳过。后果是下载中断后重跑，坏文件被静默当已完成，直到运行时才炸，且报错常指向别处，极难定位。

判据表（严格，核心是「**内容与远端一致**」= 字节数 + sha256）：

| 本地状态 | 动作 |
|---|---|
| 不存在 | `fresh` |
| size < 期望 | `resume`（`curl -C -`） |
| size > 期望 | `redownload`（多余字节必然损坏） |
| size == 期望 且 sha256 匹配 | `skip` |
| size == 期望 但 sha256 不符 | `redownload`（**尺寸对不代表内容对**） |
| 无 sha256 可用 | 退化为仅尺寸判据 + **明确告警** |

**验证证据**（单元 7/7 分支 + 正向端到端 + 三组负向对照，全部实测）：

```
对照 A  100MB 残片（模拟下载中断）
  旧判据 [ -s ]      -> [SKIP] 静默跳过        ❌ 缺陷复现
  新工具             -> resume（缺 0.13 GB）   ✅ 拒绝，退出码 1
对照 B  尺寸完全相等 246144152 B，内容错（最难抓）
  旧「尺寸判据」     -> [SKIP] 放行            ❌
  新工具             -> redownload（sha256 不符）✅ 拒绝
对照 C  正确完整文件 -> skip（sha256 匹配）    ✅ 通过
```

用法：

```bash
# 单文件
python scripts/fetch_hf_model.py --repo <repo> --file <远端路径> --dest <本地路径> [--verify-only]
# 批量（manifest JSON：{"mirror":..., "files":[{"repo","file","dest"}]}）
python scripts/fetch_hf_model.py --manifest scripts/k6_lite_manifest.json
```

⚠️ 脚本内用 `build_opener(ProxyHandler({}))` **显式禁代理**，行为对齐 `curl --noproxy '*'`（hf-mirror 在本机必须直连）。
⚠️ sha256 一律从 HF API 的 `items[].lfs.oid` **实读**，不要凭记忆填。
