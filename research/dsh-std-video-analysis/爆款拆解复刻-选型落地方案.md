# 「爆款视频拆解 → 爆款视频复刻」选型 + 落地方案

> 版本：v1　2026-08-25　背景：已完成头条 DSH 视频《dsh-std 协定》全量拆解（含下载/OCR/转写/结构还原），并完成一轮 find-skills 检索（本地 + 项目注册表 + ClawHub/GitHub 市场）

---

## 一、总体思路评估：两步走能否跑通

**结论：能跑通，方法论正确，且与行业最佳实践一致。** 「先拆解、后复刻」是爆款内容操作的正确顺序——现有的成熟技能（如 `guozhi-video-breakdown`）本质上就是把这两步做进同一个 skill。但"能跑通"有三个前提条件，缺一个就会变成"看起来在跑、实际产出废品"：

1. **必须有视频候选输入源**（第零环）：拆解环节的输入是"值得分析的视频"。没有稳定的候选池（谁来分析？分析什么？），拆解无法量产。现有 `monitor_skill`（对标监控）面向公众号选题池，需要扩展出"视频候选"这一路。
2. **拆解必须带"验证层"**（最重要的改造点）：不是所有视频都配叫"爆款"。我们刚拆的那条 dsh-std 视频**播放 78、评论 0，至今不是爆款**。如果拆解环节不去验证"这条到底爆没爆、在作者什么水平、有没有起量趋势"，复刻环节就会去复制一条**从未被市场验证的内容**——这是整条链路最大的失败模式。
3. **需要一个反馈闭环**（第五环）：复刻 → 发布 → 数据 → 回灌校准"拆解的爆款判断"。没有闭环，拆解模型永远是拍脑袋。

因此我建议把"两步走"扩成**五环**，但核心权重仍然押在用户判断的那个环节——拆解：

```
┌─────────────────────────────────────────────────────────┐
│  环0 候选池  环1 拆解  环2 复刻  环3 发布  环4 数据回灌 │
│  监控/收链  ★核心前提  ←读拆解报告→   收集表现  →校准拆解│
└─────────────────────────────────────────────────────────┘
```

**对用户判断的回应**：你认为关键点在"拆解"、它是复刻的前提——**这个判断是对的**。第 2 节专门展开论证为什么对、以及拆解环节应该怎么设计才配得上"前提"这两个字。

## 二、重点论证：为什么拆解是前提，以及拆解环节怎么设计

### 2.1 为什么拆解是复刻的前提

复刻的本质不是"抄"，而是**迁移机制、替换表达**：

- 机制（mechanism）= 这条视频**为什么**有效：命中了谁的情绪、靠什么信息差、用什么结构留住人、拿什么证据建立信任、引导了什么动作。机制可以迁移到你的账号、你的选题、你的表达。
- 表达（expression）= 这条视频**长什么样**：具体措辞、封面图、截图、人设、声音、水印。表达不能抄（原创度/平台风控/版权），也没必要抄。

**机制只能靠拆解提取，无法靠"看一遍"获得。** 不拆解就直接复刻，结果只有两种：要么抄表面（抄开头、抄标题、抄句式）——产出的就是低质搬运，既不像自己、也过不了原创审核；要么凭感觉自由发挥——和爆款没有因果关系，等于盲写。

所以拆解环节的产出，就是复刻环节的**输入契约**。拆解报告里每一行（人群/情绪引擎/钩子/结构骨架/留存节点/信任证明/转化设计/复刻边界），复刻环节都要逐项消费。**拆解得越浅，复刻就越假。**

### 2.2 拆解环节的五层设计（这是本方案的核心）

一个合格的"爆款拆解"必须分层，且**每层证据强度不同，不能混着说**：

| 层 | 干什么 | 证据来源 | 判断强度 |
|---|---|---|---|
| L1 证据层 | 拿到视频本体：下载、抽帧、contact sheet、OCR 画面文字、Whisper 转写旁白、封面/标题/评论 | 视频文件、平台元数据 | 客观事实（最高） |
| L2 结构层 | 还原时间线：分段、脚本骨架、标题/封面公式、开场钩子、每段功能 | L1 产物 | 事实+轻推断 |
| L3 机制层 | 解释为什么有效：目标人群、情绪引擎、信息差、信任背书、留存设计、转化设计 | L1+L2 + 推理 | **推断（必须标注）** |
| L4 验证层 | 问"它到底是不是爆款"：播放/互动绝对值、作者中位数基线、起量趋势、评论信号 | 平台数据 | 客观数据门（新增） |
| L5 产出层 | 输出标准化拆解报告 → 作为复刻环节的输入契约 | L2+L3+L4 | 可复用模板 |

**L4 是现有所有技能都缺、而我们这个场景绝不能缺的一层**，理由：
- 伪爆款陷阱：把"没爆的视频"当爆款拆 → 复刻出一个没被验证过的东西。dsh-std 这条就是活例子。
- 判断爆款不能看单个绝对值，要看**相对基线**：作者 2690 条视频的中位数播放是多少？这条是高于还是低于他的常态？平台给没给推荐位（bizTag=中视频、是否进热点）？
- 验证层的数据可直接复用项目现有的采集脚本（`collect_xhs_recent_metrics.py`、`web_scraper_mcp`）做扩展，不需要从零搭。

**L3 的诚实性原则**：机制是推断，不是事实。拆解报告必须把"可观察证据"和"推断出的机制"分栏，并禁止把臆测写成确定结论（防止幻觉式解释）。现有 `guozhi` 技能的 "Evidence to Cite" 列设计就是这个思路，值得沿用。

### 2.3 现有技能对照（选型依据）

| 候选 | 生态 | 强项 | 缺口（对我们场景） |
|---|---|---|---|
| **guozhi-video-breakdown**（GitHub，MIT） | Codex（可迁移 Claude） | 证据优先；10 维拆解表（每维带"证据+复刻问题"）；黄金3秒四层分析；分段图；拉片维度；底层公式；**复刻边界规则**；输出模板完整 | 面向**口播短视频**（小红书/抖音）；无 L4 验证层；无选题时效性/信息差判断；无图文TTS形态专属维度；Codex 格式需迁移 |
| **video-deconstruct**（ClawHub·jack-yang-ai） | OpenClaw/ClawHub 原生 | 「故事+心理学」叙事式拆解报告；结构=开头-中间-结尾；节奏/BGM/受众启示；契合你的 ClawHub 生态 | 偏**文案向报告**，证据链弱于 guozhi；无验证层；无视频下载/OCR/转写能力（假设你喂内容） |
| **viral-video-benchmark**（bozhouDev toolkit） | 通用 | 爆款基准/对标**监控**，偏持续性数据 | 不做单条深拆；用途与 monitor_skill 更像 |
| tiktok-agent-skills | 通用 | 电商运营向（选品/达人/字幕提取） | 领域不符 |
| viralmaxing / ViralVision / creator-research MCP | MCP | 短视频数据接入 | 可作**数据层**（喂 L4），非主流程 |

**选型判断**：方法论基座选 **guozhi-video-breakdown**——它的框架（证据优先 + 10 维拆解 + 复刻边界 + 输出模板）是现成里最完整、最接近"机制级拆解"的，且 MIT 可自由改造；它的证据提取链路（yt-dlp/ffmpeg/whisper）和我们已验证的头条链路同一思路，迁移成本低。ClawHub 的 video-deconstruct 作为**表达风格参考**（叙事式报告的写作手感），不重复引入。

### 2.4 我们领域（DSH 图文资讯视频）需要补的专属维度

现成技能都假设"口播短视频"。而 dsh-std 这条视频的真实形态是**图文解说型资讯视频**（白底幻灯片 + TTS 配音），必须补六个专属维度，拆解才算到位：

1. **选题时效性与信息增量**：这条为什么"现在"值得发？它抢的信息差是什么（新协定发布、社区大地震）？同题内容多不多？→ 决定"信息型爆款"的核心价值。
2. **图文TTS形态**：幻灯片节奏（本片每页 3–7 秒、一句话一屏）、每帧文字密度、画面是否低动态、TTS 语速/音色特征。→ 决定"能不能低成本量产"。
3. **资料来源可溯**：信息来自哪个仓库/spec/团队（本片：Yan-Zero 仓库、dsh-ecosystem-spec、dsh-TUI adapter）。→ 符合你的编辑铁律（仅平台可查数据标「数据来源」），也是资讯号的信任根基。
4. **信任构建逻辑**：不是口播的人设信任，而是"谁背书 + 开放哲学 + 不固化标准"的**中立专业感**。→ 复刻时必须复刻这层信任逻辑，而非背书对象。
5. **生产可行性评估**：这条我们用现有工具（TTS/幻灯片/合成）能不能 1 人复刻？成本多高？→ 拆解报告末尾加一栏，直接为复刻环节做 gating。
6. **转化路径差异**：资讯视频的 CTA 不是"关注/私信"，而是"仓库名/关键词/资料型收藏"（本片 2 个收藏印证资料价值）。→ 转化设计维度需要改写。

### 2.5 拆解正确性的保障（防三条暗坑）

- **防伪爆款**：L4 数据门，未过门的一律标"未验证爆款"，禁止进入复刻推荐。
- **防幻觉解释**：L1/L2 与 L3 分栏，机制标注为推断；"为什么会火"必须有证据支撑，无证据不下结论。
- **防样本偏差**：用**已知结果**的样本做校准——拿 5–10 条"真爆款 + 真扑街"视频跑拆解，验证拆解的爆款判断能否区分两者。这是衡量拆解环节是否"真的懂"的唯一硬标准。

## 三、选型结论

- **方法论基座**：`guozhi-video-breakdown`（迁移其 10 维拆解 + 复刻边界 + 输出模板到 Claude/OpenClaw 生态）。
- **表达参考**：ClawHub `video-deconstruct` 的叙事式报告手感。
- **数据层/候选池**：`viral-video-benchmark` 思路 + 项目现有 `monitor_skill` + `web_scraper_mcp` + 已验证的头条抓取链路。
- **自建（无现成，必须自己做）**：L4 验证层、DSH 图文资讯专属六维度、选题信息差判断、来源可溯。
- **不引入**：tiktok-agent-skills（电商向）、viralmaxing（仅作备选数据源）。

一句话：**不重复造轮子，但轮子必须加四根我们自己的辐条（验证层 + 资讯专属维度 + 信息差判断 + 来源可溯）。**

## 四、落地方案

### 4.1 目标架构（与现有管线对接）

```text
code-news/
├─ skills/viral-video-breakdown/          # 新 skill（拆解，v1）
│  ├─ SKILL.md                            # 主技能：证据→结构→机制→验证→产出
│  ├─ references/
│  │  ├─ evidence-extraction.md           # 头条/抖音/小红书 抓取+抽帧+OCR+转写
│  │  ├─ viral-autopsy-framework.md       # 10 维拆解 + 黄金3秒 + 分段图（移植自 guozhi）
│  │  ├─ info-video-dimensions.md         # 图文资讯专属六维度（自建）
│  │  ├─ validation-gate.md               # L4 数据门（自建）
│  │  └─ breakdown-output-template.md     # 拆解报告模板（L4 融合版）
│  └─ scripts/
│     └─ extract_video_evidence.py        # 一键抽证据（下载/抽帧/OCR/转写）
├─ skills/viral-video-replicate/          # 新 skill（复刻，v2 阶段）
│  ├─ SKILL.md                            # 读拆解报告 → 标题/旁白/分镜/素材/封面
│  └─ references/replicate-output-template.md
└─ scripts/                               # 复用现有：monitor_skill / web_scraper_mcp /
                                          #   collect_*_metrics / humanizer / cover
```

### 4.2 分阶段路线

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **Phase 0 候选池** | 扩展 monitor_skill：订阅 DSH/科技资讯视频源（头条标签、抖音/小红书话题、ClawHub/社区），产出"待拆解视频清单"（含链接+基础数据） | 每周能稳定产出 5–10 条候选 |
| **Phase 1 拆解 v1（骨架）** | 迁移 guozhi 框架 + 接入已验证头条抓取链路 → 跑通"给链接出拆解报告" | 对 dsh-std 这条视频能自动产出完整报告 |
| **Phase 2 拆解 v2（校准）** | 加 L4 验证层 + 资讯专属六维度；用 5–10 条已知结果样本校准"是否值得复刻"判断 | 拆解能区分真爆款与扑街（准确率>80%） |
| **Phase 3 复刻 v1** | 拆解报告 → 标题/旁白/分镜/素材清单/封面文案；对接 writer/humanizer/cover | 能产出可直接进生产线的脚本包 |
| **Phase 4 闭环** | 发布 → 采集表现 → 回灌校准拆解模型 | 拆解的"爆款预测"随数据迭代 |

### 4.3 交付形态

- 技能本体：SKILL.md + references + scripts（Claude/OpenClaw 兼容，参考现有 skills-lock.json 的锁版方式）。
- 执行入口：按你的偏好交付**双击 .bat**（纯 ASCII），一键跑"给定链接 → 出拆解报告"。
- 与现有 DSH 公众号专线共用信源监控与脚本素材，实现"一次调研、图文+视频多形态分发"。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 伪爆款：拆解了没爆的视频 | L4 数据门；未验证一律不推复刻 |
| 幻觉解释：机制是编的 | L1/L2 与 L3 分栏，机制强制标注"推断" |
| 平台风控/下载失败 | 复用已验证头条链路；遵循"不绕过登录墙/付费墙/平台限制"；降级走字幕/截图 |
| 原创度风险 | 复刻边界规则 + 你的编辑铁律（不露素材编号/仅平台可查数据标来源） |
| 拆解准确率低 | Phase 2 用已知结果样本校准；闭环回灌持续迭代 |
| 用户非技术向 | 全部封装成 .bat 双击 + 模板化报告，不需要碰命令行 |

## 六、需要你拍板的决策点

1. **基座选型**：确认以 `guozhi-video-breakdown` 为方法论基座（需先做一次 Codex→Claude 格式迁移评估）。
2. **候选池范围**：只做 DSH/科技资讯，还是扩大到泛科技视频？这决定 Phase 0 的监控范围与拆解维度的通用性。
3. **拆解输出形态**：报告先给"人看"（运营/编辑），还是直接给"管线吃"（进复刻环节）？建议先人后管，报告即是复刻输入契约。
4. **启动范围**：先做 Phase 1（一条视频跑通全流程）作为试点，还是直接按 Phase 0→4 全量铺？建议先试点，成本最低、最快看到真东西。
