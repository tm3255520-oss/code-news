# AI 接夜班主稿三平台成稿设计

日期：2026-06-15  
主题：`2026-06-05-ai-night-shift`  
范围：公众号 / 知乎 / 今日头条  
阶段边界：本轮只做 `生成 + 配图 + 预检 + 发布占位`，不做正式发布，不做发布后追踪

## 1. 背景

当前仓库已经完成了两步前置工作：

1. 用新的对标池重跑了对标监控、爆款分析和仿写方案。
2. 确认现有自动“生成”入口并不能直接产出成稿，只会写请求包。

这意味着下一步不能依赖现有自动生成脚本直接交付文章，而要采用“直接重写源文件，再跑三平台预检”的路径。

在四个候选题里，`AI 开始接夜班了：真正有用的，不是更会答，而是会自己跑流程` 最适合作为今天先落地的一篇，原因是：

1. 它最贴合第一阶段内容域：`AI工具 / 效率工具`。
2. 它有真实来源支撑，适合知乎、公众号、头条同时分发。
3. 它比纯资讯稿更能做出平台分化，也比纯复盘稿更少自说自话风险。

## 2. 目标

本设计只解决一个具体问题：把这 1 篇主稿做成一套三平台可预检、可确认、可继续发布的成稿包。

完成后要得到的不是“已经发出”，而是以下产物：

1. 一套统一事实底稿。
2. 三个平台各自分化后的标题、摘要、开头和正文节奏。
3. 一套非单一模板复用的封面与正文配图方案。
4. 三平台预检结果与发布占位载荷。

## 3. 非目标

本轮明确不做：

1. 不触发任何正式发布动作。
2. 不修改其他候选题的正文与载荷。
3. 不引入新的自动生成框架或新的发布器。
4. 不虚构案例、日期、功能状态或平台能力。
5. 不使用同一标题、同一开头、同一配图模板在三个平台平移复用。

## 4. 方案比较

### 4.1 方案 A：一篇主稿 + 三平台分化 + 预检通过后出占位包

优点：

1. 源文件只有一套事实底稿，后续维护最稳。
2. 平台差异集中在标题、摘要、开头和节奏层，重复发布风险最低。
3. 最符合当前 v3 阶段“先跑生成、配图、预检，不先正式发布”的边界。

缺点：

1. 需要同时维护 payload 和可读稿文件的一致性。
2. 需要在一篇底稿上做三平台差异化设计，执行上比“轻改后直接发”更细。

### 4.2 方案 B：三平台各写一篇独立稿

优点：

1. 平台适配最强。
2. 每个平台都可以写到最符合自己调性的程度。

缺点：

1. 维护成本高。
2. 同一主题容易写散，事实漂移风险更高。
3. 更容易触发同题重复和低差异发布问题。

### 4.3 方案 C：轻改现有稿，再直接跑预检

优点：

1. 最快。

缺点：

1. 提升幅度有限。
2. 解决不了当前最核心的问题：入口弱、结构像资讯复述、配图模板味重。

### 4.4 结论

采用方案 A。

1. 三平台预检结果
2. 三平台 payload
3. 发布占位状态

本轮不直接改发布脚本逻辑，除非预检时暴露出阻断性缺陷。

## 6. 统一事实底稿约束

三平台必须共用同一组事实，不允许平台化改写时改变以下内容：

1. Notion Custom Agents 的能力描述与时间点。
2. Slack Workflow Builder AI step 的能力描述与时间点。
3. OpenAI workspace agents 文档里关于 schedule、shared agents、write approvals 的能力描述。

统一结论也必须保持一致：

判断 AI 价值，不能只看它会不会回答，还要看它能不能稳定接住一条流程。

## 7. 三平台分化设计

原则：不是“一稿三发”，而是“同一事实底稿，三个不同入口”。

### 7.1 公众号

角色定位：深度主稿，写给已经在使用 AI、准备把 AI 接进日常工作的内容团队、运营和知识工作者。

写法约束：

1. 标题保留“AI 接夜班”这个强记忆点，但要把价值交代完整。
2. 开头前两段直接打掉“更会答 = 更有用”的误区。
3. 正文结构采用“趋势判断 -> 三个官方信号 -> 3 到 4 条判断标准”。
4. 读完必须能带走一套判断框架，而不是只记住产品新闻。

### 7.2 知乎

角色定位：判断型回答稿，写给想搞清楚 agent / workflow 为什么突然变重要的用户。

写法约束：

1. 标题更偏问题式或判断式，减少修辞。
2. 开头先下判断，再接一个真实工作场景，不先铺大背景。
3. 正文围绕“为什么会自己跑流程，比会回答更重要”展开。
4. 结尾必须补上边界：哪些任务适合交给 AI，哪些不适合。

### 7.3 今日头条

角色定位：强入口短决策稿，写给泛科技读者。

写法约束：

1. 标题优先突出“AI 接夜班”的动作感，压缩长度。
2. 首段直接给画面感，不做行业总述。
3. 正文只保留“趋势判断 + 3 个信号 + 1 个结论清单”。
4. 段落更短，首屏更快进入结果。

### 7.4 三平台共通硬规则

1. 不复用同一标题。
2. 不复用同一开头前两段。
3. 不夸大能力，不写“彻底替代人”“自动赚钱”“完全无人值守”等高风险表述。
4. 不把同一语句做微小改字后重复分发。

## 8. 配图与插图设计

本轮必须显式解决“历史插图长期单一模板复用”的问题。

### 8.1 设计原则

1. 配图不是装饰，而是帮助理解文章判断。
2. 同一篇里不同图要承担不同认知任务。
3. 不允许三张图都是同一种咨询卡片或同一种排版骨架。

### 8.2 本篇最少图像角色

至少做 3 类视觉角色：

1. 封面图  
   主题：夜班 / 值守 / 自动跑流程  
   目标：一眼看懂“AI 接夜班”的主隐喻

2. 正文图 1  
   主题：`会答` vs `会做`  
   目标：把聊天式 AI 和流程式 AI 的差别视觉化

3. 正文图 2  
   主题：触发 -> 执行 -> 回传  
   目标：把后台连续运行的流程结构画清楚

### 8.3 执行约束

1. 三张图至少使用两种不同版式骨架。
2. 封面图不能复用最近文章的固定咨询卡片风。
3. 正文图必须服务论证，不做泛装饰插画。

## 9. 预检标准

预检分两层：自动预检和人工门槛。两个都过，才进入发布占位。

### 9.1 自动预检

对接当前真实脚本：

1. 入口：`scripts/run_three_platform_pipeline.py --preflight-only`
2. 核心质检：`scripts/check_generated_article_quality.py`

当前硬门槛：

1. `score >= 80`
2. `failCount = 0`
3. 只要出现任意 `fail`，直接 `blocked`

当前会被自动拦截的主要问题：

1. 题材疲劳
2. 标题骨架重复
3. 标题过长
4. 冒号式报告题
5. 开头抽象套话过重
6. 没有具体收益
7. 缺少作者判断
8. 封面或配图模板味过重
9. 长文但来源和论证密度不足

### 9.2 人工门槛

这篇额外增加 5 条人工确认：

1. 三平台标题不能复用。
2. 三平台开头前两段不能复用。
3. 日期、事实点、产品能力描述逐条对齐来源。
4. 配图角色分工完成，不是同一模板平移。
5. 平台规则风险为零容忍，不做夸大承诺和重复发布占位。

### 9.3 通过标准

只有同时满足以下 4 条，才进入发布占位：

1. 自动预检 `passed`
2. 三平台标题、摘要、开头分化完成
3. 多角色配图方案完成
4. 人工事实核对和平台风险检查无阻塞项

## 10. 实施顺序

在你确认书面 spec 之后，下一轮执行顺序固定为：

1. 重写统一事实底稿
2. 同步更新 `payload + article.md + body.txt + title-variants.md`
3. 补齐三平台差异化标题、摘要、开头
4. 产出本篇配图方案
5. 运行三平台 `preflight-only`
6. 记录预检结果与阻塞项
7. 只输出发布占位，不触发正式发布

## 11. 风险与控制

### 11.1 风险

1. 平台化改写幅度不足，最后又退回“一稿三发”。
2. 标题分化做了，但首屏节奏没有分化，预检仍然会被打低。
3. 配图换了内容词，但骨架没变，继续暴露模板味。
4. 事实判断正确，但日期和能力表述不够精确。

### 11.2 控制方式

1. 明确把标题和开头前两段列为分化硬规则。
2. 把配图按角色而不是按数量管理。
3. 预检前先做人工事实对齐。
4. 任何一项不满足，就只回到修改，不进入占位。

## 12. 成功标准

本轮完成不以“已经发出”为标准，而以下列条件为准：

1. 这篇主稿的四类源文件已经统一更新。
2. 三平台标题、摘要、开头差异清楚，不存在低差异平移。
3. 配图方案明确体现多角色、多骨架，不再是单一模板复用。
4. 三平台预检全部完成，能清楚说明为什么通过或为什么被拦。
5. 最终只产生发布占位结果，不产生正式发布动作。
