# 工作台方案 v1：把 88 个接口、210 个脚本收进一个门面

> 日期：2026-10-12 ｜ 作者：Codex ｜ 任务：WK-20261012-01
> 性质：调研 + 方案（本文件不含代码改动）｜ 第一版实施见 §6 阶段 1
> 依据：本机实测盘点（§3）+ 联网检索与情报库存量（§2）
> 定位：本方案是「门面层」方案，不改动任何既有能力与真相源

---

## 0. 结论先行

**我们不需要再装一个「工作台产品」——工作台的后端早就建好了。**

能力注册表（接口 → primary → fallback）、调度真相源（cron jobs.json）、任务态台账（协同/任务台账.md）、产出真相（vault 内容生产/知识库）这四样，本身就是别人做工作台时最缺的那部分。我们缺的只有两件：

1. **一面只读的门**：今天该干什么、系统正在跑什么、东西放哪、每个能力怎么调用，一屏看完；
2. **一条按名字调用的入口**：不想记路径，说出名字就跑起来。

所以本方案就做这两件事，其余全部复用：

| 要做 | 新建物 | 复用物 |
|---|---|---|
| 只读门面 | `scripts/workbench_digest.py` + 两份渲染产物（md / html） | `cron_overview.py` 的确定性再生成范式 |
| 调用入口 | `scripts/workbench.py <关键词>` | `tool_inventory.py` 的匹配逻辑、`tool_registry.json` 的路由 |
| 核验一处我以为的缺口 | — | toolkit MCP 在 Codex 侧实测已可用（见 §2.3 更正） |

**明确不做**：不新造能力；不做云控制面/多租户；不让 LLM 生成状态数字；不把 210 个脚本都搬上面板（只上 88 个登记接口 + 高频入口）；不新建第二份真相。

### 1.2 产品侧：腾讯 WorkBuddy 的实际形态

博主们多半在讲同一件事：用 **WorkBuddy** 生成个人面板。官方文档（workbuddy.ai/docs/zh/workbuddy/Overview）给的形态是：一句话下任务 → 自主规划执行 → 交付可验收结果；功能面 = 任务 / 助理 / 专家 / 技能 / 连接器 / 探索 / 自动化 / 记忆 / 右侧边栏 / 模型配置；其中「实践七：零代码制作本地应用」正是让 AI 直接生成一个本地面板应用。

**这件事与我们直接相关：本机已经装了 WorkBuddy AI**（`AppData\Local\Programs\WorkBuddyAI`，配置在 `~/.workbuddy-ai`），并且它已经在 code-news 里干过活——`code-news/.workbuddy-ai/memory/` 里存着 2026-09-20、2026-10-04 的工作日志（文档引用校验自动化的两次执行记录）。

### 1.3 大厂方向：入口在往任务边上挪

我们 2026-07-15 采集的头条文《共享 Agent，正在把聊天框变成工作台》把三条信号放在一起：OpenAI workspace agents（agent 从个人技巧变组织资产）、Google Gemini Spark（24/7 personal agent 嵌回 Gmail/Docs/Drive）、Microsoft 的 Author → Editor → Director → Orchestrator 四层。共同结论是：**入口离任务越近，AI 越有机会接住一段连续流程**；胜负手是上下文留存、跨步骤推进、关键节点人工接管。

### 1.4 生态侧：技能太多是个公共问题，我们的对应物已存在

检索到的工具生态文章（`Skiller：一款跨平台的 AI Skills 管理工具`、`Skills Manager 体验笔记`）都在解决同一个痛点：技能散落在各工具的目录里，需要集中管理、预览、按项目分发、软链到目标目录。**我们已经有等价物**：`C:\Users\Administrator\.agents\skills`（共享 hub，35 个）+ `scripts/sync_agent_skills.py`（符号链接/副本分发 + `--verify`）。所以这一层不用重做，工作台只需要**把它显示出来**。

### 1.5 五个样本的共同规律（本方案的设计输入）

1. 工作台不是新系统，是**已有能力的一个门面**；
2. 门面上必须能看到**「现在到哪一步了 + 哪一步在等我」**，这是博主们最强调的一点；
3. 模块之间要能**一键流转**（选题 → 文案 → 剪辑），而不是靠人搬运；
4. **先出功能清单，再开发**；上线后按「现状—问题—期望」增量纠偏，不推翻重做；
5. 状态要可信。我们的口径更严：**确定性流程禁用 LLM**（vault 经验沉淀铁律），所以面板数字一律脚本现算。

## 3. 方案：三层结构，只新建门面层

```
L2 调用层   一条命令 / 面板按钮      workbench.py「<名字>」  + 收敛的 .bat/.cmd
                   ↑ 按名反查
L1 门面层   只读面板（本方案唯一新建物）  工作台总览.md（Obsidian）+ 工作台.html（双击）
                   ↑ 确定性生成，零 LLM
L0 事实层   四个真相源（一律只读，不动）
            tool_registry.json ｜ ~/.hermes/cron/jobs.json ｜ 协同/任务台账.md ｜ vault 产出目录
```

### 3.1 面板的六个区块（每块都能指到唯一来源）

| 区块 | 回答什么问题 | 取数来源（只读） | 生成方式 |
|---|---|---|---|
| ① 在等我 | 哪几件事卡在「进行中/待审/待你确认」 | `协同/任务台账.md` 状态列 + `协同/交接/*.md` 最后一块 | 解析表格行 |
| ② 系统在跑什么 | 41 个启用任务的排期、最近一次跑没跑、产出落在哪 | `~/.hermes/cron/jobs.json` + `运行手册/定时任务总览与资源窗口规划.md`（cron_overview 再生）+ cron 逐日台账 | 直接读，不重算 cron 语义 |
| ③ 今天产出了什么 | 采集/选题/稿子/发布各线最近产出时间（判据是**最近产出时间**而非文件数） | vault `内容生产/1-情报与选题`、`2-调研与素材`、`5-发布` 各目录最新文件时间 | 目录 mtime 扫描 |
| ④ 我能调什么（核心） | 登记接口（写方案时 88，现 90），按 采集/分析/创作/视频/发布/协同 分组；每条给出「叫什么 + 怎么调 + 找谁兜底」 | `config/tool_registry.json`（primary/fallbacks/purpose/mode） | 直接渲染注册表 |
| ⑤ 账号与发布 | 账号体检结论、发布台账闭环有没有缺口 | `内容生产/5-发布/账号体检总览.md`（account_dashboard cron 产物）+ 发布台账 | 读产物 |
| ⑥ 一键入口 | 启动代理栈 / 跑主管线 / 开工三查 / 收工三写 / 打开 vault / 矩媒 / 格映 | 现有 .bat/.cmd 与脚本，做**薄封装**（不改脚本） | 列命令 + 双击执行 |

告警（面板顶部一行）：最近失败的任务、`check_doc_references.py` 的 MISSING 增量、发布闭环缺口——沿用各自既有输出，不新增监控。

### 3.2 调用层：一条命令，不记路径

```
python scripts/workbench.py 爆款拆解        → 命中 viral-video-breakdown（技能）→ 打印怎么触发
python scripts/workbench.py 对标视频入库     → 命中 scripts/ref_video_intake.py + 用法示例
python scripts/workbench.py --run 对标视频入库 <链接>  → 确认后直接执行
```

> 语法口径：**查询只吃一个词**（含空格请加引号），后面的参数一律透传给目标脚本；
> 命中不是第一条时用 `--pick N` 挑。命中的形态不能命令行执行（技能 / 会话内 MCP 工具）时，
> 明确拒绝并告诉你该怎么触发，退出码 2——不装作跑过。

实现上不新写匹配算法：`tool_inventory.py` 已经在做「关键词 → 已有实现」的检索，`workbench.py` 是它的人在环版本（多了 registry 路由和 fallback 提示）。这正是仓库「复用守则」要的**扩展合并**，不是新建能力。

### 3.3 宿主选型

| 方案 | 优点 | 代价 | 结论 |
|---|---|---|---|
| **A. Markdown 面板（vault 内）** | 零依赖、手机/平板 Obsidian 也能看、随 vault 同步 | 交互弱（只能点链接） | **先做**（阶段 1 一起出） |
| **B. 静态 HTML 面板（双击打开）** | 可以放按钮、分组折叠、本地零依赖 | 一份额外渲染产物 | **先做**（阶段 1 一起出） |

A 与 B 由**同一个脚本、同一份数据**生成，只是两种渲染，不产生维护分叉。

## 5. 红线与边界

1. **面板只读**：不写上游、不改生产目录、不替人做发布决策；
2. **面板数字一律确定性生成**：零 LLM（铁律：确定性流程禁用 LLM）；生成不出来的就不显示，不猜；
3. **正式发布仍默认关闭**：门面不改变任何发布闸门（知乎线按既有裁定自动公开，其余平台保持人工确认）；
4. **不上云控制面**：人月聊IT 那套「控制面/执行面分离 + 多租户」是企业场景，我们是单机个人工作流，分层照抄思维即可，基础设施不搬；
5. **不追求全覆盖**：先覆盖 88 个登记接口 + 高频入口；210 个脚本里的实验留痕（agnes_* 等）不进面板，确有价值再单独归档；
6. **不成为第二份真相**：面板所有数字必须能从来源文件现算复查；对不上时以来源为准，并修面板。
