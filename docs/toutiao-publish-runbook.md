# 头条文章发布运行手册

更新时间：2026-05-24

## 目标

这份文档用于沉淀今日头条图文发布链路的操作规则、自动化流程、已验证机制和踩坑记录，减少重复发布、误删、漏图、封面异常等问题。

适用范围：

- 头条号图文文章发布
- Playwright 自动化发布
- 封面图与正文配图生成
- 发布后校验与异常清理

相关脚本：

- `.tmp/render_toutiao_assets.js`
- `.tmp/publish_toutiao_article.js`

相关记录文件：

- `.tmp/toutiao-publish-records.json`
- `.tmp/generated/<slug>/debug/*.json`
- `.tmp/generated/<slug>/debug/*.png`

## 硬规则

以下规则必须执行，不能省略：

1. 相同内容只能发布一次。
2. 已发布或已提交审核的同一篇内容，不能再用“新发文章”方式重复提交。
3. 如果需要修改已发内容，必须走后台的`修改`入口，不能重新发一篇同标题同正文的新文章。
4. 自动化验证不能再拿已经发布过的 payload 做二次发布测试。
5. 发现重复发布后，先确认应保留的版本，再删除重复项，不能直接批量删。

## 标准发布流程

### 1. 选题与去重预检

发布前先确认这篇内容没有在头条账号里出现过。

必须同时检查两层：

- 本地记录：`.tmp/toutiao-publish-records.json`
- 头条后台列表：`https://mp.toutiao.com/profile_v4/graphic/articles`

当前脚本已加入以下去重机制：

- 用正文摘要、正文段落、来源列表生成 `contentFingerprint`
- 命中相同 `contentFingerprint`、相同 `slug` 或相同 `title` 时直接拦截
- 拦截时返回 `duplicate_blocked`

注意：

- 远端文章列表如果没有真正加载出作品卡片，不能继续发布
- “审核中”也视为已占用该内容，不能再发第二次

### 2. 准备 payload

payload 至少应包含以下字段：

- `slug`
- `title`
- `summary`
- `cover`
- `article_blocks`
- `body_images`
- `sources`

要求：

- `slug` 唯一，不能复用
- 标题、摘要、正文要与历史作品区分开
- `body_images` 明确插图插入位置，使用 `insert_after_block`

### 3. 生成文章与图片资产

执行：

```bash
node .tmp/render_toutiao_assets.js .tmp/toutiao_payload_xxx.json
```

生成物通常在：

```text
.tmp/generated/<slug>/
```

核心产物：

- `article.md`
- `body.txt`
- `cover.png`
- `body-01.png`
- `body-02.png`
- `body-03.png`
- `manifest.json`

### 4. 登录态确认

发布脚本使用持久化 Chrome 用户目录：

```text
.tmp/browser-profiles/toutiao
```

要求：

- 登录头条创作者后台
- 能正常进入发布页
- 如有弹窗，先关闭后再继续

### 5. 填写标题、摘要、正文

执行：

```bash
node .tmp/publish_toutiao_article.js .tmp/toutiao_payload_xxx.json
```

当前脚本已验证可完成：

- 填写标题
- 填写摘要
- 逐段写入正文
- 在指定段落后插入正文配图

## 正文配图链路

这部分已经打通，结论如下：

1. 不是调用系统文件弹窗。
2. 点击工具栏图片入口后，页面会注入 `input[type=file]`。
3. 可以直接用 `setInputFiles` 喂图。
4. 喂图后必须点击确认按钮，图片才会真正插入正文。
5. 插图后要把光标移到图片块下面，才能继续输入后续正文。

已验证行为：

- 工具栏图片按钮可用
- 上传后会出现确认态
- 确认后正文里会出现图片块
- 一张正文图在 DOM 中可能对应两张 `img`，所以判断是否插入成功时，要按图片块数量统计，不能只按 `img` 数量统计

当前正文插图成功的可靠证据：

- `editorImageBlockCount`
- `after-body.png`

## 封面链路

封面链路可用，但有一个重要平台行为必须记住。

已确认：

1. 点击封面区域后，页面也会插入文件 input。
2. 可以直接 `setInputFiles` 上传封面。
3. 页面可能同时存在多个候选 file input，脚本要顺序尝试。

关键注意事项：

1. 头条会根据正文里的 3 张图自动提升成“三图封面”。
2. 如果正文先插入了 3 张图，平台很可能自动选用这 3 张图作为封面。
3. 自定义单封面 `cover.png` 不一定能稳定覆盖掉平台自动生成的三图封面。

当前稳定结论：

- 正文配图 + 自动三图封面是稳定的
- 强制替换成单张自定义封面，仍需要额外验证，不能默认成功

因此发布前要区分两种目标：

- 如果接受平台自动三图封面，现有链路可用
- 如果必须固定单封面，发布前必须肉眼确认封面区域已切到正确状态

## 发布前检查清单

点击“发布”前必须过一遍下面这份清单：

1. 这篇内容没有在头条后台出现过。
2. `duplicate-preflight.json` 没有命中重复拦截。
3. 标题、摘要、正文都已写入。
4. 正文插图数量正确。
5. 封面状态符合预期。
6. 页面没有遮挡弹窗、抽屉或确认框未关闭。
7. 当前准备发布的是最终版本，而不是测试版本。

建议保留以下快照：

- `ready`
- `after-body`
- `after-cover`
- `before-publish`
- `after-publish`

## 发布后校验

发布完成后必须回到文章列表页确认：

1. 是否出现新条目
2. 时间是否符合本次提交时间
3. 状态是`审核中`还是`已发布`
4. 是否意外生成了重复条目

不要因为看到“提交成功”就结束，后台列表页才是最终校验点。

## 删除与清理

如果确实出现重复发布，处理顺序如下：

1. 先确认要保留的那一条
2. 再按时间精确定位重复条目
3. 删除时填写删除理由
4. 删除后刷新列表，确认只剩目标版本

已验证的后台行为：

- 对已推送内容删除时，会弹出确认框
- 删除理由是必填项
- 没填理由时，点确认不会真正删除

建议删除理由模板：

```text
重复发布，保留 <时间> 版本
```

## 本次项目中确认过的坑

### 1. 最大事故：重复发布

原因：

- 对已发布 payload 再次执行了真实发布
- 初版预检没有等远端列表完全加载

规避方式：

- 同内容只发一次
- 去重预检未通过时直接退出
- 远端列表没加载完整时直接拒绝发布

### 2. 正文无图误判

原因：

- 早期只做了封面上传，没有实现正文插图

规避方式：

- 把“封面上传”和“正文配图上传”视为两条独立链路
- 发布后先看 `after-body.png`，不要只看封面区域

### 3. 封面被平台自动改成三图

原因：

- 正文插入 3 张图后，平台自动生成三图封面

规避方式：

- 把“自动三图封面”当成当前默认稳定结果
- 需要单封面时单独验证，不要口头假设已替换成功

### 4. 删除失败但界面看起来像点到了

原因：

- 删除确认框要求填写理由

规避方式：

- 自动化里把删除理由写成强制步骤

## 推荐工作方式

以后处理头条发布，建议固定用下面这套顺序：

1. 先确认选题唯一性
2. 再生成文章与图片
3. 再跑发布脚本
4. 发布前看 `after-body` 和 `after-cover`
5. 发布后看后台列表
6. 如有异常，先截图再处理

## 当前结论

截至 2026-05-24，这条链路的成熟度如下：

- 正文生成：可用
- 正文配图上传：可用
- 自动发布：可用
- 重复发布拦截：已补上，必须保留
- 自动三图封面：可用
- 强制单封面替换：未完全稳定，需继续验证

## 后续改进建议

1. 把远端去重从“标题匹配”升级成“标题 + 时间 + 内容摘要”联合判断。
2. 给发布脚本增加 `--dry-run` 模式，只做预检与截图，不点发布。
3. 给单封面模式增加专项验证脚本，避免把平台自动三图误判成单封面成功。
4. 给删除脚本单独封装成安全工具，只允许按“标题 + 时间”双条件删除。
